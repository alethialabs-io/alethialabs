Alethia stores no static cloud credential for AWS, GCP or Azure. The control plane is its own OIDC
issuer: it signs short-lived assertions, and each cloud exchanges one for a session of about an hour
on a role, service account or managed identity that you create and can delete at any time.

## How it works

### The issuer

The issuer lives at `${APP_URL}/api/oidc` and publishes its public keys and an OIDC discovery
document. Each assertion it signs lasts 10 minutes or less, has the fixed subject `alethia-connector`,
and names one cloud as its audience: `sts.amazonaws.com`, `alethia-gcp-wif` or
`api://AzureADTokenExchange`. The audience stops an assertion for one cloud being replayed at another.

The only long-lived secret is the issuer's signing key, `ALETHIA_OIDC_SIGNING_KEY`, held by the
control plane. To revoke Alethia's access, delete the role, the federation provider or the managed
identity in your account. How a runner uses the assertion during a job is in
[Cloud credentials](/concepts/runner/cloud-credentials).

### Per cloud

| | AWS | GCP | Azure |
| --- | --- | --- | --- |
| You create | An IAM OIDC provider for the issuer, and `AlethiaProvisionerRole`, whose trust policy allows only `sts:AssumeRoleWithWebIdentity` from that provider for the fixed audience and subject | A Workload Identity Pool with an OIDC provider for the issuer, and a service account bound with `roles/iam.workloadIdentityUser` | A user-assigned managed identity with a federated credential for the issuer, in your subscription. No app registration |
| Alethia stores | The role ARN | The project ID and federation configuration | The tenant, subscription and client IDs |
| Permissions | Five scoped policies instead of `AdministratorAccess` | 11 predefined and 5 custom roles instead of `roles/editor` | A custom "Alethia Provisioner" role instead of `Contributor` |

There is no ExternalId and no trust in an Alethia AWS account: the subject and audience pin replaces
it. No access key, service account key or client secret exists.

### What Alethia may do in your cloud

The trust controls who may use the role. The permissions control what it may do.

- **AWS.** Four data-plane policies list the specific EC2, EKS, RDS and other actions the templates
  use. An IAM policy lets the templates create the roles they need, explicitly denies attaching
  `AdministratorAccess`, `PowerUserAccess` or `IAMFullAccess`, limits `PassRole` to the provisioned
  services, and denies `organizations:*`, `account:*` and billing. Reads stay `Describe*`, `Get*` and
  `List*`. See [Connect AWS](/guides/connectors/aws).
- **GCP.** Predefined admin roles for services whose Google-maintained role is already narrow, such as
  GKE, networking, Cloud SQL and DNS. Five custom roles replace admin roles that included data access:
  bucket management without object data, Firestore management without entity data, Pub/Sub management
  without publish or consume, add-on service account management, and a project metadata reader. IAM
  bindings are scoped to resources, so the provisioner needs no project `setIamPolicy`.
  `cloudkms.admin` creates the key for Kubernetes Secrets encryption but cannot use it. See
  [Connect GCP](/guides/connectors/gcp).
- **Azure.** The custom role lists only the actions the services need. Its one escalation-grade
  permission, `roleAssignments/write`, is limited by a condition to the built-in DNS Zone Contributor
  role, for external-dns, so it has no path to Owner. See [Connect Azure](/guides/connectors/azure).

### Hetzner

Hetzner has no federation, so it is not keyless. It uses one API token, scoped to a whole Hetzner
project. You choose to store it encrypted in Alethia, or to keep it only in your own runner so it never
enters Alethia's database. See [Cloud credentials](/concepts/runner/cloud-credentials#hetzner).

### Key rotation

The signing key rotates without downtime. During the overlap, the published key set holds the old and
the new key, and each assertion's `kid` header selects one. New assertions use the new key; the old
one is retired once every cloud has refreshed its copy of the key set. See
[Rotating the issuer signing key](/self-host/managed-cloud-connectors#rotate-the-issuer-signing-key).

### Execution isolation

Keyless credentials control who can reach a cloud. [Isolated execution](/concepts/isolated-execution)
controls what provisioning code can do once it runs. Alethia's own templates run in the runner. Your
OpenTofu or Helm runs, on the managed fleet, in a per-job container with no platform secrets, no cloud
metadata, and egress only to allowed domains. One job's state token reaches only its own state, and
cloud credentials are minted per job.

### Signing in

People sign in to the console with OAuth or an email code, and to the CLI with a device grant or a
service-account token. Runners use a per-runner token stored only as a hash. See
[Authentication](/concepts/authentication).

### Row-level security

Every table that belongs to an organization has a Postgres row-level security policy on its
organization ID. Each request sets the active organization, so even a query that forgets to filter
returns only that organization's rows. Role and permission decisions are made above it, by the
[access control](/concepts/access-control) layer.

### Git tokens

OAuth tokens for GitHub, GitLab and Bitbucket are kept on your sign-in account. Alethia checks a
token's expiry before use and refreshes it through the provider. A job gets the token when it needs
it, never in its snapshot.

## What it does not do

- It does not store a cloud key for AWS, GCP or Azure.
- It does not give the connector account admin rights in any cloud.
- It does not make Hetzner keyless.
- It does not let one job read another job's state.
