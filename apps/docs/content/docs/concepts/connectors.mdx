# Connectors architecture

Connectors decouple **what** a Project needs (a DNS zone, secrets, a registry, observability) from **who** provides it. A **connector** is a provider *type* in the catalog; an account you actually connect to a cloud is a **cloud identity** (see the [glossary](/reference/glossary#connectivity)). Cloud and Git connectors are first-class; the **pluggable per-category** connectors are added by registration, not by editing call sites.

This page explains how the catalog is built and how credentials flow. To connect an account, read its status, or disconnect it, see [Connectors](/guides/connectors).

## Single source of truth

Every pluggable provider is declared once in a manifest, `packages/core/categories/catalog.json` (slug, category, `auth_method`, icon, credential fields, provider-config fields, module path). That manifest is consumed three ways so the provider set never drifts:

- **Go** loads it with `go:embed` (`packages/core/categories`) to resolve which module to compose and what credential a provider needs.
- **Codegen** (`pnpm -F console gen:connectors`) emits the typed TS registry (`lib/connectors/registry.generated.ts`) that drives the credential form and the Project provider selectors, plus the SQL seed of `connectors` catalog rows.
- **Behavior** that can't be data — `Tfvars()` and `Validate()` — lives in small per-slug Go impls.

This mirrors the [cloud-provider registry](/concepts/cloud-abstraction) one level down, per category.

## The `CategoryProvider` contract

Each provider impl exposes a small interface: `Category()`, `Slug()`, `ModulePath()`, `Tfvars(ctx)` (maps the component's config + decrypted credential into module variables), and `Validate(ctx)` (rejects nonsensical combinations before a plan is produced). A registry resolves a provider by `(category, slug)`.

## Credential storage

API-key credentials live in the `connector_credentials` table, owner/org-scoped under the same RLS as everything else. Secret fields are encrypted at rest with AES-256-GCM (`ALETHIA_CRED_ENCRYPTION_KEY`); non-secret fields (a Vault address, a Docker Hub username) are stored in clear.

## Runtime credential flow

The zero-credential model is preserved end to end:

1. A Project's `config_snapshot` carries only **identifiers** — including each component's chosen provider slug — never secrets.
2. When a runner **claims** a job, the claim endpoint (`app/api/jobs/claim/route.ts`) resolves the connectors the Project references, decrypts their credentials **in the console**, and attaches the plaintext to the claim response (alongside the cloud identity). The runner never holds the encryption key.
3. The runner injects them into OpenTofu variables **in memory** at provision time.

## Module composition

For each component with a pluggable provider, the runner copies the provider's module from `infra/templates/categories/<category>/<slug>/` into the working directory, writes a generated `_categories.tf.json` wiring the module with its variables, and sets a `<category>_provider` guard variable. The cluster-cloud templates gate their native resources on that variable (`count = var.dns_provider == "native" ? 1 : 0`), so the native resource is **skipped** when a pluggable provider is chosen. Observability is purely additive (no native default).

## Open-core

Connectors are core value and stay AGPL/community — the registry-of-record (`connectors` table) and the category contract are community. Only premium connectors or org-scoped connector governance would live in `ee/` (see [Open Core](/concepts/access-control/open-core)).
