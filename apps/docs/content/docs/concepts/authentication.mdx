Alethia has three callers and a way to sign in for each. People use the console with an OAuth
provider or an email code; the CLI gets its tokens through the browser or uses a service-account
token; a runner presents a token whose hash Alethia stores.

## How it works

### The console

| Sign-in | Method |
| --- | --- |
| GitHub, Google | OAuth 2.0 |
| GitLab, Bitbucket | OAuth 2.0 |
| Email | A 6-digit one-time code |

After sign-in, Alethia creates a server-side session and sets a signed, HTTP-only cookie. The session
is not a JWT. Each request checks the cookie and sets your active organization, and every action then
goes through [access control](/concepts/access-control). Sign-in with
[SSO](/guides/access/sso) is an Enterprise feature.

### The CLI

A terminal cannot host an OAuth redirect, and you should never type a password into one. So
`alethia login` uses a flow modeled on the OAuth 2.0 Device Authorization Grant (RFC 8628): the
browser does the sign-in with any method the console supports, and the terminal receives a token pair.

- The access token lasts 1 hour; the refresh token 90 days.
- The CLI's tokens are separate from the console's session.

A pipeline has no browser, so it uses a **service-account token**: created once, passed in
`$ALETHIA_TOKEN`, acting as its creator in one organization, limited by the scopes and projects it was
created with.

The protocol and its differences from RFC 8628 are in
[Device Authorization Grant](/reference/standards/device-code). Signing in, token storage and service
tokens are in [CLI authentication](/reference/cli/authentication).

### Runners

When a runner is registered, Alethia generates a random token, stores only its SHA-256 hash, and shows
the token once. Every runner request carries `X-Runner-ID` and `X-Runner-Token`; Alethia hashes the
token and compares it with the stored hash in constant time. A lost token cannot be recovered:
register the runner again.

Managed fleet VMs start with a short-lived bootstrap token minted for that VM and exchange it for
their runner token. See [Warm-pool scaling](/concepts/runner/scaling).

| Caller | Method | Lifetime | Kept in |
| --- | --- | --- | --- |
| Console | OAuth or email code | Session, refreshed | Signed HTTP-only cookie |
| CLI | Device grant, or a service-account token | Access 1 hour, refresh 90 days; a service token until revoked or expired | The system keychain, or `$ALETHIA_TOKEN` |
| Runner | Token checked against a stored hash | Until the runner is registered again | The runner's environment |

## What it does not do

- It does not decide what you may do. That is [access control](/concepts/access-control).
- It does not store a runner's token, only its hash.
- It does not use the console's session for the CLI.
