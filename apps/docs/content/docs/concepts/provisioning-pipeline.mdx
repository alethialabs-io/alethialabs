When you plan or deploy an environment, Alethia freezes its design into a snapshot on the job. A
runner turns the snapshot into OpenTofu variables for that cloud's template, plans, checks the plan,
applies exactly that plan, and then sets up the cluster.

## How it works

### 1. Design

You design the environment on the canvas, in the CLI, or from a proposal. A proposal comes from
scanning your source repositories: Alethia reads each repository without running it, detects its
services (a monorepo gives several), and proposes the components they need. You review the proposal
before anything is saved.

### 2. Snapshot

When a job is queued, Alethia reads every component of the environment and stores the result on the
job as its configuration snapshot. The job runs that snapshot, even if you edit the design afterwards.
When a signing key is configured, the snapshot is signed, and the control plane fails a job whose
snapshot changed after it was queued instead of handing it to a runner. The snapshot carries identifiers, never secrets: the Git token and
connector credentials reach the runner separately, at claim time.

### 3. Variables

The runner reads the snapshot and maps each field to the variable names of the cloud's template, for
example the cluster version to `eks_cluster_version`, `gke_cluster_version` or
`aks_cluster_version`. It writes them to `terraform.tfvars.json`. No templating engine edits the
`.tf` files: the templates are plain OpenTofu with `variable` blocks.

### 4. Plan

The runner initializes OpenTofu against the [state proxy](/concepts/terraform-state), runs
`tofu plan`, and saves the binary plan with the control plane. If an Infracost key is configured, it
also prices the plan (see [Cost estimation](/concepts/cost-estimation)).

### 5. Check

[Elench](/concepts/elench) evaluates the plan before anything is applied. On a plan job the report is
shown in the Plan tab. On a deploy, a failing hard control that no one waived stops the job before
`tofu apply`.

### 6. Apply

A deploy applies the plan you reviewed, not a new one. The deploy names the plan job and the SHA-256
of its plan file. The runner downloads the file, checks the digest, and refuses the deploy if:

- the plan job did not succeed;
- the configuration changed since the plan (plan again);
- the plan file is missing, or its digest does not match.

A deploy that names no plan job, such as an automatic re-apply, plans afresh.

### 7. Cluster setup

After the apply, the runner reads the OpenTofu outputs, writes a kubeconfig that mints short-lived
tokens (no cloud CLI), checks that the cluster answers, installs ArgoCD and the cluster services, and
generates manifests for your detected services. It commits manifests only to an empty apps
repository, so it never overwrites yours. See [GitOps and ArgoCD](/concepts/gitops-argocd).

The control plane then records cluster endpoints, database endpoints and the ArgoCD address on the
environment and sets it `ACTIVE`. Passwords, kubeconfigs and tokens are removed from the job's
results before they leave the runner.

## What it does not do

- It does not apply a plan nobody reviewed, when the deploy names one.
- It does not store secrets in the snapshot.
- It does not overwrite an apps repository that already has manifests.
- It does not create resources it can reuse: a component marked existing, such as a network, is read
  with a data source instead. See [Reuse existing resources](/guides/design-project/network#use-an-existing-network).
