A bring-your-own chart is a Helm chart from your own Git repository or OCI registry, deployed next to
marketplace add-ons in the same cluster. It is not Alethia's code, so ArgoCD runs it under a narrow
project: its own namespace, a short list of allowed kinds, and no pruning or self-heal.

To attach, scan and bind a chart, see
[Bring your own Helm charts](/guides/design-project/bring-your-own-charts). It is separate from
[bring-your-own IaC](/concepts/bring-your-own-iac), which provisions infrastructure from your OpenTofu.

## How it works

### Each deploy

On every environment deploy, Alethia:

1. creates the chart's namespace, because the chart may not create one, and sets its
   [admission rules](/concepts/chart-admission);
2. stores a credential for the chart's repository in a Secret scoped to that repository, so no chart
   can read another chart's token or the apps repository's;
3. applies the chart's ArgoCD project;
4. applies the Application, which then syncs on its own.

An OCI chart uses the credential of your registry connection instead of a Git token. Everything is
applied again on each deploy, so a change takes effect on your next deploy.

### Where your chart runs

Each chart runs in a namespace of its own. If you leave the namespace blank, it is `byo-` and the
chart's ID: a chart named `payments` runs in `byo-payments`.

A chart cannot target:

- a Kubernetes system namespace, such as `kube-system`;
- a namespace where platform controllers or marketplace add-ons run;
- `default`, where your environment's own services run;
- a namespace that starts with `byo-`, unless it is the chart's own;
- a preview namespace: the prefix set in the project's **Preview environments** settings, or anything
  that starts with the prefix and `-`, because untrusted pull request code runs there. Alethia also
  refuses a prefix change, or turning previews on, that would put an attached chart in a preview
  namespace.

A chart attached before these rules keeps its namespace, and each deploy warns about it on the
**Deploy** tab. A chart that ran in `default` moves to its own namespace on the next deploy; what it
created in `default` stays there, no longer managed by ArgoCD, until you delete it. Each of those
objects carries an `argocd.argoproj.io/tracking-id` annotation that starts with `addon-<chart id>:`.

### A push to the tracked ref deploys

ArgoCD watches the chart's ref (`HEAD` by default). A commit to a tracked branch deploys on its own,
with no Alethia deploy and no approval. So write access to that branch is deploy access to that
namespace. To make deploys explicit, attach a tag or a full commit SHA: the cluster then changes only
when you change the ref. A push cannot escape the project: every sync is checked against it.

### Sync behavior

| | Marketplace add-on | Your chart |
| --- | --- | --- |
| Deployed automatically | Yes | Yes |
| Prune: delete resources no longer in the chart | Yes | No |
| Self-heal: revert changes made in the cluster | Yes | No |

**A resource you remove from the chart keeps running.** Delete it with `kubectl`, or remove the chart.

**A change you make in the cluster stays.** ArgoCD shows the Application `OutOfSync` and leaves it. A
deploy alone does not revert it, because there is nothing new to sync. To revert it, push a commit to
the ref, delete the edited resource so the next sync recreates it, or sync the Application in ArgoCD.

### What your chart may create

The project denies by default. A chart may create only these namespaced kinds, in its own namespace.
A chart that declares any other kind fails its sync, and the result names the resource.

| Kind | API group |
| --- | --- |
| `Deployment`, `StatefulSet`, `DaemonSet`, `ReplicaSet` | `apps` |
| `Job`, `CronJob` | `batch` |
| `Pod`, `ConfigMap`, `Secret`, `PersistentVolumeClaim`, `Service` | core |
| `Ingress` | `networking.k8s.io` |
| `HorizontalPodAutoscaler` | `autoscaling` |
| `PodDisruptionBudget` | `policy` |

The API group is part of the match: an `Ingress` from the old `extensions` group is refused.

Left out on purpose:

- **Cluster-scoped kinds**, such as `Namespace`, `ClusterRole` or `CustomResourceDefinition`.
- **`Role`, `RoleBinding` and `ServiceAccount`.** A chart that could make its own identity could grant
  itself more than the project allows. Charts often create a `ServiceAccount` by default: set
  `serviceAccount.create: false` or its equivalent.
- **Secret-sync kinds** from `external-secrets.io`. A chart reads only the secrets its
  [bindings](/guides/design-project/bring-your-own-charts#bind-a-workload-to-your-infrastructure)
  create. Each deploy deletes such objects that no binding accounts for, and names them.
- **Kinds an operator serves**, such as a cert-manager `Certificate` or an ArgoCD `Application`.
- **`Endpoints`, `EndpointSlice`, `ResourceQuota`, `LimitRange` and `NetworkPolicy`.**

The project also allows only your chart's repository as a source and only its namespace as a
destination. To ask for another namespaced kind, open a support case with the kind, its API group and
what the chart uses it for. A kind added to the list applies to every bring-your-own chart.

### Removing a chart

Removing the add-on deletes its Application. ArgoCD's finalizer then deletes everything the chart
created in its namespace, including resources that pruning would have left. The namespace stays.

## What it does not do

- It does not let a chart create cluster-scoped resources. Split that part out, or ask for it as a
  marketplace add-on.
- It does not prune or self-heal your chart.
- It does not require an approval for a push to a tracked branch.
