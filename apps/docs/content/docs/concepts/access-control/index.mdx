Every action in Alethia passes one authorization check before it runs. You act in an organization;
you hold roles through grants; each role carries permissions; and a permission is the right to take
one action on one kind of resource. Anything not granted is denied.

## How it works

### The terms

- **Actor**: a signed-in user, or a service token, in their active organization.
- **Resource**: something you act on, such as a project, runner, cloud identity, job, connector or
  member.
- **Action**: what you try to do, such as `view`, `edit`, `plan`, `deploy` or `destroy`.
- **Permission**: one `resource:action` pair, such as `project:deploy`. Only the pairs in the
  [permission matrix](/concepts/access-control/roles-and-permissions#the-matrix) exist.
- **Role**: a named set of permissions: `owner`, `admin`, `operator` or `viewer`.
- **Grant**: a principal holds a role at a scope: the whole organization, or one project.

### One decision point

A single decision point answers every question. It allows a request or refuses it with
`403 Forbidden`, and list views ask it which resources you may see, so a list is filtered by your
grants, not only hidden in the UI. Every denial, and every allowed action that changes something, is
recorded in the [Activity log](/guides/access/activity-log).

There is no shortcut such as "the creator of a row can do anything". A grant on the organization
covers every project in it; a grant on a project covers only that project.

### Two layers

Below the decision point, Postgres [row-level security](/concepts/security#row-level-security) limits
every query to the active organization's rows. The decision point decides what you may do; row-level
security decides whose data a query can reach. A cross-organization leak needs both to fail.

### Engines

The decision point has one interface and two engines. The default engine reads grants from Postgres
and is part of the open-source Community edition. Enterprise can use [OpenFGA](/concepts/access-control/openfga)
instead, for large tenancies. Both give the same answer for every request.

### Editions

The whole model above is in the free Community edition, where each user is the only owner of a
personal organization. Enterprise adds organizations with several members, teams, invitations, SSO,
custom roles, the access portal and Activity export, with no change to how permissions are decided. See
the [feature matrix](/editions/feature-matrix).

## What it does not do

- It does not grant permissions one by one. You grant a role.
- It does not allow anything not granted.
- It does not authenticate you. That is [authentication](/concepts/authentication).
