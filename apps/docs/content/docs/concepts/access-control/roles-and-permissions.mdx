A permission is one `resource:action` pair, such as `project:deploy`, and only the pairs in the matrix
below exist. A role bundles permissions, and a grant gives a role to a person at the scope of the whole
organization or one project.

## How it works

### The matrix

| Resource | What it is | Actions |
| --- | --- | --- |
| `org` | The organization | `view`, `edit`, `manage_billing`, `manage_tokens` |
| `project` | An infrastructure application | `view`, `create`, `edit`, `plan`, `deploy`, `destroy`, `audit` |
| `runner` | An execution agent | `view`, `create`, `edit`, `deploy`, `destroy` |
| `cloud_identity` | A connected cloud account | `view`, `manage_identities`, `test` |
| `job` | A provisioning job | `view`, `create`, `edit` |
| `connector` | A Git or pluggable provider connection | `view`, `manage_connectors` |
| `member` | A member of the organization | `view`, `manage_members` |
| `activity` | The Activity log | `view_activity`, `export_activity` |
| `billing` | The subscription | `manage_billing` |
| `alert` | Alert channels, rules and deliveries | `view_alerts`, `manage_alerts` |
| `fleet` | Managed warm-pool settings, which create real VMs | `view`, `create`, `edit`, `destroy` |
| `support_case` | A support case | `view`, `create`, `reply`, `manage_support` |
| `cluster` | A provisioned cluster you can get a kubeconfig for | `access_readonly`, `access_admin` |

`plan`, `deploy` and `destroy` queue those jobs. `audit` queues an Elench audit. `test` checks a cloud
connection again. `manage_tokens` manages service-account tokens. Who may see a cluster is still
`project:view`; the `cluster` actions are the two [cluster access](/concepts/cluster-access) tiers.

### The built-in roles

| Role | Holds |
| --- | --- |
| `owner` | Every permission. The creator of an organization, and every Community user in their personal organization, is an owner. |
| `admin` | Everything except billing. |
| `operator` | `view`, `create`, `edit`, `plan`, `deploy`, `destroy` and `audit` on projects, runners, jobs and the organization's settings, `view` on connectors, read access to alerts, the Activity log with export, read-only cluster access, and their own support cases. Not cloud identities, members, billing, the fleet or tokens. |
| `viewer` | `view` on everything, alerts and the Activity log (no export), and their own support cases. |

| Role | Infrastructure | Cloud identities | Connectors | Members | Alerts | Fleet | Activity | Cluster access | Billing |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| owner | Full | Manage | Manage | Manage | Manage | Manage | View, export | Admin | Manage |
| admin | Full | Manage | Manage | Manage | Manage | Manage | View, export | Admin | No |
| operator | Full | No | View | No | View | No | View, export | Read-only | No |
| viewer | View | View | View | View | View | View | View | No | No |

Every role can open, follow and reply to its own support cases; seeing and triaging all of them
(`manage_support`) is for owners and admins. Activity export also needs Enterprise. Custom roles, which
are copies of these with changes, are an [Enterprise](/guides/access/custom-roles) feature.

### Grants

You never attach a permission to a person. A grant says: this principal holds this role at this scope.

- **Principal**: a user, or in Enterprise a team.
- **Role**: a built-in or custom role.
- **Scope**: the whole organization, or one project.

```text
alice → operator → project "production"   # operator on that project only
bob   → viewer   → organization           # read-only across the organization
you   → owner    → organization           # the Community default
```

### Inheritance

Projects, runners, cloud identities, connectors and clusters belong to the organization. A grant flows
down: `operator` on the organization covers every project in it. A grant on one project covers only
that project.

```text
dana → operator → project "staging-api"
  ⇒ dana can plan, deploy and destroy "staging-api"
  ⇒ dana cannot touch "production-api"
```

Grant at the highest scope that makes sense and let inheritance do the rest. Exceptions, including
explicit denies, are in [Grants and scopes](/guides/access/grants-and-scopes).

## What it does not do

- It does not let a permission outside the matrix exist or be granted.
- It does not give operators cloud identities, members, billing or the fleet.
- It does not give anyone but owners and admins an admin kubeconfig.
