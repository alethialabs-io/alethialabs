OpenFGA is an optional Enterprise engine for the access control decision point: a dedicated
relationship-based authorization server. Postgres stays the source of truth, every grant change is also
written to OpenFGA, and both engines return the same decision for every request.

<Mermaid chart={`

  Admin["Roles, grants, teams (console)"] --> PG[("Postgres: source of truth")]
  PG -->|dual write| FGA["OpenFGA tuples"]
  Req["Authorization check"] --> PDP{"Decision point"}
  PDP -->|default| PGE["Postgres engine"]

`} />

## How it works

You manage roles, grants and exceptions exactly as without OpenFGA. They are stored in Postgres, and
each change is also written to OpenFGA as relationship tuples, which the OpenFGA engine reads.

- **The model is generated** from the same resource and action registry as everything else, so it
  covers every permission, the deny exceptions and the hierarchy.
- **Custom roles need no model change.** A role expands to tuples when it is granted.
- **The engines agree.** For any actor, action and resource, both return the same decision, with the
  same allow and deny precedence and inheritance as in [Grants and scopes](/guides/access/grants-and-scopes).

To turn it on, an operator runs the OpenFGA server, creates a store, and sets `OPENFGA_API_URL` and
`OPENFGA_STORE_ID`. On boot, Alethia writes the generated model and fills OpenFGA with tuples from the
existing grants. See [Enterprise setup](/self-host/enterprise-setup).

## What it does not do

- It is not required, even with a license. Without `OPENFGA_*`, the Postgres engine decides.
- It does not replace Postgres as the place where you manage access.
- It does not change any decision: it answers the same questions the same way.

Use it for very large tenancies or when you want one authorization service shared beyond Alethia.
Because the switch is a configuration change and a backfill, you can start on Postgres and move later.
