The Hetzner template (`infra/templates/project/hetzner/`) builds a Kubernetes cluster on Hetzner Cloud
servers that run Talos Linux. Hetzner has no managed Kubernetes, so the template creates the servers,
private network and firewall itself, and Talos turns them into a cluster.

  Net["Private network and firewall"] --> CP["1 control-plane server"]
  Net --> W["Default workers"]
  Net --> P["Extra worker pools, one /24 subnet each"]
  Talos["Talos machine secrets and configs"] --> CP
  Talos --> W
  Talos --> P
  CP --> K["Cilium, Hetzner cloud controller, volume driver"]

## How it works

### What it builds

The template has no modules: each file builds one part.

| File | Resources |
| --- | --- |
| `servers.tf` | The control-plane server, default workers, and the servers of each extra pool |
| `talos.tf` | Talos machine secrets, a machine configuration per role and pool, the bootstrap and the admin kubeconfig |
| `image.tf` | A Talos disk snapshot per CPU architecture the cluster uses |
| `network.tf` | The private network (or yours), the node subnet, public IPv4 addresses and the firewall |
| `cilium.tf`, `csi.tf` | Cilium, the Hetzner cloud controller manager and volume driver, rendered for the runner to apply |
| `dns.tf` | A Hetzner DNS zone, when Cloud DNS is on |
| `buckets.tf` | Hetzner Object Storage buckets |

| Servers | Count | Type |
| --- | --- | --- |
| Control plane | 1 | The worker server type |
| Default workers | `worker_count` (default 1) | `worker_server_type` (default `cpx22`) |
| An extra pool | The pool's `desired_size`, or `min_size` | The pool's `instance_type` |

Every server is on the private network, behind the firewall, with a public IPv4 and IPv6 address,
which Talos uses to configure it. All servers join with the same machine secrets, so a server can only
join its own cluster. `cax` types are arm64; `cx`, `cpx` and `ccx` are amd64.

The cluster's credentials come from the connected Hetzner API token, which the cluster also holds as
the Secret `kube-system/hcloud` for the cloud controller and the volume driver. Hetzner is not keyless.

### The worker count is fixed

The template installs no cluster autoscaler. An autoscaler that creates servers would need the Talos
worker configuration, which holds the cluster's join secrets, inside the cluster, and would use a
token that can create and delete every server in the Hetzner project. Alethia keeps the join secrets
out of the cluster until it can keep them safe.

To change the number of workers:

1. Set the count: the cluster's **Desired** (or **Min**) node count for default workers, at least 1;
   `desired_size` (or `min_size`) for a pool.
2. Plan. The plan adds servers at the end of the pool, or removes those with the highest index.
3. If it removes servers, drain their nodes first with `kubectl drain <node>`: the apply deletes them
   without moving pods.
4. Apply.

Plan for peak load. For short-lived extra capacity, add a pool and set its size to `0` afterwards.

### Worker pools, labels and taints

The [node pool keys](/reference/node-pools) work as on
every cloud. Servers are named `<project>-<environment>-<pool>-<index>`. A pool's servers use its
`arch` image, the default workers' firewall and network, and their own `/24` subnet.

```yaml
provider_config:
  extra_node_pools:
    - name: db
      instance_type: ccx23
      min_size: 2
      max_size: 2
      taints:
        - { key: dedicated, value: db, effect: NoSchedule }
    - name: arm
      instance_type: cax21
      arch: arm64
      min_size: 3
      max_size: 3
```

Labels are set in the Talos machine configuration, so a changed label reaches running nodes on the
next apply. `node_labels` do not reach the control plane. Taints are set when a node registers, and
Kubernetes does not let a node change its own taints afterwards.

<Callout type="warn">
  A taint change reaches only servers that join after it. To retaint a whole pool, set its size to `0`
  and apply, then set it back and apply again.
</Callout>

### How a pool gets its subnet

The `/24` subnets of the cluster network are numbered from `0`, the subnet of the control plane and
default workers. A free `/24` is numbered `1` or higher and outside the pod and service ranges; the
default `10.0.0.0/16` has 95. The plan gives each pool, in order:

1. the number in `node_pool_subnet_index` for that pool, if set;
2. the number recorded for the pool when it was created;
3. the `/24` its servers already use;
4. for a new pool, the free `/24` its name hashes to, or the lowest free one.

So pools never share a `/24`, and a pool keeps its subnet when others are added, removed or
reordered. The record is a label on the cluster's firewall, `subnet.alethia.io/<pool>=<number>`,
outside the OpenTofu state.

<Callout type="warn">
  Do not edit the `subnet.alethia.io/` labels, and set `node_pool_subnet_index` only for a pool you are
  adding. Moving a pool's subnet replaces its servers. Changing the network range, `pod_cidr` or
  `service_cidr` can move pools too: change those before you add pools.
</Callout>

A cluster created before the record existed keeps each pool's current `/24` on its first plan; apply
once before adding pools. With your own network (`provision_network: false`), the plan cannot see its
existing subnets; set `node_pool_subnet_index` to a `/24` the network does not use.

### What Hetzner refuses

Beyond the rules every cloud applies, the plan refuses:

- `capacity_type: spot`. Hetzner has no interruptible servers.
- An `instance_type` that is not a Hetzner type (`cx`, `cpx`, `ccx` or `cax` and a size).
- An `arch` that does not match the type: `cax` needs `arm64`.
- A pool that does not fit: no free `/24` left, or a `node_pool_subnet_index` that is `0`, outside the
  network, in the pod or service range, already taken, or names no pool.

## What it does not do

- It does not autoscale workers.
- It does not offer Spot.
- It does not update the taints of registered nodes.
- It does not change resources when you set none of the pool keys; the first plan after an upgrade
  shows only the new output `nodepool_contract_render`.
