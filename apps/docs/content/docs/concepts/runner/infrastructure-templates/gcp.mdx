The GCP template (`infra/templates/project/gcp/`) builds a GKE cluster and the Google Cloud services
your design declares, in your project. Pods reach Google Cloud through GKE Workload Identity, with no
key files.

<Mermaid chart={`
flowchart TD
  Net["VPC network, subnets, Cloud NAT"] --> GKE["GKE: Standard with node pools, or Autopilot"]
  GKE --> WI["Workload Identity service accounts"]
  Net --> Data["Cloud SQL, Memorystore, Firestore, Pub/Sub, Cloud Storage, Artifact Registry"]
  Edge["Cloud DNS, Cloud Armor"] --> GKE
`} />

## How it works

### What it builds

| File | Resources |
| --- | --- |
| `gke.tf` | GKE cluster with Workload Identity and its default node pool, or an Autopilot cluster |
| `nodepools.tf` | The node labels, taints and extra node pools |
| `networking.tf` | VPC network, subnets, Cloud NAT and Cloud Router, firewall rules, private services access |
| `cloud-sql.tf` | Cloud SQL for PostgreSQL or MySQL, with backups and optional regional high availability |
| `memorystore.tf` | Memorystore for Redis |
| `memorystore-valkey.tf` | Memorystore for Valkey |
| `firestore.tf` | Firestore database and indexes |
| `pubsub.tf` | Pub/Sub topics and subscriptions |
| `cloud-storage.tf` | Cloud Storage buckets, and the Cloud KMS key for buckets that use your own key |
| `artifact-registry.tf` | Artifact Registry repositories |
| `cloud-dns.tf` | Cloud DNS managed zone |
| `secret-manager.tf` | Secret Manager secrets |
| `cloud-armor.tf` | Cloud Armor security policy |

These files call modules under `modules/` for GKE, Cloud SQL, both Memorystore products, Firestore,
Artifact Registry, Cloud Storage, Cloud Armor, Cloud DNS, Pub/Sub, Secret Manager and the VPC network.

GKE Autopilot (`enable_autopilot`) leaves node management to Google.

### Node pools

The template always makes one default pool, sized by `gke_node_min_size`, `gke_node_max_size` and
`gke_node_desired_size`. The [node pool keys](/reference/node-pools)
build these on GKE:

- `node_labels` reach every pool. The template's own labels (`environment`, `service`, `managed-by`
  and classification tags) cannot be reused as keys. `node_taints` reach the extra pools only.
- Each entry in `extra_node_pools` is a node pool named `<cluster name>-<name>`, shortened with a hash
  past GKE's 40-character limit. Pools are keyed by name, so removing one leaves the others.
- **Size.** The cluster autoscaler keeps a pool between `min_size` and `max_size` across its zones. A
  zonal cluster's pool starts with `desired_size` nodes (or `min_size`). A regional cluster's pool
  spans three zones and starts with a multiple of three: `desired_size` rounded up, kept within the
  bounds where a multiple of three fits, otherwise up to two nodes over `max_size` until the
  autoscaler removes them. After creation the autoscaler owns the count.
- **Spot.** `capacity_type: spot` uses Spot VMs, which Google can reclaim at any time.
- **arm64.** An arm64 pool needs an Arm machine family: `t2a`, `c4a`, `n4a` or `a4x`. The plan refuses
  a pool whose `arch` does not match its machine type. GKE adds its own
  `kubernetes.io/arch=arm64:NoSchedule` taint, so arm64 pods tolerate both that and Alethia's.
- **Autopilot** has no node pools to manage, so the plan refuses all three keys there.
- **Isolation.** An extra pool has the default pool's node service account, the GKE metadata server,
  shielded nodes with secure boot, the same disk settings and encryption, and the same node
  management.

```json
{
  "node_labels": { "team": "payments" },
  "node_taints": [{ "key": "dedicated", "value": "batch", "effect": "NoSchedule" }],
  "extra_node_pools": [
    { "name": "batch", "instance_type": "e2-standard-8", "capacity_type": "spot", "min_size": 0, "max_size": 6 }
  ]
}
```

<Callout type="warn">
  Changing a pool's `name` or `capacity_type` replaces the pool and the pods on it. Changing its
  `instance_type` keeps the pool and recreates its nodes. Labels, taints and size bounds update in
  place; a new taint evicts running pods only if its effect is `NoExecute`.
</Callout>

### Cloud SQL Query Insights

On a database, `cloud_sql_query_insights_enabled: true` turns on Query Insights. Two more keys, both
needing it, add detail: `cloud_sql_query_insights_record_application_tags` and
`cloud_sql_query_insights_record_client_address`. To turn it off, set it to `false`: removing the key
leaves the instance as it is. Database logs already go to Cloud Logging; change what is logged with
`cloud_sql_database_flags`.

### Bucket encryption with your own key

On a bucket, `cmek_enabled: true` encrypts it with a Cloud KMS key, `gcs-buckets`, in the project's
key ring. The Cloud Storage service agent gets `roles/cloudkms.cryptoKeyEncrypterDecrypter` on that key
only. The bucket must be in the project's region, and the Cloud KMS API must be on. Objects already in
a bucket keep their encryption; only new objects use the key.

<Callout type="warn">
  Disabling or destroying the key makes the objects written under it unreadable. If you turn
  `cmek_enabled` off on every bucket, the template removes the key and Cloud KMS destroys its versions
  after 30 days. Cloud KMS never deletes a key name, so you then cannot turn `cmek_enabled` on again
  in that project: creating `gcs-buckets` again fails with `409 AlreadyExists`. Keep it on for at
  least one bucket to keep the option.
</Callout>

## What it does not do

- It does not manage node pools on Autopilot.
- It does not turn Query Insights off when you remove the key.
- It does not offer cache logging: the Google provider has no logging setting for Memorystore.
