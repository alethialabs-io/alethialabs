The AWS template (`infra/templates/project/aws/`) builds an EKS cluster and the AWS services your
design declares, in your account. Pods reach AWS through IAM roles for service accounts (IRSA), never
static keys.

## How it works

### What it builds

| File | Resources |
| --- | --- |
| `networking.tf` | VPC, public and private subnets, NAT and internet gateways, route tables, security groups |
| `eks.tf` | EKS cluster, the default and extra managed node groups, the OIDC provider for IRSA |
| `karpenter.tf` | Karpenter's interruption queue (SQS) and EventBridge rules, and the EC2 Spot service-linked role when `ec2_spot_service_role` is set |
| `irsa.tf` | IAM roles for service accounts |
| `rds.tf` | Aurora PostgreSQL or MySQL cluster and instances |
| `elasticache.tf` | ElastiCache Redis replication group |
| `valkey.tf` | ElastiCache Serverless Valkey cache |
| `dynamodb.tf` | DynamoDB tables with KMS encryption |
| `sqs.tf` | SQS queues (standard and FIFO) and SNS topics |
| `s3.tf` | S3 buckets with encryption, versioning and lifecycle rules |
| `ecr.tf` | ECR repositories with lifecycle policies and scan on push |
| `route53.tf` | Route 53 hosted zone |
| `acm-certificate.tf` | ACM certificates with DNS validation |
| `waf.tf` | WAFv2 web ACL with managed rule groups |
| `custom_secrets.tf` | Secrets Manager secrets with generated passwords |

These files call modules under `modules/` for EKS, RDS, Redis, Valkey, DynamoDB, ECR, S3, SQS and
SNS, WAFv2, ACM, Route 53 and password generation.

Aurora Serverless v2 scales from 0.5 to 128 Aurora capacity units.

### Karpenter NodePool

With `enable_karpenter`, the runner applies a Karpenter `NodePool` named `default` after the cluster
is up. It decides which EC2 instances Karpenter may launch. Set these keys in the cluster's
`provider_config`; with none set, the defaults apply.

| Key | Default | Allowed values |
| --- | --- | --- |
| `karpenter_capacity_types` | `["on-demand"]` | `spot`, `on-demand`, or both. With both, Karpenter prefers Spot. |
| `karpenter_architectures` | `["amd64"]` | `amd64` only. Use `karpenter_arm64_nodepool` for arm64. |
| `karpenter_instance_categories` | `["t", "m"]` | EC2 categories such as `c`, `m`, `r`. An empty list removes the requirement. |
| `karpenter_instance_families` | `[]` | Families such as `c7i`, each in one of the categories. |
| `karpenter_cpu_limit` | `100` | Total vCPU the pool may launch, 1 to 1000. |
| `karpenter_node_labels` | `{}` | Labels on every Karpenter node. |
| `karpenter_node_taints` | `[]` | Taints, each `{ key, value, effect }`. |
| `karpenter_arm64_nodepool` | `null` | Adds an `arm64` pool. Fields: `instance_families` (Graviton, not `a1`) and `cpu_limit` (default `100`). |

Keys in the `kubernetes.io`, `k8s.io`, `karpenter.sh` and `karpenter.k8s.aws` domains are refused for
labels and taints, except `node-restriction.kubernetes.io/`. The plan refuses a value outside these
rules, and the runner checks again before it applies the pool. Change the settings, not the
`NodePool` in the cluster: the next deploy replaces in-cluster edits.

<Callout type="warn">
  Karpenter launches instances outside OpenTofu, so plan-time cost guards do not see them. The CPU
  limit is the only bound on that fleet's size.
</Callout>

```json
{
  "enable_karpenter": true,
  "karpenter_capacity_types": ["spot", "on-demand"],
  "karpenter_instance_categories": ["c", "m"],
  "karpenter_instance_families": ["c7i", "m7i"],
  "karpenter_cpu_limit": 400,
  "karpenter_node_labels": { "workload": "batch" },
  "karpenter_node_taints": [{ "key": "workload", "value": "batch", "effect": "NoSchedule" }]
}
```

**Spot.** AWS can reclaim a Spot instance with two minutes' notice. Karpenter gets the notice through
the interruption queue and drains the node first. Run only work that can restart, or list both
capacity types. Spot needs the `AWSServiceRoleForEC2Spot` role: create it once with
`aws iam create-service-linked-role --aws-service-name spot.amazonaws.com`, or set
`ec2_spot_service_role` to `true`.

**The arm64 pool.** It uses the default pool's capacity types, categories, labels and taints, with its
own families and CPU limit. Its nodes carry the taint `alethia.io/arch=arm64:NoSchedule`, which you
cannot remove, so only pods that ask for arm64 land there. To run a workload on it, build an arm64 or
multi-arch image, tolerate `alethia.io/arch=arm64:NoSchedule`, and select `kubernetes.io/arch: arm64`.
A DaemonSet of your own, such as a log shipper, needs the same toleration. Removing the setting
deletes the pool; the runner waits up to 15 minutes for Karpenter to drain it.

### Node groups

The [node pool keys](/reference/node-pools) build these on
EKS:

- `node_labels` reach the default node group and every extra one. `node_taints` reach the extra node
  groups only.
- Each entry in `extra_node_pools` is a managed node group named `<cluster>-<pool name>`.
  `capacity_type: spot` makes it a Spot node group.
- An extra node group uses the default group's operating system (`eks_ami_type`, Bottlerocket by
  default), with the arm64 or NVIDIA image where the instance type needs one. The plan refuses a pool
  with no matching image, such as a GPU pool on FIPS Bottlerocket.
- An `arm64` pool needs a Graviton type, such as `m7g.large`; an `amd64` pool an x86 type.
- **Size.** A node group starts with `desired_size` nodes and stays there: nothing scales it, and a
  later change to `desired_size` does not resize it. For capacity that follows demand, use Karpenter.
- **Isolation.** Every node group has the default group's controls: IMDSv2 with a hop limit of 1, the
  same private subnets and security group, an encrypted gp3 root volume, and the same IAM policies.

## What it does not do

- It does not let Karpenter's default pool launch arm64 instances.
- It does not autoscale extra managed node groups.
- It does not count Karpenter's instances in plan-time cost guards.
