# AWS Resources

The AWS template set (`infra/templates/project/aws/`) is the most extensive, with ~15 top-level `.tf` files and 10 reusable modules.

## Top-Level Resources

| File | Resources Created |
|------|------------------|
| `networking.tf` | VPC, public/private subnets, NAT gateway, internet gateway, route tables, security groups |
| `eks.tf` | EKS cluster, managed node group, OIDC provider for IRSA |
| `karpenter.tf` | Karpenter provisioner, node pools, instance types |
| `rds.tf` | Aurora PostgreSQL/MySQL cluster, instances, subnet group |
| `elasticache.tf` | ElastiCache Redis replication group, subnet group |
| `valkey.tf` | Valkey (open-source Redis fork) node |
| `dynamodb.tf` | DynamoDB tables with KMS encryption |
| `ecr.tf` | ECR repositories with lifecycle policies, scan-on-push |
| `s3.tf` | S3 buckets with encryption, versioning, lifecycle rules |
| `sqs.tf` | SQS queues (standard + FIFO) + SNS topics with subscriptions |
| `waf.tf` | WAFv2 web ACL with managed rule groups |
| `acm-certificate.tf` | ACM SSL/TLS certificates with DNS validation |
| `irsa.tf` | IAM Roles for Service Accounts (pod-level AWS access) |
| `custom_secrets.tf` | Secrets Manager secrets with auto-generated passwords |

## Key Features

**IRSA (IAM Roles for Service Accounts)** — Kubernetes pods can assume IAM roles via their service account, eliminating the need for static credentials in containers. The EKS module creates an OIDC provider and the IRSA module creates per-service-account IAM roles.

**Karpenter** — Just-in-time node provisioning. Instead of pre-scaling node groups, Karpenter watches for pending pods and launches appropriately-sized EC2 instances within seconds. Supports spot instances and multiple instance families.

**Aurora Serverless v2** — Auto-scaling database with ACU-based capacity (0.5–128 ACUs). Scales to zero-ish (0.5 ACU minimum) during idle periods.

## Karpenter node pool

When Karpenter is on (`enable_karpenter`), the runner applies one Karpenter `NodePool` after the cluster is up. The pool decides which EC2 instances Karpenter can launch. You set its shape on the cluster component: select the cluster on the canvas and open the **Advanced** section of the inspector. Each setting below is a key in the cluster's `provider_config`.

If you set nothing, every default below applies, and the runner renders the same pool as before these settings existed.

| Setting | Default | Allowed values |
|---------|---------|----------------|
| `karpenter_capacity_types` | `["on-demand"]` | `spot`, `on-demand`, or both. With both, Karpenter prefers Spot and falls back to on-demand. |
| `karpenter_architectures` | `["amd64"]` | `amd64` only. The plan refuses `arm64`. See [Why arm64 is not offered](/concepts/runner/infrastructure-templates/aws#why-arm64-is-not-offered). |
| `karpenter_instance_categories` | `["t", "m"]` | EC2 instance categories, such as `c`, `m` or `r`. An empty list removes the category requirement. |
| `karpenter_instance_families` | `[]` (no requirement) | EC2 instance families, such as `c7i` or `m7i`. Each family must belong to one of the categories, unless the category list is empty. |
| `karpenter_cpu_limit` | `100` | The total vCPU the pool can launch, a whole number from 1 to 1000. It is the only bound on the size of Karpenter's fleet. Karpenter launches EC2 instances outside OpenTofu, so the plan-time cost guards do not see them. |
| `karpenter_node_labels` | `{}` | Labels on every Karpenter node. Keys in the `kubernetes.io`, `k8s.io`, `karpenter.sh` and `karpenter.k8s.aws` domains are refused, except `node-restriction.kubernetes.io/`. |
| `karpenter_node_taints` | `[]` | Taints on every Karpenter node, each `{ key, value, effect }`. `value` is optional. `effect` is `NoSchedule`, `PreferNoSchedule` or `NoExecute`. Keys in the reserved domains above are refused. |

The plan refuses a value outside these rules and names what is allowed. The runner checks the same rules again before it applies the pool.

### Example: Spot nodes for batch work

This `provider_config` lets Karpenter launch `c7i` and `m7i` instances, on Spot when it can, up to 400 vCPU. It labels and taints the nodes so that only pods that tolerate the `workload=batch` taint run there:

```json
{
  "enable_karpenter": true,
  "karpenter_capacity_types": ["spot", "on-demand"],
  "karpenter_instance_categories": ["c", "m"],
  "karpenter_instance_families": ["c7i", "m7i"],
  "karpenter_cpu_limit": 400,
  "karpenter_node_labels": { "workload": "batch" },
  "karpenter_node_taints": [
    { "key": "workload", "value": "batch", "effect": "NoSchedule" }
  ]
}
```

A batch pod then selects and tolerates those nodes:

```yaml
spec:
  nodeSelector:
    workload: batch
  tolerations:
    - key: workload
      operator: Equal
      value: batch
      effect: NoSchedule
```

<Callout type="warn">
AWS can reclaim a Spot instance with two minutes' notice. Karpenter receives that notice through the interruption queue the template creates (an SQS queue fed by EventBridge rules), then cordons and drains the node before AWS reclaims it. Run only work that can stop and restart on Spot, or list both capacity types so that Karpenter can fall back to on-demand.
</Callout>

<Callout type="info">
Spot needs the `AWSServiceRoleForEC2Spot` service-linked role in the AWS account. An account that has never used Spot does not have it. Create it once with `aws iam create-service-linked-role --aws-service-name spot.amazonaws.com`, or set `ec2_spot_service_role` to `true` on the cluster to let the template create it.
</Callout>

### Why arm64 is not offered

The default node pool launches amd64 (x86_64) instances only. The managed node group is x86_64, and the images that Alethia builds are amd64-only. An amd64-only image crashes on an arm64 node with `exec format error`. A taint on the default pool does not solve this, because it is the only Karpenter pool. Every pod without the toleration could then run only on the fixed-size managed node group. Graviton (arm64) needs a separate, tainted node pool, which is tracked in [#5534](https://github.com/alethialabs-io/alethialabs/issues/5534).

Edit these settings on the cluster, not on the `NodePool` in the cluster. The next deploy renders the pool again from the settings and replaces a change made in the cluster.
