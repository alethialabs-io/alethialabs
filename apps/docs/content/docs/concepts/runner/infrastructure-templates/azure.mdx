# Azure Resources

The Azure template set (`infra/templates/project/azure/`) provides Azure-native equivalents for all supported resource types.

## Resources

| File | Resources Created |
|------|------------------|
| `aks.tf` | AKS cluster, default node pool, Azure AD integration |
| `nodepools.tf` | Maps `node_labels`, `node_taints` and `extra_node_pools` onto the AKS node pools |
| `vnet.tf` | Virtual Network, subnets, NSG, NAT Gateway |
| `azure-db.tf` | Azure Database for PostgreSQL/MySQL (Flexible Server) |
| `azure-cache-redis.tf` | Azure Cache for Redis |
| `cosmos-db.tf` | Cosmos DB account, database, container |
| `acr.tf` | Azure Container Registry |
| `storage-account.tf` | Storage account, blob containers |
| `service-bus.tf` | Service Bus namespace, queues, topics |
| `azure-dns.tf` | Azure DNS zone, record sets |
| `key-vault.tf` | Key Vault, access policies |
| `azure-waf.tf` | Web application firewall policy (OWASP 3.2 plus your custom rules) |
| `application-gateway.tf` | Application Gateway v2, its public IP, and the AGIC workload identity |

## Key Features

**Azure AD Integration** — AKS integrates with Azure AD for RBAC. Cluster admins are Azure AD users or groups, not separate IAM identities.

**Flexible Server** — Azure's latest managed database tier with zone-redundant HA, automatic backups, and vCore-based scaling (1–64 vCores).

**Cosmos DB** — Globally distributed multi-model database supporting SQL (document), Table (key-value), MongoDB, Cassandra, and Gremlin APIs. Multi-region writes for global distribution.

**Ingress through an Application Gateway** — Azure has no per-Ingress load balancer. Instead, the template provisions one Application Gateway v2, and the Application Gateway Ingress Controller (AGIC) turns every `Ingress` object in the cluster into listeners and routing rules on that gateway. Set `ingressClassName: azure-application-gateway` on your `Ingress` to publish through it. AGIC authenticates with a workload identity, so it holds no static credential.

**The firewall binds to the gateway** — On Azure a firewall policy attaches to an Application Gateway, not to an `Ingress` annotation. Turning the firewall on therefore also provisions a gateway (on the WAF\_v2 tier, which the association requires) and binds the policy to it, so every request the gateway serves is inspected.

**The gateway is opt-in** — An Application Gateway bills per hour for as long as it exists, whether or not you have published anything through it. It is created when you turn the firewall on, or when you set `azure_application_gateway_enabled` to `true`. It needs a dedicated subnet, so the template must be creating your virtual network. Without a gateway, expose services with the `ingress-nginx` add-on instead.

## Operational settings

The settings below are off by default. A project that sets none of them gets the same infrastructure as before, and pays for nothing new. Each one is a template variable that you set on the component it belongs to. In the console, open the component on the canvas and set the value on its template settings card. The examples show the component's `provider_config` that the card writes.

<Callout type="warn">
A Log Analytics workspace bills per GB of data it ingests. Control-plane log retention, database log exports and cache logging all send data to a workspace, so each one adds cost when you turn it on.
</Callout>

### Control-plane log retention

Set `aks_log_retention_days` on the **cluster** to keep AKS control-plane logs. Use a whole number of days from 30 to 730.

```json
{ "aks_log_retention_days": 90 }
```

The template then creates a Log Analytics workspace with that retention. It turns on the AKS monitoring add-on (Container Insights) and sends the `kube-apiserver` and `kube-audit-admin` logs to the workspace. Container logs use the same retention. The database and cache settings below also use this workspace when it exists.

### Database log exports

Set `azure_db_log_exports` on the **database** to send Flexible Server logs to Log Analytics. The categories depend on the engine:

| Engine | Categories |
|--------|------------|
| PostgreSQL | `PostgreSQLLogs`, `PostgreSQLFlexSessions`, `PostgreSQLFlexQueryStoreRuntime`, `PostgreSQLFlexQueryStoreWaitStats`, `PostgreSQLFlexTableStats`, `PostgreSQLFlexDatabaseXacts` |
| MySQL | `MySqlSlowLogs`, `MySqlAuditLogs` |

```json
{ "azure_db_log_exports": ["PostgreSQLLogs", "PostgreSQLFlexSessions"] }
```

Some categories stay empty until you turn on the matching server parameter with `azure_db_database_flags`:

- `MySqlAuditLogs` needs `audit_log_enabled` set to `ON`.
- `PostgreSQLFlexQueryStoreRuntime` needs Query Store on: set `pg_qs.query_capture_mode` to `TOP` or `ALL`.
- `PostgreSQLFlexQueryStoreWaitStats` needs Query Store on as above, and wait sampling on: also set `pgms_wait_sampling.query_capture_mode` to `all` (it defaults to `none`).

The logs go to the workspace from control-plane log retention. If the project has no cluster, or does not set `aks_log_retention_days`, also set `azure_db_log_workspace_id` to the resource ID of an existing workspace. The plan fails if the logs have nowhere to go, or if a category belongs to the other engine.

### Database server parameters

Set `azure_db_database_flags` on the **database** to change Flexible Server parameters. Each entry becomes one server parameter on the engine you provisioned. Values are strings.

```json
{ "azure_db_database_flags": { "max_connections": "200", "log_min_duration_statement": "500" } }
```

The template refuses `require_secure_transport`, `ssl_min_protocol_version` and `tls_version`. Each of these can turn TLS off or allow a version below TLS 1.2, and the server defaults already require TLS 1.2.

<Callout type="warn">
The template refuses only the TLS parameters. Other parameters can also weaken the server, and the template accepts them. For example, `password_encryption` set to `md5` stores weaker password hashes. Changes to `pgaudit.log`, `log_connections` or `audit_log_enabled` reduce what the server records. `azure.extensions` allows more PostgreSQL extensions. Review each value as you would a change to the server's security settings.
</Callout>

Some parameters are static. When you change a static parameter, Azure restarts the server to apply it, and the database is unavailable during the restart.

### Storage encryption with your own key

Set `cmek_enabled` on a **bucket** to encrypt the storage account with a customer-managed key.

```json
{ "cmek_enabled": true }
```

Azure encrypts a whole storage account with one key, and a project has one storage account. So when any bucket sets `cmek_enabled`, every container in the account uses the key. The template creates the key in the project's own Key Vault. It also creates a managed identity that the storage account uses to reach the key. That identity has only the Key Vault Crypto Service Encryption User role, on that one key. The role's data actions are exactly read, wrap and unwrap on the key. The built-in role also has Event Grid control-plane actions, which give no access to key material.

Azure accepts the key only from a vault with purge protection, so `key_vault_purge_protection_enabled` must stay `true` (the default).

### Cache logging

Set `azure_cache_log_categories` on the **cache** to send Azure Managed Redis connection logs to Log Analytics. Managed Redis has one log category, `ConnectionEvents`.

```json
{ "azure_cache_log_categories": ["ConnectionEvents"] }
```

The destination works the same way as database log exports: the template's workspace when there is one, otherwise the workspace in `azure_cache_log_workspace_id`. The plan fails if neither exists.

## Node pools

AKS runs your workloads on node pools. The template always makes the default pool. It makes one
more pool, `pool1`, `pool2` and so on, for each extra VM size in `aks_instance_types`, and a `spot`
pool when `aks_spot_enabled` is `true`. Those pools share one size.

Set three keys on the **cluster** to label your nodes, taint them, and add named pools that each
have their own size. They are the same keys on every cloud. The
[cluster guide](/guides/design-project/cluster#node-labels-taints-and-extra-pools) describes every
field and every rule.

```json
{
  "node_labels": { "team": "payments" },
  "node_taints": [{ "key": "dedicated", "value": "batch", "effect": "NoSchedule" }],
  "extra_node_pools": [
    {
      "name": "gpu",
      "instance_type": "Standard_NC4as_T4_v3",
      "capacity_type": "spot",
      "min_size": 0,
      "max_size": 3,
      "taints": [{ "key": "gpu", "value": "true", "effect": "NoSchedule" }]
    }
  ]
}
```

On AKS, the template builds them like this:

- **`node_labels`** go on every pool: the default pool, `pool1`…`poolN`, the `spot` pool and every
  named pool.
- **`node_taints`** go on the named pools only. The default pool runs Alethia's add-ons, and the
  positional and `spot` pools keep the taints they had.
- **Each entry in `extra_node_pools`** is one user node pool (`mode = User`), named for the entry.
  It has its own VM size and its own `min_size`, `max_size` and `desired_size`. The pool is keyed
  by its name, so removing an entry from the middle of the list removes that pool only.
- **Size.** The cluster autoscaler scales each pool between `min_size` and `max_size`.
  `desired_size` is the node count the pool starts with. After that the autoscaler owns the count,
  so a later change to `desired_size` does nothing.
- **Taints** use the AKS form `key=value:Effect`, or `key:Effect` when the taint has no value.
- **Spot.** A pool with `capacity_type: spot` is a Spot pool. It uses the cluster's Spot settings,
  the same ones as the `spot` pool: `aks_spot_eviction_policy` (`Delete` by default) and
  `aks_spot_max_price` (`-1` by default, which means up to the on-demand price). You can set them
  without `aks_spot_enabled`. AKS labels and taints the nodes of a Spot pool with
  `kubernetes.azure.com/scalesetpriority=spot`, and the template declares both on the pool.
- **arm64.** An arm64 pool needs an Arm64 VM size. In Azure's
  [VM size names](https://learn.microsoft.com/azure/virtual-machines/vm-naming-conventions), the
  lowercase feature letter `p` after the vCPU count marks an Arm-based processor, as in
  `Standard_D4ps_v5`, `Standard_D2pds_v5`, `Standard_E4ps_v6` and `Standard_B2pts_v2`. A size
  without `p`, such as `Standard_D4s_v5` or `Standard_B2s_v2`, is amd64. The plan refuses an arm64
  pool on an amd64 size, and an amd64 pool on an Arm64 size. Alethia taints every arm64 pool with
  `alethia.io/arch=arm64:NoSchedule`.
- **Isolation.** A named pool uses the default pool's subnet, OS disk type and size, and maximum
  pods per node. A pool cannot cost less because it is less isolated.

When you set none of the three keys, the plan is the same as before: no pool changes.

<Callout type="warn">
Some changes replace a pool, and with it the pool's nodes and the pods on them. Changing a pool's
`name` or `capacity_type` replaces it. Changing its `instance_type` keeps the pool but replaces
every node in it: the template moves the pool's workloads to a temporary pool, rebuilds the pool on
the new size, moves them back and deletes the temporary pool. Changing `node_labels`,
`node_taints` or a pool's `labels`, `taints`, `min_size` or `max_size` updates the pool in place,
with the azurerm provider version the template pins (4.x). A taint that you add does not evict the
pods already on the node, unless its effect is `NoExecute`.
</Callout>
