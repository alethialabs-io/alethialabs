The Azure template (`infra/templates/project/azure/`) builds an AKS cluster and the Azure services
your design declares, in your subscription. Controllers in the cluster use workload identities, with
no client secrets.

## How it works

### What it builds

| File | Resources |
| --- | --- |
| `aks.tf` | AKS cluster, default node pool, Microsoft Entra ID integration |
| `nodepools.tf` | The node labels, taints and extra node pools |
| `vnet.tf` | Virtual network, subnets, network security group, NAT gateway |
| `azure-db.tf` | Azure Database for PostgreSQL or MySQL (Flexible Server) |
| `azure-cache-redis.tf` | Azure Managed Redis |
| `cosmos-db.tf` | Cosmos DB account, database and container |
| `service-bus.tf` | Service Bus namespace, queues and topics |
| `storage-account.tf` | Storage account and blob containers |
| `acr.tf` | Azure Container Registry |
| `azure-dns.tf` | Azure DNS zone |
| `key-vault.tf` | Key Vault with Azure RBAC, the provisioner's Key Vault Secrets Officer role, and secrets |
| `azure-waf.tf` | WAF policy: OWASP 3.2 and your custom rules |
| `application-gateway.tf` | Application Gateway v2, its public IP, and the ingress controller's workload identity |

These files call modules under `modules/` for AKS, the database, Redis, Cosmos DB, ACR, storage,
Service Bus, DNS, the WAF, Key Vault and the virtual network.

### Ingress through an Application Gateway

Azure has no load balancer per Ingress. Instead, the template can build one Application Gateway v2,
and the Application Gateway Ingress Controller turns each `Ingress` with
`ingressClassName: azure-application-gateway` into rules on it. A WAF policy attaches to a gateway,
so turning the WAF on also builds a gateway (WAF_v2 tier) and binds the policy to it.

The gateway bills per hour while it exists. It is built only when you turn the WAF on or set
`azure_application_gateway_enabled: true`, and it needs the template to create the virtual network.
Without it, use the Traefik add-on.

### Logs

A Log Analytics workspace bills per GB ingested, so each logging setting adds cost.

- **Control plane.** On the cluster, `aks_log_retention_days` (30 to 730) creates a workspace with that
  retention, turns on Container Insights, and sends the `kube-apiserver` and `kube-audit-admin` logs
  to it.
- **Database.** On the database, `azure_db_log_exports` lists the categories to send:
  `PostgreSQLLogs`, `PostgreSQLFlexSessions`, `PostgreSQLFlexQueryStoreRuntime`,
  `PostgreSQLFlexQueryStoreWaitStats`, `PostgreSQLFlexTableStats` and `PostgreSQLFlexDatabaseXacts`
  for PostgreSQL; `MySqlSlowLogs` and `MySqlAuditLogs` for MySQL. Some stay empty until a server
  parameter is on: `audit_log_enabled` for MySQL audit logs, Query Store
  (`pg_qs.query_capture_mode`) and wait sampling for the Query Store categories.
- **Cache.** On the cache, `azure_cache_log_categories: ["ConnectionEvents"]`.

Database and cache logs go to the cluster's workspace, or to the workspace in
`azure_db_log_workspace_id` or `azure_cache_log_workspace_id`. The plan fails if they have nowhere to
go, or if a category belongs to the other engine.

### Database server parameters

On the database, `azure_db_database_flags` sets Flexible Server parameters as strings, for example
`{ "max_connections": "200" }`. The template refuses `require_secure_transport`,
`ssl_min_protocol_version` and `tls_version`, which could weaken TLS below 1.2.

<Callout type="warn">
  Other parameters can also weaken the server and are accepted, such as `password_encryption: md5`
  or changes to `pgaudit.log`. Review them as security changes. A static parameter restarts the
  server.
</Callout>

### Storage encryption with your own key

On a bucket, `cmek_enabled: true` encrypts the project's storage account with a key in the project's
Key Vault. Azure encrypts a whole account with one key, so every container uses it. A managed identity
reaches the key with only the Key Vault Crypto Service Encryption User role, on that key.
`key_vault_purge_protection_enabled` must stay `true`.

### Node pools

The template always makes the default pool, a pool per extra VM size in `aks_instance_types`
(`pool1`, `pool2` and so on), and a `spot` pool when `aks_spot_enabled` is `true`. The autoscaler
scales each between its bounds; `aks_node_desired_size` and `aks_spot_node_min_size` set only the
starting counts.

The [node pool keys](/reference/node-pools) build these on
AKS:

- `node_labels` reach every pool. `node_taints` reach the named extra pools only.
- Each entry in `extra_node_pools` is a user node pool with its own VM size and bounds, keyed by name.
  A name that collides with the temporary name AKS uses when rebuilding another pool is refused.
- **Spot.** `capacity_type: spot` uses the cluster's Spot settings: `aks_spot_eviction_policy`
  (`Delete`) and `aks_spot_max_price` (`-1`, up to the on-demand price).
- **arm64.** An arm64 pool needs an Arm VM size: one with `p` after the vCPU count, such as
  `Standard_D4ps_v5`. The plan refuses a mismatch.
- **Isolation.** A named pool has the default pool's subnet, disk type and size, and pod limit.

<Callout type="warn">
  Changing a pool's `name` or `capacity_type` replaces it. Changing its `instance_type` replaces every
  node without draining it first: pods managed by a controller are rescheduled, others are not. The
  same applies to the default and positional pools for `aks_instance_types`, `aks_os_disk_type` and
  `aks_disk_size_gb`. Labels, taints and bounds update in place. Raising a minimum above the current
  node count is not verified.
</Callout>

## What it does not do

- It does not build an Application Gateway unless you turn on the WAF or the gateway.
- It does not refuse every risky server parameter, only the TLS ones.
- It does not encrypt one container with a different key from the rest of the account.
