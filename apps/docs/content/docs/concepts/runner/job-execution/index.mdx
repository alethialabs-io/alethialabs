# Job Execution

All jobs share the same claiming mechanism and keyless credential handling, but differ in what they
execute. For the queue mechanics, see [Job queue](/concepts/job-queue); for what each job type does, see
[Job types](/guides/jobs/job-types).

## Claiming

A push wake stream (SSE) signals when a job is claimable; the runner then calls
`POST /api/jobs/claim` (a 30-second safety poll is the fallback if the stream drops). The server
runs `claim_next_job()` — a PostgreSQL function using `FOR UPDATE SKIP LOCKED` for atomic,
exactly-once claiming. Job status walks `QUEUED → CLAIMED → PROCESSING → SUCCESS | FAILED | CANCELLED`.

When a job is returned, the runner:
1. Sets status to `PROCESSING`.
2. Reads the environment config snapshot and cloud identity from the claim.
3. Mints cloud credentials keylessly ([details](/concepts/runner/cloud-credentials)).
4. Dispatches on `types.JobType` (the switch in `internal/agent/runner.go`) to the handler.
5. Sets status to `SUCCESS` or `FAILED`.

## Dispatch

The switch in `internal/agent/runner.go` routes each `provisionJobType` to its handler. What each type
does is in the [Job types](/guides/jobs/job-types) catalog; this table adds only how the runner
executes it.

| Job type | Handler | Execution |
|----------|---------|-----------|
| `PLAN` / `DEPLOY` / `DESTROY` | `executePlan` / `executeDeploy` / `executeDestroy` | Through the **sandbox seam**. [Plan](/concepts/runner/job-execution/plan-jobs) · [Deploy](/concepts/runner/job-execution/deploy-jobs) · [Destroy](/concepts/runner/job-execution/destroy-jobs) |
| `DEPLOY_RUNNER` / `UPDATE_RUNNER` / `DESTROY_RUNNER` | `executeDeployRunner` / … | [Runner lifecycle jobs](/concepts/runner/job-execution/runner-jobs) |
| `ANALYZE_REPO` | `executeAnalyzeRepo` | Posts the `RepoDigest`. |
| `DETECT_DRIFT` | `executeDriftDetection` | Posts the posture on `execution_metadata.drift_posture`. Bring-your-own modules need the container sandbox on a managed runner. |
| `AUDIT` | `executeAudit` | Posts `execution_metadata.verify_result`; a verdict that cannot be persisted fails the job. |
| `CHART_SCAN` | `executeChartScan` | Always runs inside the sandbox. |
| `IAC_SCAN` | `executeIacScan` | On a managed runner, refuses unless the container sandbox is enforced. |
| `STATE_SURGERY` | `executeStateSurgery` | Ships **inert**: refuses unless `ALETHIA_BREAKGLASS_STATE_SURGERY_ENABLED` opts the runner in. |
| `PROBE_CLUSTER` | `executeProbeCluster` | Writes `environment_probes`. |
| `BUILD` | `executeBuild` | Schedules kaniko Jobs in the customer's cluster; posts `execution_metadata.build_result`. |

## Error handling

When any step fails:
1. The error is logged to the STDERR stream.
2. Job status is set to `FAILED` with the error message.
3. tofu state is preserved through the [Console state proxy](/concepts/terraform-state) (partial
   apply state, with fenced locks so a reclaimed lock can't clobber a slow writer).
4. Cloud credentials are cleared (the deferred cleanup always runs).
5. The runner returns to the poll loop for the next job.

Users can retry failed jobs — since state is preserved, retries continue from the last successful
resource rather than starting over.
