The managed fleet keeps a warm pool of runners for each cloud, one runner by default, so most jobs
start without waiting for a VM to boot. A scaler inside the control plane adds VMs when jobs queue
up and destroys idle ones when the queue clears.

This page is for operators of the managed fleet. To run it, see
[Managed provisioning](/self-host/managed-provisioning).

## How it works

### The loop

The scaler runs every 60 seconds, and also at once whenever a job is queued, so a new job does not
wait for the next tick. Within one control plane process only one pass runs at a time. Across
replicas, only the replica that holds the fleet leader lease acts; a crashed leader is replaced when
its lease expires.

Each pass compares the pool's target with the VMs that exist and fixes, in order: unhealthy VMs, the
count, the spread over locations, and the runner version.

### Pools

A pool is one row per cloud, edited in the console. The scaler reads the enabled pools on every pass,
so a change applies without a redeploy.

| Setting | Default | Meaning |
| --- | --- | --- |
| Warm minimum | `1` | Runners kept ready with an empty queue. `0` lets the pool scale to zero, at the cost of a cold start. |
| Maximum | `10` | Ceiling on healthy runners. |
| Buffer | `1` | Spare runners above demand. |
| Slots per runner | `1` | Jobs one runner runs at once. |
| Surge | `1` | Extra runners allowed during a version rollout. |
| Scale-down grace | `5` ticks | Passes the pool must be over target before idle runners are destroyed. |
| Locations | `fsn1` | Hetzner locations to spread across. |
| Minimum per location | `0` | Healthy runners to keep in each location. |

### Target size

```ts
demand = max(inFlightJobs, ceil(queuedJobs / slotsPerRunner))
target = clamp(max(warmMin, demand + buffer), 0, max)
```

Both job counts are for the pool's cloud. Scale-up fills locations below their minimum first, then
the least-loaded one.

**Scale-down** waits until the pool has been over target for the grace period, then destroys idle
runners down to the target: never a busy one, and never below a location's minimum. A runner that
may hold a job is **drained** first: it stops claiming, finishes its job, and is destroyed once idle.
Drain is used for version rollouts and for a pool you pause or delete. A VM that never registers is
removed.

### VMs

The provider is chosen with `FLEET_PROVIDER`. `hcloud` creates Hetzner VMs; the default, `manual`,
only logs what it would do. A VM is an `ubuntu-24.04` server, ARM `cax21` first and x86 `cpx31` as
the fallback (`HCLOUD_SERVER_TYPES` and `HCLOUD_IMAGE` change them). Its cloud-init runs one
container: `ghcr.io/alethialabs-io/runner-<cloud>:<tag>`.

A VM holds no long-lived credential. It boots with a bootstrap token minted for that one VM, short
lived and swept when unused. The runner exchanges it for its own runner ID and token, then claims
jobs. Cloud credentials are minted per job and state goes through the state proxy.

### The ledger

Each create, drain or destroy is recorded with its reason (`scale-up-demand`, `min-per-location`,
`rollout-surge`, `rollout-drain`, `scale-down-idle`, `reap-dead`, `reap-drained` or `teardown`), the
queue depth and the pool size at that moment.

### Cold start and cost

A cold start happens only when demand passes the warm pool, or for a pool with a warm minimum of `0`.
The job stays queued while the VM boots, pulls the image, registers and claims.

You pay for the VM-hours of the warm pool and of the VMs above it while a backlog lasts. Managed
runner time is billed by provisioned hours: a session opens when a runner comes online and closes when
it is destroyed.

## What it does not do

- It does not run a separate scaling service. The scaler is part of the control plane.
- It does not destroy a busy runner.
- It does not put a shared secret on fleet VMs.
- It does not scale self-operated runners. Those are yours to size.
