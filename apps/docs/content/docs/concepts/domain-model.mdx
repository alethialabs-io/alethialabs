Alethia organizes infrastructure as organizations that own projects, projects that own several
environments, and environments that declare components. A job is one unit of work a runner does on
one environment. For the canonical name of each term, see the [Glossary](/reference/glossary).

## How it works

- An **organization** is the tenancy boundary. Every project, runner, connection and job belongs to
  exactly one, and the database refuses a query for another organization's rows. See
  [Security](/concepts/security#row-level-security).
- A **project** is one infrastructure application. It uses one
  [cloud identity](/reference/glossary#connectivity) (a connected cloud account) and has a default
  region.
- An **environment** is a target you provision on its own, such as `staging` or `production`.
- A **component** is a resource an environment declares: a cluster, a network, a database, a cache.
- A **job** is the work a runner does for one environment.

## Environments

A project owns several environments, not one. Each environment has its own OpenTofu state, its own
components and its own status, so deploying `production` never changes `staging`.

| Property | Meaning |
| --- | --- |
| Name | Unique in the project. It is part of the OpenTofu state key and of the URL. |
| Stage | `development`, `staging` or `production`. The stage sets template defaults such as instance sizes and high availability, and the order [promotions](/concepts/promotions) follow. |
| Default | One environment per project is the default. Single-value views, such as the project list's status column and the CLI, show it. |
| Lifecycle | `persistent`, or `ephemeral`. An ephemeral environment has an expiry, and Alethia queues a destroy for it when the expiry passes. |
| Region | Empty means the project's region. |

Where an environment's infrastructure comes from is a separate choice: see
[Fabrics and placement](/concepts/fabrics-and-placement).

## Components

Some components exist at most once per environment: the network, the cluster, the DNS zone,
observability, the GitOps repository and a [bring-your-own IaC](/concepts/bring-your-own-iac)
module. Others can exist many times, each with its own name: databases, caches, queues, topics, NoSQL
tables, container registries, secrets, storage buckets and [add-ons](/concepts/gitops-argocd).

Each component has its own status, so a cluster can be `ACTIVE` while a database you just added is
`CREATING`.

| Component status | Meaning |
| --- | --- |
| `PENDING` | Declared, not provisioned yet. |
| `CREATING` | Being created by `tofu apply`. |
| `ACTIVE` | Provisioned. |
| `UPDATING` | A change is being applied. |
| `FAILED` | Creation or update failed. |
| `DESTROYING` | Being removed. |
| `DESTROYED` | Removed. |

`DRAFT` means the design was never submitted. `FAILED` can be retried.

## Jobs

A job references one project, one environment and one cloud identity, and records the runner that
claimed it. It moves `QUEUED → CLAIMED → PROCESSING → SUCCESS` or `FAILED`; a queued or claimed job
can also be `CANCELLED`. A promotion adds no job type: it runs a plan, then a deploy. The full list of
job types is in [Job types](/guides/jobs/job-types), and how a job is claimed and recovered is in
[Job queue](/concepts/job-queue).

## What it does not do

- An environment does not inherit components from another environment. Each declares its own.
  [Promotions](/concepts/promotions) copy structural changes on purpose, behind gates.
- A project does not span cloud accounts. To run the same design on another cloud, see
  [Multi-cloud conversion](/concepts/multi-cloud-conversion).
