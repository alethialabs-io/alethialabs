Elench is the check Alethia runs on every OpenTofu plan between `tofu plan` and `tofu apply`. Named,
versioned controls evaluate the plan JSON, a failing hard control stops the apply unless someone with
authority waives it, and the result is sealed in an evidence receipt.

## How it works

### The verdict comes from code

The controls are deterministic code with no side effects: the same plan always gives the same
verdict, which is what lets a receipt be checked later. A language model may explain a failing control
or suggest a fix in the [assistant](/guides/assistant), but a fix is offered only if running the
controls again shows it resolves the failure without a new one. The model is never the gate.

The controls cover keyless access, least privilege and OIDC subject pinning on AWS, GCP and Azure, and
a Kubernetes set for manifests. Each control, what it detects and what it cannot see is in the
[control catalog](/reference/control-catalog).

### Statuses

| Status | Meaning |
| --- | --- |
| `pass` | Evaluated, and the plan satisfies it. |
| `fail` | Evaluated, and violated. On a deploy this stops the apply unless waived. |
| `warn` | A concern that does not stop the apply. |
| `not_evaluable` | The plan does not hold what the control needs. Never counted as a pass. |

The overall verdict is the worst status: `fail`, then `warn`, then `not_evaluable`, then `pass`. A
policy computed only at apply time, or an AWS managed policy referenced only by ARN, is
`not_evaluable` with a note saying why, never a silent pass.

### Plan and deploy

On a plan, the report is shown in the Plan tab and stops nothing. On a deploy, the same check runs on
the reviewed plan, and a failing hard control stops the job before any resource changes.

### Overrides

An override is an authorized, time-limited waiver of specific control IDs, never of the whole check.
Alethia records who granted it and when it expires, and the runner applies only the controls it names.
The verdict is not rewritten to `pass`: the waiver is sealed into the receipt as an exception. See
[Override a verify failure](/guides/jobs/verify-override).

### IAM Access Analyzer

On AWS, the check can also ask IAM Access Analyzer whether a planned policy could grant any action from
a list of sensitive actions, before anything is deployed. It is off unless the runner sets
`ALETHIA_VERIFY_ACCESS_ANALYZER=1`. An error from the analyzer is `not_evaluable`.

### Receipts

Every apply seals a receipt bound to the SHA-256 of the plan, the verdict, the control catalog version
and any exception. With a signing key it is signed with ed25519 and can be checked offline. See
[Receipts and signing](/concepts/elench/receipts).

### Audits of infrastructure you bring

The controls work on any plan, so an `AUDIT` job can check a `tofu show -json` plan or Kubernetes
manifests that Alethia did not generate, with the same controls. It provisions nothing and writes the
report to the project's feed. Queue it from the assistant; it needs the `project:audit` permission.

### After the apply

- **Drift.** Scheduled refresh-only plans check that live resources still match the state. See
  [Drift detection](/concepts/drift).
- **Vulnerabilities.** If the Trivy Operator add-on runs in the cluster, Alethia reads its
  vulnerability reports on each deploy and drift check and sums them by severity. The Evidence page
  shows the highest severity found, **Clean**, or **Not scanned** when there are no reports.

## What it does not do

- It does not prove compliance. A receipt is evidence that named controls passed on one plan; whether
  that meets a standard is an auditor's judgment.
- It does not judge what the plan cannot show. Those controls are `not_evaluable`.
- It does not let a model decide a verdict or apply a fix.
- It does not see resources outside the plan. Drift detection covers resources in state only.
