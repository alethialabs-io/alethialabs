Alethia seals an evidence receipt on every apply. It binds the Elench verdict to the exact plan that
was applied, and when a signing key is configured it is signed, so you can check it later without
trusting the console.

## How it works

### What a receipt records

| Field | Why |
| --- | --- |
| `plan_sha256` | Binds the receipt to the exact plan. |
| Verdict and the per-control report | What was decided, including `not_evaluable` controls. |
| Catalog version | A verdict means something only against the controls that produced it. |
| Exception | Any waiver: the control IDs, the reason, who granted it, and when it expires. |
| OpenTofu version, runner, evaluation time | Where and when it was produced. |

### Signing

With `ALETHIA_RECEIPT_SIGNING_KEY` set on the runner, each receipt is signed with ed25519 over its
canonical JSON, so any change breaks the signature. Without a key, the receipt is still attached,
unsigned: an apply is never blocked on signing.

| State | Meaning |
| --- | --- |
| **Signed** | Tamper-evident and checkable offline. |
| **Unsigned** | A faithful record, not signed. |
| **—** | No apply has sealed a receipt for this environment yet. |

### Checking one

```bash
alethia verify receipt --job <job-id>
```

The command checks the signature and exits non-zero when it cannot, so a pipeline can gate on it.
`alethia verify show --job <job-id>` prints the report. See [Verify commands](/reference/cli/verify).

A receipt always verifies under the public key it carries, whoever made it, so that alone proves only
that it was not altered. The CLI checks the signature against a key it trusts and says which:

| Trust | The signing key is |
| --- | --- |
| `pinned` | A key you gave with `--key-file`, held outside Alethia. The strongest answer. |
| `org` | A key registered for your organization. Registered, not proven to be held by you. |
| `platform` | Alethia's platform key. The receipt says "Alethia asserted this". |
| `self` | Only the receipt's own key. Proves it was not altered, not who made it. |

### Transparency log

An operator can turn on anchoring with `ALETHIA_REKOR_ANCHOR_ENABLED=true`. The control plane then
logs a hash of each signed receipt in a Rekor transparency log (only the hash; the receipt's contents
are not uploaded), so anyone can check offline that the receipt existed at that time. Anchoring never
blocks an apply: if it fails, the receipt stays unanchored.

### Waivers

A waiver passes specific failing controls for a limited time. It is sealed into the receipt as an
exception, so the record shows the check was passed on purpose, not turned off. Active waivers are
listed on the Evidence page.

## What it does not do

- It does not prove compliance, only what was checked on one plan.
- A platform-signed receipt does not prove that your organization asserted anything. Use your own key
  for that.
- It does not record the Git commit of a bring-your-own module. That is on the environment's source.
