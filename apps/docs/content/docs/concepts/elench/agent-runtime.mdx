Alethia defines each agent tool once and serves it to its own assistant and, read-only, to your agents
(Claude Code, Codex, Cursor and others) over MCP. Every call is checked against your permissions, and
no tool can approve an apply or a destroy.

## How it works

### One registry, two audiences

Every tool is marked with an audience:

| Audience | Who sees it |
| --- | --- |
| In-app | Only the console's assistant: design proposals, canvas tools, and tools that queue jobs. |
| External or both | Read-only tools that are safe for your own agents. |

A test fails the build if a tool has no audience, so the external set cannot widen by accident. The
audience decides only visibility: each tool still checks your permission when it runs.

### The MCP server

The MCP server serves the external tools and six operation tools: `plan`, `request_apply`,
`request_destroy`, `wait_for_job`, `get_job_logs` and `cancel_job`. Clients sign in with OAuth; the
token carries the scopes you approved and is bound to the server. The full list is in the
[tool reference](/agents/tools).

Approval happens outside MCP. `request_apply` records a pending approval bound to the plan's digest
and to the calling client, and returns a console link. A person approves it there. The agent then
calls `request_apply` again, and only that call queues the deploy, once, for that plan, through the
same checks every other path uses. So text an agent reads can lead at most to a pending request.

Evidence is readable too: `get_plan_result` returns a job's status and its [Elench](/concepts/elench)
verdict, and `get_drift_posture` returns an environment's [drift posture](/concepts/drift). Queuing an
audit stays in the console's assistant.

### Agents and memory

An agent is stored data, not a running process: a persona, a mission, a tool scope and a memory
namespace. Each turn runs on stateless compute that loads the agent and narrows the tools to its
scope.

Memory is kept per tenant: under the organization, or under one project in it. Every memory path is
checked, and a path that tries to leave its namespace (`..`, an absolute path, a backslash, a null
byte) is refused, so one tenant cannot read another's memory.

Each scope also has pinned context: custom instructions and knowledge documents, at the organization
and project level, plus facts derived from the project. They are added to the agent's instructions
before its first tool call. You edit them in the assistant's [knowledge panel](/guides/assistant/knowledge).

## What it does not do

- It does not let any tool approve an apply or a destroy.
- It does not give external agents tools that write designs or queue jobs directly, other than the
  operation tools above.
- It does not give an agent more than the person it acts for.
