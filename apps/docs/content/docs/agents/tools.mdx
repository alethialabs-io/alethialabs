The MCP server at `<console origin>/api/mcp` offers the 19 tools below. Twelve change nothing in your
account, and a client connected with `?readonly` sees only those: the eleven reads and
`send_feedback`.

Every tool:

- **acts as you.** Each call checks your role in the organization, the same check the console makes.
  A tool refuses what you cannot see.
- **stays inside what you granted.** The scopes you approved when you connected the client decide
  which tools it is offered. A tool that needs a scope you did not grant is not listed, and refuses a
  call.
- **takes `snake_case` arguments and returns structured content**, with the same JSON as text. A
  refusal or a failure comes back as a tool error with a message.
- **carries all four MCP annotations**, which tell a client which tools change something.
- **leaves secrets out.** No result carries a password, a token or a cloud credential.

## Reads

The reads are the ones the console's assistant uses.

| Tool | Arguments | Returns |
| --- | --- | --- |
| `list_resources` | `kind` (`project`, `job`, `runner`, `cluster`, `connector` or `cloud_identity`), `filter` (optional: `project_id`, `environment_id`, `limit` up to 50) | The items of that kind, and whether more matched than were returned. |
| `get_resource` | `kind` (`project`, `design`, `job`, `drift`, `cloud_inventory` or `scan`), `id`, `environment_id` (optional) | One item in full. A design comes with its `revision`. An unknown id is a tool error. |
| `get_plan_result` | `job_id` | What a plan would do: resources added, changed and destroyed, the monthly cost change, the verify verdict and the plan digest (`plan_sha256`). |
| `catalog` | `provider` (optional) | Every service a design can contain, with each cloud's service name and how it is deployed there. With `provider`, also that cloud's valid regions, instance types, versions and engines. |
| `cidr_for_hosts` | `hosts`, `base` (optional), `cloud` (optional) | The smallest network CIDR block that fits the hosts and that the cloud's template accepts. |
| `compare_providers` | `scan_job_id` | A finished scan's estimated monthly cost on each cloud, cheapest first. |
| `get_usage` | `kind` (`runner_minutes`, `ai` or `billing`) | Runner minutes against the plan, AI credit use, or the plan and seats. |
| `search_docs` | `query`, `top_k` (1 to 8, default 4) | The most relevant passages of these docs, each with its URL. |
| `wait_for_job` | `job_id` or `approval_id`, `timeout_s` (up to 50) | Where the job or the approval stands, whether it is done, and when to ask again. |
| `get_job_logs` | `job_id`, `cursor` (optional) | The job's log from the cursor, in a field named `untrusted_output`, and the next cursor. |
| `validate_design` | `design` | Whether the design is valid, and each problem with its path and, where known, a fix. Nothing is saved. |

Amounts are integer minor units with a currency code. Timestamps are ISO 8601.

## Designs

These tools change records in Alethia, never your cloud. A problem you can fix comes back in
`errors`, not as a tool error.

| Tool | Scope | Arguments | Returns |
| --- | --- | --- | --- |
| `create_project` | `design` | `name`, `design`, `idempotency_key` | `status` (`created` or `invalid`), the `project_id` and its `revision`. |
| `apply_design_patch` | `design` | `project_id`, `environment_id` (optional), `base_revision`, `patch`, `idempotency_key` | `status` (`applied`, `invalid` or `conflict`) and the new `revision`. |

`patch` is a list of JSON Patch operations (`add`, `remove`, `replace`), applied in order, all or
none. Read the design with `get_resource` and pass its `revision` as `base_revision`. If the design
changed since, the tool answers `conflict` with the `current_revision`: read it again and retry. The
same `idempotency_key` returns the first result.

## Operations

| Tool | Scope | Arguments | Returns |
| --- | --- | --- | --- |
| `scan_repo` | `plan` | `repo`, `idempotency_key` | The `job_id` of a scan that infers what a repository needs. The repository is cloned and parsed, never run. The same key returns the same job. |
| `plan` | `plan` | `project_id`, `environment_id`, `destroy` (optional), `idempotency_key` | The `job_id` of a plan of what the design would create or change. With `destroy: true`, a plan of what tearing the environment down would remove. It changes nothing in the cloud. The same key returns the same job. |
| `request_apply` | `apply` | `plan_job_id`, `reason` (optional) | An approval request for that plan: `approval_id`, `status`, `approve_url`, `digest_prefix`, `expires_at` and `job_id`. |
| `request_destroy` | `destroy` | `project_id`, `environment_id`, `reason` (optional) | The same, for destroying the environment. The approval is for the environment's latest destroy plan, so call `plan` with `destroy: true` first. |
| `cancel_job` | `plan` | `job_id` | The job's status after the cancel. A finished job stays as it is. |
| `send_feedback` | none | `text`, `missing_capability` (optional) | Whether the Alethia team received it. On a self-managed installation there is no team inbox, so it answers `false`. |

### How an apply or a destroy runs

No tool approves. An apply or a destroy runs only after you approve it in the console:

1. The agent calls `request_apply` with a plan it has reviewed. Nothing runs. The tool returns
   `status: "pending"`, a link and the first 8 characters of the plan's digest.
2. You open the link in the console, check that the page shows the same 8 characters, and approve.
   For a destroy, you type the environment's name.
3. The agent calls `request_apply` again with the same plan. Only now does the deploy start. The tool
   returns `status: "consumed"` and the `job_id`. Calling it again returns the same job.

A destroy runs the same way, against a destroy plan: the agent calls `plan` with `destroy: true`,
waits for it, and then calls `request_destroy`. The destroy removes exactly what that plan lists. If
the environment changes after the destroy plan, the agent must plan the destroy again.

An approval covers one plan, for the client that asked for it, once. It expires after the time your
organization set (60 minutes by default). A newer plan, or a change to the environment, voids it.

## Not on the server

These need a person in the console, or the CLI:

- Approving an apply or a destroy.
- An audit of existing infrastructure.
- Connecting a cloud, and anything that opens part of the console.
