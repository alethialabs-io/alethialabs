The `alethia` CLI is how an agent acts on Alethia. This page lists what changes when a program, not a
person, runs it.

## Agent mode

In agent mode the CLI:

- never prompts;
- prints no colour and no spinner, and writes progress as plain lines on stderr;
- makes `json` the default `--output`.

Agent mode is on when any of these is true:

| Setting | Effect |
| --- | --- |
| `--agent yes` | On for this command. `--agent no` turns it off. |
| `ALETHIA_AGENT=yes` | On for every command in that environment. `no` turns it off. |
| `--agent auto` (the default) | On when the environment has a non-empty `AGENT`, `AI_AGENT`, `CLAUDECODE`, `CODEX_SANDBOX` or `CURSOR_AGENT`. |

The flag wins over the environment variable. Any value other than `yes`, `no` or `auto` (or a
boolean) is a usage error, not a guess.

`--no-input`, or a standard input that is not a terminal, also stops every prompt, without the other
changes.

## Output and errors

A command writes its result to stdout, and nothing else. Under `--output json` that result is one
JSON document.

An error goes to stderr. Under `--output json` it is one line in the `alethia.error/v1` format:

```json
{"error":{"code":"confirmation_required","class":"input_required","exit_code":9,"message":"…","hint":null,"docs_url":null,"retryable":false,"retry_after_seconds":null,"request_id":null,"http_status":null,"operation":null},"schema":"alethia.error/v1"}
```

Every key is always present. A value the error does not carry is `null`. Branch on `code` or on the
exit code, not on `message`.

## Exit codes

`alethia plan` and `alethia apply` give `2` and `3` their own meanings; see
[plan and apply](/reference/cli/plan-and-apply#exit-codes). Every other code means the same thing for
every command:

| Code | Meaning | Retry |
| --- | --- | --- |
| `0` | Success | — |
| `1` | A failure the CLI could not classify | No |
| `4` | Not signed in, or the credential has expired | After `alethia login` |
| `5` | Signed in, and not permitted | No |
| `6` | The thing named does not exist | No |
| `7` | Conflict or failed precondition | After the state changes |
| `8` | Usage or validation error | After fixing the input |
| `9` | A confirmation or a value is needed, and nothing can ask for it | With `--yes` or the missing flag |
| `10` | Rate limit, quota or plan limit | After the wait the error names |
| `11` | The control plane could not be reached or could not answer | Yes, with backoff |
| `12` | The wait deadline passed; the operation is still running | Resume with the operation id |
| `13` | The remote operation finished, and it failed | No |
| `14` | This CLI is too old for the control plane | After `alethia update` |
| `130` | Interrupted | — |

## Apply and destroy need a confirmation

`alethia apply`, `alethia up` and `alethia project destroy` ask before they change infrastructure. In
agent mode nothing can ask, so they stop with exit `9` and the code `confirmation_required`. They go
ahead only when the command carries `--yes`.

Do not add `--yes` yourself. Run `alethia plan`, show the person what it would change, and add
`--yes` only when the person tells you to.

A deploy into a protected environment can also wait for a person to approve it in the console. Then
`apply` prints the page where the job is approved and waits. See
[plan and apply](/reference/cli/plan-and-apply).

## Credentials

The CLI uses one of two credentials. Both act as the person who created them. A CLI sign-in works in
your active organization, which `alethia org switch` changes. A service-account token works only in
the organization it was created for.

| Credential | How you get it | Where it lives |
| --- | --- | --- |
| CLI sign-in | `alethia login` opens the browser; `--no-browser` prints the URL instead | The system keychain, or a file with `--insecure-storage` |
| Service-account token | `alethia token create --name <purpose>` prints it once | Wherever you put it. The CLI reads it from `ALETHIA_TOKEN` or `--token` and never stores it |

An agent in your shell uses your CLI sign-in. `alethia login` refuses while `ALETHIA_TOKEN` is set.

A service-account token carries scopes and a project list. A token minted without either holds all
five scopes (`read`, `design`, `plan`, `apply`, `destroy`) over every project, so it can do everything
you can do in its organization. `alethia token create` mints that token. To give a token less, mint
it through the API with `scopes` and `project_ids`. A request outside its limit is refused with
`insufficient_scope`. Give a token an expiry with
`--expires-in-days`, and revoke it with `alethia token revoke <id>` when the work is done.
See [authentication](/reference/cli/authentication).
