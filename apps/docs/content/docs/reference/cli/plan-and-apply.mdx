title: Plan & Apply
description: Describe a project in alethia.yaml, preview the changes with plan, and create and deploy it with apply.

One file describes a project; two commands take it from a file to a running cluster. Nothing has
to be copied out of another command's output: the cloud account is named by its **label**, the
runner by its **name**, and every environment by the name the file gives it.

## `alethia.yaml`

The manifest is the whole shape of a project — where it provisions, every environment with its
placement, and the components each environment carries:

```yaml
project: boutique
cloud:
  account: prod-account        # the connector's label, as `alethia connector list` shows it
  region: nbg1
environments:
  - name: prod
    stage: production
    placement: dedicated       # owns the Fabric: this is the environment with a cluster
    components:
      cluster:
        node_min_size: 2
        node_max_size: 3
  - name: dev-1
    stage: development
    placement: namespace       # placed onto prod's Fabric, no new cluster
    namespace: boutique-dev-1
    components:
      repositories:
        apps_destination_repo: https://github.com/alethialabs-io/alethia-examples
        apps_path: examples/online-boutique/overlays/dev-1
      databases:
        - name: orders
          engine: postgres
```

| Key | What it is |
| --- | --- |
| `project` | The project's name. Unique in the organization, so `apply` finds an existing project by it. |
| `cloud.account` | The cloud account's label (or its id). Omit it to create an unlinked project. |
| `cloud.region` | The region to provision into. |
| `iac.version` | OpenTofu version to pin. Optional; the server defaults it. |
| `environments[].name` | The environment's name. |
| `environments[].stage` | `development`, `staging` or `production`. |
| `environments[].placement` | `dedicated`, `vcluster` or `namespace`. Optional: the **first** environment defaults to `dedicated` and owns the Fabric; every later one defaults to `namespace` and shares it. |
| `environments[].namespace` | The destination namespace for a shared placement. Optional; derived from the name. Ignored on `dedicated`. |
| `environments[].lifecycle` | `persistent` (default) or `ephemeral`. Set when the environment is created, and not changed after that. |
| `environments[].addons` | The catalog add-ons the environment runs, as a list of `{ id, version, mode, settings, values, values_file }`. See [Add-ons](#add-ons). |
| `environments[].components` | The environment's resources, keyed by kind. A one-per-environment kind (`cluster`, `network`, `dns`, `observability`, `repositories`) is written as its fields; a named kind (`databases`, `caches`, `queues`, …) as a list of entries, each with a `name`. `alethia project component kinds` lists them and the fields each takes. |

A misspelt key, a stage outside the allowed set, a component kind the server does not publish or a
field a kind does not take is refused **before anything is sent**, naming every problem at once.
The CLI only ever refuses what the server would certainly refuse: anything else is passed through
for the server to decide.

<Callout type="warn">
  Placement is the key with a bill attached. Each `dedicated` environment is a separate cluster with
  its own OpenTofu state; `namespace` and `vcluster` share the Fabric that already exists. The
  example above is **one** cluster hosting two environments.
</Callout>

## `alethia apply`

Create whatever the file declares that does not exist yet, show the plan, and deploy every
environment.

```bash
alethia apply                          # ./alethia.yaml, asks before applying
alethia apply --yes --no-input         # in a pipeline
alethia apply --runner my-box          # deploy with a named runner
alethia apply --env dev-1              # create everything, deploy only dev-1
alethia apply --yes --timeout 45m      # wait at most 45 minutes for the deploys
```

```
▸ Reading alethia.yaml · boutique · hetzner/nbg1
  + project boutique
  prod   dedicated  + environment  + cluster
  dev-1  namespace  + environment  + repositories  + databases/orders
  1 project to create · 2 environments · 3 components
Apply these changes? Yes
  ✓ created project boutique
  ✓ added cluster in prod
  ✓ added repositories in dev-1
  ✓ added databases/orders in dev-1
▸ Deploying prod (job 4f3c2b1a-…)
  ✓ Job completed successfully
▸ Deploying dev-1 (job 8a1d0e77-…)
  ✓ Job completed successfully

✓ boutique is up.
```

The plan and the last line are the command's output, on stdout. Everything between them is
progress, on stderr. So a script that reads stdout gets the plan and the result and nothing else.

Running `apply` again is safe. On a project that already matches the file it creates nothing,
marks each environment `=`, and deploys again. What it cannot reconcile is shown and refused before
a single write: an existing environment whose stage, placement or lifecycle differs from the file.
`alethia up` runs the same apply, so it behaves and exits the same way.

### What the file leaves out is never removed

`apply` creates and updates. It does not remove anything. An environment, a component or an add-on
that is on the server and not in the file is **unmanaged**: `plan` and `apply` list it and leave it
as it is.

```
  staging is on the server and not in the file — left alone (unmanaged)
  Not in the file means unmanaged: apply leaves it as it is and never removes it.
```

To remove an environment, destroy it with
[`alethia project destroy`](/reference/cli/project). To remove a component, use
[`alethia project component remove`](/reference/cli/project). Deleting its lines from the file does
neither.

### Waiting for the deploys

`apply` deploys each environment in file order, and waits for each one before it starts the next.
The first environment owns the cluster, so the others cannot be deployed before it.

A deploy applies a reviewed plan. So for each environment `apply` first queues a preview (a PLAN
job), waits for it, and prints how many resources it would create, update, replace and delete. The
deploy then applies exactly that plan. A preview that fails stops the run with exit `13`, and that
environment is not deployed.

```
▸ Previewing prod (job 2b7e91c0-…); a deploy applies a reviewed plan
  prod Plan: 14 to create, 0 to update, 0 to replace, 0 to delete.
▸ Deploying prod (job 4f3c2b1a-…)
```

- `--no-wait` returns once the deploys are queued. It still waits for each preview, because a
  deploy needs its plan. Every job is named in the result. `--wait=false` means the same.
- `--timeout` sets how long the whole run may take, previews included, for example
  `--timeout 45m`. When the time passes, `apply` stops waiting and exits `12`. The job that is
  running keeps running. The error names its job, the command that follows it, and the
  environments that were not deployed yet. Run `alethia apply` again when that job has finished.
- Press Ctrl+C to stop waiting. The job keeps running and `apply` exits `130`.

A deploy that stays queued for two minutes because no runner has claimed it is also reported, with
the command that shows which runners are online.

### When a deploy needs a person's approval

A deploy or a destroy started from the CLI needs a person's approval of the plan it applies. This is
true for a device sign-in and for a service token, because the control plane cannot tell a person at
a terminal from an agent in the same shell. A person clicking deploy in the console needs no
separate approval: the click is the approval.

When the control plane answers that a deploy needs an approval, `apply` asks for one, prints the
console page where a person approves it, and waits:

```
⚠ This deploy needs a person's approval. Approve it at https://alethialabs.io/approvals/6b21d8f4-… — the page must show plan 2b7e91c0-… with a digest starting a1b2c3d4.
Waiting for approval 6b21d8f4-… to be decided (expires 2026-12-01T10:00:00Z)...
```

The approval page shows the same eight digest characters. Check that they match before you approve:
that is how you know you approve the plan the command showed you. Once it is approved, `apply`
queues the deploy with the approval and carries on.

- **Rejected:** `apply` exits `5` and nothing is deployed.
- **Expired, or superseded** by a newer plan or a change to the environment: `apply` exits `7`. Run
  it again to ask for a new approval.
- **`--no-wait`, or agent mode:** `apply` asks for every environment's approval, waits for none,
  and exits `9`. The error names each approval page, and the `alethia project deploy` command that
  deploys each plan once it is approved.

One approval covers one plan of one environment, once. It cannot be reused for a later plan.

## `alethia approve`

Open the console page where a person approves a deploy or a destroy that the CLI asked for.

```bash
alethia approve 6b21d8f4-0c5e-4a93-9f27-3d81b6e5c704                # opens the page in your browser
alethia approve 6b21d8f4-0c5e-4a93-9f27-3d81b6e5c704 --no-browser   # prints the page, to send to whoever approves
```

| Argument or flag | Required | Description |
|---|---|---|
| `[approval-id]` | No | The approval id the deploy or destroy printed. Omit it on a terminal and you are asked for it. |
| `--no-browser` | No | Print the page instead of opening it. |

`approve` never approves anything. It sends nothing to the control plane, so neither a stored CLI
credential nor an agent that holds one can approve its own request. The decision is made only in a
signed-in console session.

### Exit codes of `apply`

| Code | Meaning |
| --- | --- |
| `0` | Done. Without `--no-wait`, every deploy finished. |
| `1` | The file does not exist or is not valid. |
| `2` | The file cannot be applied as written. This is the code `alethia plan` gives the same file; see [Exit codes](#exit-codes). |
| `5` | A person rejected the approval a deploy asked for. |
| `7` | The approval expired, or a newer plan or change superseded it. |
| `9` | Nobody could confirm and `--yes` was not passed, or a deploy is waiting for a person's approval and the command did not wait. |
| `12` | `--timeout` passed. The preview or the deploy is still running. |
| `13` | A preview or a deploy finished and failed, or was cancelled. `alethia jobs logs` with the job's id shows why. |
| `130` | You stopped the wait with Ctrl+C. |

Any other code is one of the CLI's general exit codes: for example `4` when you are not signed
in, `7` when the server refuses a change because of a conflict, and `11` when the control plane
cannot be reached.

An environment's `lifecycle` is set once, when the environment is created. Nothing changes it after
that: not `apply`, and not the console. A file that leaves `lifecycle` out means `persistent`. If the
file says a different lifecycle than the server holds for an existing environment, `plan` shows the
difference and `apply` refuses the whole file:

```
  preview  namespace  = environment
    ✗ the file says lifecycle persistent, the server has ephemeral — a lifecycle is set only when an environment is created, …
```

To keep the environment, make the file match the server. If the server holds `persistent`, remove
`lifecycle` or set it to `persistent`. If the server holds `ephemeral`, set `lifecycle: ephemeral`.

To get the other lifecycle, declare a new environment with it, and `apply` creates that
environment. Two things do not happen on their own:

- The old environment is not removed. `apply` never deletes, so it keeps running until it is
  destroyed.
- The new environment gets `namespace` placement unless the file sets `placement`. The one
  exception is an environment listed first in the file, which gets `dedicated`.

### Changing a component

Edit a field of a component that already exists, and `plan` and `apply` show the change and make
it. Each row starts with a mark:

| Mark | Meaning |
| --- | --- |
| `+` | It does not exist yet. `apply` creates it. |
| `~` | It exists, and at least one field the file declares has a different value on the server. `apply` changes those fields. |
| `=` | It exists, and every field the file declares already matches. `apply` sends nothing for it. |

Under each `~` row, one line names each changed field with the server's value and the file's value.
Here the file raises `max_capacity` of the `orders` database in `prod` from `4` to `8`:

```
▸ Reading alethia.yaml · boutique · hetzner/nbg1
  prod   dedicated  = environment  = cluster  ~ databases/orders
    ~ databases/orders  max_capacity: 4 → 8
  dev-1  namespace  = environment  = repositories
  0 projects to create · 0 environments · 0 components · 1 component to update
```

`(unset)` means the server has no value for that field.

- **A field you leave out is never cleared.** `apply` compares only the fields the file names, and
  sends only the ones that changed. This is true for every kind: a named component such as a
  database, and a one-per-environment kind such as `cluster`. To change one field of a database,
  write that field; the other fields keep their values.
- **A `cloud_identity_id` must be one you can use.** It must name a cloud account of your
  organization, or your own personal one. Any other id is refused as `Cloud identity not found`.
- **Values compare by meaning.** `2` and `2.0` are the same number. Lists and maps compare item by
  item, and the order of a list counts.
- **A refused change does not stop the others.** If the server refuses a change, `apply` reports it
  for that component, does not deploy that environment, and continues with the other environments.
  Then it exits with an error that names each refused component.

### When the server changes first

`apply` changes a component only if the server still holds the copy that `apply` read. There is no
saved plan file: `apply` reads every component again, computes the changes against that read, and
then makes them. Two rules protect that read.

**A component changed after the read is not overwritten.** `apply` sends the component's revision
(its `updated_at`) with each change. If someone changed the component in the meantime, for example
in the console or with another `apply`, the server refuses the change. `apply` then names each
setting that changed on the server:

```
  ✗ databases/orders in prod was not updated: databases/orders changed on the server after
    `alethia plan` read it: max_capacity: 4 → 16; re-run `alethia plan` to see the difference
    against the server's copy now, then apply again
```

Run `alethia plan` again, decide which value you want, and then run `alethia apply`. A component
that was removed after the read is refused in the same way. `apply` does not create it again.

**A component is not changed while its environment is deploying or being destroyed.** The server
refuses every change that `apply` makes to an existing component while one of these is unfinished
for that environment:

- a deploy job, or the image build that starts a deploy of an environment with services built from
  a repository;
- a destroy job;
- a promotion into the environment, from the moment its plan is queued, through approval, until its
  deploy finishes. The promotion deploys the design that its plan read, so a change made in between
  would not be part of that deploy.

A job counts from the moment it is queued until it finishes. Other jobs, such as a plan that is not
part of a promotion or a drift check, do not block a change. The error names what holds the
environment:

```
  ✗ databases/orders in prod was not updated: databases/orders cannot be changed while a deploy
    of this environment is processing (job 3f9c…); follow it with
    `alethia jobs logs 3f9c… --follow`, then re-run `alethia apply` once it has finished
```

Wait for that job or promotion to finish, then run `alethia apply` again. `apply` does not queue the
change for later.

The rule has three limits:

- The component's own status does not block a change. A database can stay `CREATING` after a
  successful deploy while its chart is still starting, and you can still change it.
- Adding a component that does not exist yet is not refused. `apply` creates it even while a deploy
  is running. That deploy does not include it; the next deploy does.
- A deploy reads the components a moment before its job is queued. A change that lands in that
  moment is accepted and is not part of that deploy. It stays saved, and the next deploy applies it.

Both refusals follow the rule above: that environment is not deployed, and the other environments
continue.

### Setting and removing a `provider_config` key

A component's `provider_config` holds its template knobs, the same ones the console's **Advanced**
section sets. `plan` and `apply` treat it **key by key**, not as one value:

```yaml
      databases:
        - name: orders
          engine: postgres
          provider_config:
            rds_backup_retention_period: 14   # set this key
            rds_performance_insights: null    # remove this key
```

- A key you write is set to the file's value.
- A key you write as `null` is removed. `plan` shows it as a change only while the server still
  holds the key, so the removal shows once and then settles.
- A key you do not write is kept, and shows no change. A key set in the console stays set.
- `provider_config` itself must be a mapping. A whole `provider_config: null`, or an empty
  `provider_config:`, is refused before anything is sent, because the server refuses it. To remove
  every key, write each one as `null`.

`apply` sends only the keys that changed. The keys a component accepts depend on its cloud;
[Setting template knobs](/reference/cli/project#setting-template-knobs) explains how to find them.

`apply` changes the component's **settings**. It does not tell you whether the next deploy replaces
the cloud resource. To see that, read the OpenTofu plan of the deploy: `alethia project preview`.

The runner: `--runner` takes a name or an id. Omitted, `apply` uses the only online runner that
takes jobs for the project's cloud, without a question. With several you are asked on a terminal,
and under `--no-input` the job is left for the server to place. A runner that does not take the
project's cloud is refused, whether you name it or pick it: it would never claim the deploy.

{/* fieldspec: alethia apply */}

| Field        | What it is                                                                                                                 | Set without the form |
| ------------ | -------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| Manifest     | The alethia.yaml to apply (default: ./alethia.yaml)                                                                        | `--file`             |
| Runner       | Runner to deploy with, by NAME or id. Omitted: the only online runner that takes this cloud's jobs, or asked on a terminal | `--runner`           |
| Environments | Only deploy these environments (repeatable; default: every environment in the file)                                        | `--env`              |
| Confirm      | Apply without asking (required with --no-input)                                                                            | `--yes`              |
| Wait         | Queue the deploys and return instead of waiting for them or for a person's approval (exits 9 when one is needed)           | `--no-wait`          |
| Timeout      | Stop waiting after this long, for example 30m (the deploys keep running; exits 12). Omitted or 0: wait without a limit     | `--timeout`          |

`--wait` is the flag every command that queues a job has. `apply` waits by default, so it is on
unless you turn it off: `--wait=false` is the same as `--no-wait`.

With `--output json`, `alethia plan` prints the plan and `alethia apply` prints the result as one
object each. In the plan, a component with the action `update` carries a `changes` array, one entry
per changed field:

```json
{
  "kind": "databases",
  "name": "orders",
  "action": "update",
  "fields": { "engine": "postgres", "max_capacity": 8 },
  "changes": [{ "field": "max_capacity", "from": 4, "to": 8 }]
}
```

`from` is `null` when the server has no value for the field. A `create` or `unchanged` component has
no `changes` key. A component that exists also carries `revision`, the server's `updated_at` that the
plan read, which `apply` sends back with the change.

The result of `apply` has the shape every command that changes something returns. Its `object` is
what this apply did:

```json
{
  "id": "4b1d2c9e-7f3a-4e55-9c1d-2a6f0b8e1c37",
  "kind": "project",
  "action": "created",
  "job": { "id": "8a1d0e77-2b4c-4f6e-9d1a-3c5e7f9b1d2f", "type": "DEPLOY" },
  "dry_run": false,
  "object": {
    "project_id": "4b1d2c9e-7f3a-4e55-9c1d-2a6f0b8e1c37",
    "created": ["project boutique", "prod cluster", "dev-1 repositories", "dev-1 databases/orders"],
    "jobs": [
      {
        "id": "4f3c2b1a-9d8e-4c7b-a6f5-1e2d3c4b5a69",
        "type": "DEPLOY",
        "status": "SUCCESS",
        "environment": "prod",
        "awaiting_approval": false,
        "warnings": []
      },
      {
        "id": "8a1d0e77-2b4c-4f6e-9d1a-3c5e7f9b1d2f",
        "type": "DEPLOY",
        "status": "SUCCESS",
        "environment": "dev-1",
        "awaiting_approval": false,
        "warnings": []
      }
    ]
  }
}
```

- `action` is `created` when this run created the project, `updated` when it wrote anything into a
  project that existed, `queued` when it only queued deploys, and `unchanged` when it did nothing.
- `job` is the last deploy that was queued. `object.jobs` lists every one, in the order they ran.
- `warnings` are the warnings a finished deploy recorded, the same list
  [`alethia jobs get`](/reference/cli/jobs) shows. It is always an array.
- `object.errors` is present when the server refused a change. Each entry is
  `{ "environment", "component", "error" }`. That environment is not deployed, the others are, and
  `apply` exits with the code of the first refusal.

When `apply` fails after it has written something, stdout still carries this object, with what was
created and the jobs that were queued. The error is on stderr, as one JSON object on the last line.

<Callout type="warn">
  **Changed for scripts.** Before this release, `apply --output json` printed the inner object on its
  own, each job had `job_id` in place of `id`, and progress lines were on stdout in table form. Read
  `.object.jobs[].id` now. `alethia up --output json` prints the same result.
</Callout>

## Add-ons

An environment can declare the [catalog add-ons](/reference/cli/addons) it runs. `plan` shows what
would change, and `apply` makes it so. This file declares two environments. `staging` runs
external-dns pinned to chart version `1.14.5` with two settings, and kube-prometheus-stack with a
Helm values file. `prod` runs loki at the catalog's default version:

```yaml
project: boutique
cloud:
  account: prod-account
  region: nbg1
environments:
  - name: prod
    stage: production
    placement: dedicated
    addons:
      - id: loki                         # no version: the catalog's default version
        settings:
          retentionDays: 30
  - name: staging
    stage: staging
    placement: namespace
    namespace: boutique-staging
    addons:
      - id: external-dns
        version: 1.14.5                  # pin the chart version
        settings:
          provider: cloudflare
          domainFilter: staging.boutique.example.com
      - id: kube-prometheus-stack
        settings:
          retentionDays: 7
        values_file: helm/kps-staging.yaml   # relative to alethia.yaml
```

`helm/kps-staging.yaml` is an ordinary Helm values file, next to `alethia.yaml` in the repository:

```yaml
grafana:
  replicas: 2
prometheus:
  prometheusSpec:
    resources:
      requests:
        memory: 2Gi
```

| Key | What it is |
| --- | --- |
| `id` | The add-on's catalog id. Required. An id the catalog does not have is refused, and the refusal lists the ids it does have. |
| `version` | A chart-version pin: one exact version, such as `1.14.5`. A range such as `^1.14` is refused. |
| `mode` | `managed` or `gitops`. Omitted on a new add-on, `managed`. |
| `settings` | The add-on's settings, by name: the same keys `alethia addon enable` sets. A key the add-on does not have is refused, and the refusal lists the keys it does have. |
| `values` | An Advanced Helm-values override, written inline as a mapping. |
| `values_file` | The same override, read from a file. The path is relative to `alethia.yaml` and must name an existing file inside its directory: an absolute path, a `..` out of it, a symlink that leads out of it, or a file that does not exist is refused with one message, which names the path as you wrote it. Use `values` or `values_file`, not both. See [Where a values file can come from](#where-a-values-file-can-come-from). |

### Where a values file can come from

The fence is the folder that holds `alethia.yaml`, not the files that Git tracks. `apply` sends any
file inside that folder that `values_file` names. This includes a file that a CI step writes into
the workspace, such as a kubeconfig or a credentials file. If `alethia.yaml` names that file,
`apply` sends its contents to the server as the override.

Keep each values file committed, and review it as you review `alethia.yaml`. Do not name a file
that a pipeline step creates.

### Keep and clear

Each key means what the same flag of [`alethia addon enable`](/reference/cli/addons) means, because
`apply` sends the same request:

| You write | `apply` does |
| --- | --- |
| nothing for a key | keeps what is stored: the pin, the mode, each setting, the override |
| `version: 1.14.5` | pins the chart version |
| `version: ""` or `version: null` | removes the pin, so the catalog's default version applies |
| `settings: { key: value }` | sets that one setting and keeps the others |
| `settings: { key: null }` | resets that setting to the add-on's default |
| `values` or `values_file: path` | replaces the whole stored override |
| `values_file: ""` or `values: null` | removes the override |

### What `plan` shows

Add-ons get one line per environment, with the same marks as components. Under it, one line names
each changed field. Here staging's external-dns runs the catalog's default version and an older
domain filter, kube-prometheus-stack's values file changed, and reloader in `prod` is enabled on
the server but not in the file:

```
▸ Reading alethia.yaml · boutique · hetzner/nbg1
  prod     dedicated  = environment
    add-ons  = loki
    add-on reloader is enabled on the server and not in the file — left alone (unmanaged)
  staging  namespace  = environment
    add-ons  ~ external-dns  ~ kube-prometheus-stack
    ~ external-dns  settings.domainFilter: boutique.example.com → staging.boutique.example.com
    ~ external-dns  version: (catalog default) → 1.14.5
    ~ kube-prometheus-stack  values: changed (6 lines)
  0 projects to create · 0 environments · 0 components · 0 add-ons to enable · 2 to change
```

**A plan never shows what an override says.** A values file can be any file in the repository,
and a plan is printed into CI logs. So the `values` line says only `changed (N lines)`, with N the
line count of the new override, or `removed`. It shows no hash either: a short hash of a value
such as a password can be guessed offline from a public log. An override that is the same mapping
as the stored one is unchanged and gets no line, even if its whitespace differs. With `--output json`, the
`values` change has `"from": null` and the same summary in `"to"`. `apply` still sends the whole
file.

`(default)` means a setting is reset to its default. A setting
you reset with `null` shows as a change only while the server holds a value other than the default,
so the reset shows once and then settles.

`--output json` puts the add-ons on each environment as `addons`, each with an `id`, an `action`
and, for an `update`, the same `changes` array components carry. A change to one setting has the
setting's name in `key`. Add-ons that are on the server but not in the file are in
`unmanaged_addons`.

### What `apply` never does

- **It never disables an add-on.** An add-on that is enabled on the server and not in the file is
  listed as unmanaged and keeps running. Disable one with
  [`alethia addon disable`](/reference/cli/addons).
- **It never takes a secret from the file.** `alethia.yaml` is committed to git, so a secret setting
  in it is refused before anything is sent. The refusal names the setting. Set a secret with
  `alethia addon enable <id> --set <key>=…` or in the console. `apply` keeps a stored secret as it
  is, and `plan` never prints a secret's value.

<Callout type="info">
  **A secret for an environment that `apply` creates.** The file cannot carry a secret, and
  `alethia addon enable --env <name>` needs the environment to exist. So the first `apply` installs
  the add-on without it: external-dns on a token provider such as Cloudflare comes up and cannot
  write DNS records yet. Set the token once the environment exists, here from an environment
  variable so it stays out of your shell history, and deploy again:

  ```bash
  alethia apply --yes
  alethia addon enable external-dns --project boutique --env staging --set apiToken="$CLOUDFLARE_API_TOKEN"
  alethia apply --yes
  ```

  The second `apply` leaves the token as it is. On a workload-identity provider (`aws`, `google`,
  `azure`) there is no token: set `workloadIdentity` under `settings` in the file, because it is an
  identifier and not a secret.
</Callout>

`apply` enables add-ons after it creates components and before it deploys. If the server refuses an
add-on, `apply` reports it, does not deploy that environment, and continues with the others.

## `alethia up`

The whole first run in one command: sign in, attach nothing (see below), write the manifest, apply
it. Every step is skipped when it is already done, so it resumes wherever the last run stopped.

```bash
alethia up                                  # asks for what it needs
alethia up --project boutique --region nbg1 --cloud-account prod-account --yes --no-input
```

| Step | Skipped when |
| --- | --- |
| the control-plane URL and the login | this machine has a live credential |
| a cloud account | one is connected — **otherwise `up` stops**, see below |
| a runner | a runner that takes the account's cloud is online, or a managed fleet takes the deploy — **otherwise `up` stops**, see below |
| `alethia.yaml` | this directory has one |
| the apply | never; that is the point |

With the manifest already present, an account connected and a runner available, `alethia up`
**is** `alethia apply`.

<Callout type="info">
  `up` cannot attach a cloud account for you. Each cloud has its own keyless flow with its own
  arguments — `alethia connector aws|gcp|azure|hetzner` — so `up` stops and names them
  rather than growing a fifth version that would drift from the four.
</Callout>

<Callout type="info">
  `up` cannot start a runner for you either: a runner is a process that somebody has to start. When
  nothing would claim the deploy, `up` stops before it creates anything or queues a job, and prints
  the command that adds a runner for the account's cloud —
  [`alethia runner register`](/reference/cli/runners), or `alethia runner deploy` when a runner is
  already online to build one. Run that command, then run `alethia up` again. With `--runner`, the
  named runner must exist, be online, and take the account's cloud.
</Callout>

{/* fieldspec: alethia up */}

| Field         | What it is                                                                                                       | Set without the form |
| ------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------- |
| Manifest      | The alethia.yaml to apply, written when it does not exist yet                                                    | `--file`             |
| Project name  | Name for a project this authors (asked for on a terminal when the file is missing)                               | `--project`          |
| Region        | Cloud region for a project this authors                                                                          | `--region`           |
| Cloud account | Cloud account to link, by its LABEL or its id                                                                    | `--cloud-account`    |
| Stage         | Stage for the environment this authors                                                                           | `--stage`            |
| Machine type  | Machine type for the cluster nodes, e.g. t3.xlarge (needs a cloud account; not with --node-size)                 | `--instance-type`    |
| Node size     | Node size as vCPUxGiB, e.g. 4x16, mapped to the nearest machine type (not with --instance-type)                  | `--node-size`        |
| Runner        | Runner to deploy with, by NAME or id. Omitted: the only online runner, or asked on a terminal                    | `--runner`           |
| Confirm       | Apply without asking (required with --no-input)                                                                  | `--yes`              |
| Wait          | Queue the deploys and return instead of waiting for them or for a person's approval (exits 9 when one is needed) | `--no-wait`          |

Scripted, `up` writes a single environment at `--stage`; on a terminal it asks for the whole matrix.
[`alethia project env add`](/reference/cli/project) is how a second environment arrives later.

`--instance-type` and `--node-size` choose the cluster's node shape. `up` writes it into the file
as a `cluster` component on each `dedicated` environment, so the file shows it and `apply` creates
the cluster with it. Without either flag the file has no `cluster` component, and the cluster gets
the catalog's default machine type for its cloud. The two flags are mutually exclusive.

## `alethia plan`

The same comparison, with the writes left out: what `apply` would create, what it would change
(field by field, as in [Changing a component](#changing-a-component)), what already matches, and
anything it would refuse. Nothing is written and no job is queued.

```bash
alethia plan
alethia plan --file staging.yaml --output json
alethia plan --detailed-exitcode
```

{/* fieldspec: alethia plan */}

| Field              | What it is                                                                                                           | Set without the form  |
| ------------------ | -------------------------------------------------------------------------------------------------------------------- | --------------------- |
| Manifest           | The alethia.yaml to plan (default: ./alethia.yaml)                                                                   | `--file`              |
| Detailed exit code | Exit 0 with no changes, 2 with changes, 3 with problems (1 is an error). Default: 0 unless the plan has problems (2) | `--detailed-exitcode` |

The per-environment OpenTofu plan runs inside every deploy. To queue one on its own, for a
pipeline that gates on it, use [`alethia project preview`](/reference/cli/project).

A plan never contains a removal. What is on the server and not in the file is listed as unmanaged:
see [What the file leaves out is never removed](#what-the-file-leaves-out-is-never-removed). In
`--output json`, those environments are in `unmanaged` and those add-ons in each environment's
`unmanaged_addons`.

### Exit codes

A plan has **problems** when the file asks for something `apply` cannot do: a stage, placement or
lifecycle that differs from an existing environment, or an add-on setting that `apply` refuses to
send. `apply` refuses such a file before it writes anything. The exit code of `plan` tells you so
first, and a pipeline can stop on it when the pull request opens instead of at `apply`.

By default, `plan` answers one question: does `apply` accept this file?

| Code | Meaning |
| --- | --- |
| `0` | `apply` accepts the file. There can be changes. |
| `1` | The file does not exist or is not valid. |
| `2` | The plan has problems. `apply` refuses the file. |

A plan with changes and no problems exits `0`, so a pipeline that runs `plan` and then `apply`
keeps working.

With `--detailed-exitcode`, the code also says whether there is anything to apply. This is the
Terraform convention. Problems win over changes, because a plan with both cannot be applied:

| Code | Meaning |
| --- | --- |
| `0` | No changes and no problems. |
| `1` | The file does not exist or is not valid. |
| `2` | Changes, and no problems. |
| `3` | The plan has problems. `apply` refuses the file. |

In both tables, any other code is one of the CLI's general exit codes and means that `plan` could
not ask: for example `4` when you are not signed in, and `11` when the control plane cannot be
reached. A pipeline that treats every code other than `0` and `2` as a failure handles all of
them.

`alethia apply` exits `2` when it refuses a file for its problems.

`plan` prints the whole plan first in every case, on stdout. The code comes last. The refusal goes
to stderr in every format, so stdout carries only the plan. With `--output json`, the refusal is one
JSON object with the code `plan_refused`. The plan has no table shape, so `--output csv` prints no
rows for it; read the plan with `--output json`.

`alethia apply` sends the refusal to stderr in the same way.

### Problems in `--output json`

Each environment in `environments` lists its problems in `problems`, one sentence each. An
environment without problems has no `problems` key. This is a plan with one problem; the `manifest`
key, which repeats the file as read, is left out:

```json
{
  "project_id": "4b1d2c9e-7f3a-4e55-9c1d-2a6f0b8e1c37",
  "environments": [
    {
      "name": "production",
      "stage": "staging",
      "placement": "dedicated",
      "action": "unchanged",
      "id": "9e2f4a10-3c6b-4d8e-a1f7-5b0c6d2e8f94",
      "components": null,
      "problems": [
        "the file says stage staging, the server has production — a stage cannot be changed from here; edit it in the console or the file"
      ],
      "deploy": true
    }
  ]
}
```

A script can list every problem with `jq`:

```bash
alethia plan --output json | jq -r '.environments[] | .name as $env | .problems[]? | "\($env): \(.)"'
```

### Run `plan` on every pull request

This GitHub Actions job fails a pull request when `alethia.yaml` cannot be applied. `plan` reads
the add-on values files the manifest names, so list their directory under `paths` too (here
`values/`); otherwise a pull request that changes only a values file skips the check. It passes when
the file has changes that `apply` accepts. It signs in with a service token in the `ALETHIA_TOKEN`
secret; `alethia token create --name ci | gh secret set ALETHIA_TOKEN` makes one:

```yaml
name: alethia plan
on:
  pull_request:
    paths:
      - alethia.yaml
      - values/**   # the add-on values files alethia.yaml names, if it names any
jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install the Alethia CLI
        run: |
          curl -fsSL https://get.alethialabs.io | sh
          echo "$HOME/.local/bin" >> "$GITHUB_PATH"
      - name: Plan
        env:
          ALETHIA_TOKEN: ${{ secrets.ALETHIA_TOKEN }}
        run: alethia plan --no-input
```

To also see whether the file differs from the server, use `--detailed-exitcode` and read the code
yourself. `0` means the file matches what the server has. It does not mean `apply` does nothing:
`apply` deploys every environment again, even when nothing differs. A step stops on the first
non-zero code, so capture it:

```bash
set +e
alethia plan --no-input --detailed-exitcode
code=$?
set -e
case "$code" in
  0) echo "the file matches the server" ;;
  2) echo "the file differs from the server" ;;
  *) exit "$code" ;;   # 3 problems; anything else is an error
esac
```

## Start from an existing project

A project that you built in the console has no `alethia.yaml` yet.
[`alethia export`](/reference/cli/configuration#alethia-export) writes one from what the project has
now, so you can manage the project from git from that point on.

<Steps>
<Step>

Write the file. This example takes every environment of the project; you can also export one of
them.

```bash
alethia export shop --all --out alethia.yaml
```

</Step>
<Step>

Plan it. The file describes what the project already has, so there is nothing to do:

```bash
alethia plan
```

```
▸ Reading alethia.yaml · shop · aws/eu-west-1
  prod     dedicated  = environment  = cluster  = databases/orders
    add-ons  = cert-manager  = external-dns
  staging  namespace  = environment  = databases/orders
  0 projects to create · 0 environments · 0 components
```

</Step>
<Step>

Commit `alethia.yaml`. From now on, edit the file and run `alethia apply` — in a pipeline,
`alethia apply --yes --no-input`.

</Step>
</Steps>

`export` writes only the values that Alethia publishes as plain, non-secret settings, so a secret
that Alethia stores is never written. It cannot recognize a password typed into an ordinary
setting, so review the file before you commit it. See
[What is written, and what is left out](/reference/cli/configuration#what-is-written-and-what-is-left-out). The comment at its top lists what `export` left out, such as an
add-on's Advanced values override, and why. A value that is not in the file keeps what is stored,
so `plan` shows no change for it and `apply` never clears it.

## One environment at a time

`plan` and `apply` work on the whole file. To queue one job for one environment, use the `project`
commands. They are described on the [project page](/reference/cli/project):

- `alethia project preview` queues the OpenTofu plan of one environment.
- `alethia project deploy` deploys one environment from a reviewed plan: the one you name, or a
  preview it makes and shows you first.
- `alethia project destroy` tears one environment down.

## `alethia project destroy`

Queue a DESTROY job for one environment. The Runner runs `tofu destroy` and tears down every
resource of that environment; the console guide's
[destroy workflow](/guides/jobs/plan-and-apply#destroy-an-environment) says what is kept and what is lost.
`alethia apply` never does this: removing an environment from `alethia.yaml` leaves it running.

```bash
alethia project destroy --project boutique --env dev-1                   # asks you to type the project's name
alethia project destroy --project boutique --env prod --cascade --wait   # prod and every environment on its cluster
```

The flags, the confirmation and the result are on the
[project page](/reference/cli/project).

A destroy from the CLI needs a person's approval too, given against a **destroy plan**: a plan of
the teardown that deletes nothing itself. The destroy then tears down exactly that plan. To read the
teardown before you destroy, make the destroy plan first and destroy that plan:

```bash
alethia project preview --project boutique --env dev-1 --destroy --wait
alethia project destroy --project boutique --env dev-1 --latest-plan
```

Without `--latest-plan` or `--plan-job-id`, the destroy makes the destroy plan itself when the
approval is needed, waits for it and prints what it would delete. The approval is asked for, shown
and waited for the same way as a deploy's (see
[When a deploy needs a person's approval](#when-a-deploy-needs-a-persons-approval)). With
`--no-wait` the command exits `9` with the page, and the error names the command that destroys
exactly that plan once it is approved. A `--cascade` destroy cannot be approved this way: start it
from the console.

### Destroying an environment that other environments run on

A `dedicated` environment owns its cluster. `namespace` and `vcluster` environments placed on that
cluster run inside it, and their own teardown needs the cluster to still exist. So while any of them
is live, destroying the `dedicated` environment is **refused**, and the error names each one:

```text
Environment "prod" owns the cluster that 2 other environments are still placed on:
dev-1 (namespace, ACTIVE), staging (vcluster, FAILED). ...
Re-run with --cascade to see every environment it would destroy and confirm
```

An environment that was never applied (`DRAFT`) or is already `DESTROYED` does not count. Destroying
a `namespace` or `vcluster` environment is never refused for this reason.

Either destroy the listed environments first, or pass `--cascade`. It prints what it will destroy,
then asks:

```text
Will destroy, in order: dev-1 (namespace), staging (vcluster, failed), prod (dedicated, owns the cluster)
```

The order is enforced by the Console, not by timing: the DESTROY of `prod` stays `QUEUED`, and no
Runner can start it, until no live environment is left on its cluster. If the destroy of `dev-1` or
`staging` fails, `prod` keeps waiting. `--wait` stops at the failed job and names the two ways out:
destroy the failed environment again, or cancel the waiting job with
[`alethia jobs cancel`](/reference/cli/jobs).

<Callout type="info">
To tear down a deployed **Runner** (not a Project), use [`alethia runner destroy`](/reference/cli/runners).
</Callout>

## Scripting Examples

```bash
# From nothing to a running project, unattended
alethia up --project boutique --region nbg1 --cloud-account prod-account --yes --no-input

# The whole project from its file, unattended
alethia apply --yes --no-input

# Plan one environment, review, apply that exact plan. No id moves between the commands.
# --latest is resolved over the whole org, so narrow the review step to this project and job type.
alethia project preview --project boutique --env prod --runner eu-box --wait
alethia jobs get --latest --project boutique --type PLAN
alethia project deploy --project boutique --env prod --latest-plan --wait --yes

# Read the teardown, then destroy exactly that plan
alethia project preview --project boutique --env prod --destroy --wait
alethia project destroy --project boutique --env prod --latest-plan --wait
```
