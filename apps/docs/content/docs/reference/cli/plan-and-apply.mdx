# Plan & Apply

One file describes a project; two commands take it from a file to a running cluster. Nothing has
to be copied out of another command's output: the cloud account is named by its **label**, the
runner by its **name**, and every environment by the name the file gives it.

## `alethia.yaml`

The manifest is the whole shape of a project — where it provisions, every environment with its
placement, and the components each environment carries:

```yaml
project: boutique
cloud:
  account: prod-account        # the connector's label, as `alethia connector list` shows it
  region: nbg1
environments:
  - name: prod
    stage: production
    placement: dedicated       # owns the Fabric: this is the environment with a cluster
    components:
      cluster:
        node_min_size: 2
        node_max_size: 3
  - name: dev-1
    stage: development
    placement: namespace       # placed onto prod's Fabric, no new cluster
    namespace: boutique-dev-1
    components:
      repositories:
        apps_destination_repo: https://github.com/alethialabs-io/alethia-examples
        apps_path: examples/online-boutique/overlays/dev-1
      databases:
        - name: orders
          engine: postgres
```

| Key | What it is |
| --- | --- |
| `project` | The project's name. Unique in the organization, so `apply` finds an existing project by it. |
| `cloud.account` | The cloud account's label (or its id). Omit it to create an unlinked project. |
| `cloud.region` | The region to provision into. |
| `iac.version` | OpenTofu version to pin. Optional; the server defaults it. |
| `environments[].name` | The environment's name. |
| `environments[].stage` | `development`, `staging` or `production`. |
| `environments[].placement` | `dedicated`, `vcluster` or `namespace`. Optional: the **first** environment defaults to `dedicated` and owns the Fabric; every later one defaults to `namespace` and shares it. |
| `environments[].namespace` | The destination namespace for a shared placement. Optional; derived from the name. Ignored on `dedicated`. |
| `environments[].lifecycle` | `persistent` (default) or `ephemeral`. |
| `environments[].addons` | The catalog add-ons the environment runs, as a list of `{ id, version, mode, settings, values, values_file }`. See [Add-ons](#add-ons). |
| `environments[].components` | The environment's resources, keyed by kind. A one-per-environment kind (`cluster`, `network`, `dns`, `observability`, `repositories`) is written as its fields; a named kind (`databases`, `caches`, `queues`, …) as a list of entries, each with a `name`. `alethia project component kinds` lists them and the fields each takes. |

A misspelt key, a stage outside the allowed set, a component kind the server does not publish or a
field a kind does not take is refused **before anything is sent**, naming every problem at once.
The CLI only ever refuses what the server would certainly refuse: anything else is passed through
for the server to decide.

<Callout type="warn">
  Placement is the key with a bill attached. Each `dedicated` environment is a separate cluster with
  its own OpenTofu state; `namespace` and `vcluster` share the Fabric that already exists. The
  example above is **one** cluster hosting two environments.
</Callout>

## `alethia apply`

Create whatever the file declares that does not exist yet, show the plan, and deploy every
environment.

```bash
alethia apply                          # ./alethia.yaml, asks before applying
alethia apply --yes --no-input         # in a pipeline
alethia apply --runner my-box          # deploy with a named runner
alethia apply --env dev-1              # create everything, deploy only dev-1
```

```
▸ Reading alethia.yaml · boutique · hetzner/nbg1
  + project boutique
  prod   dedicated  + environment  + cluster
  dev-1  namespace  + environment  + repositories  + databases/orders
  1 project to create · 2 environments · 3 components
Apply these changes? Yes
  ✓ created project boutique
  ✓ added cluster in prod
  ✓ added repositories in dev-1
  ✓ added databases/orders in dev-1
▸ Deploying prod (job 4f3c2b1a-…)
  ✓ Job completed successfully
▸ Deploying dev-1 (job 8a1d0e77-…)
  ✓ Job completed successfully

✓ boutique is up.
```

`apply` is idempotent. Re-run it on a project that already matches the file and it creates
nothing, marks each environment `=`, and deploys again. It **never deletes**: an environment on the
server that the file does not mention is listed as left alone, not torn down. What it cannot
reconcile — an existing environment whose stage or placement differs from the file — is shown and
refused before a single write.

### Changing a component

Edit a field of a component that already exists, and `plan` and `apply` show the change and make
it. Each row starts with a mark:

| Mark | Meaning |
| --- | --- |
| `+` | It does not exist yet. `apply` creates it. |
| `~` | It exists, and at least one field the file declares has a different value on the server. `apply` changes those fields. |
| `=` | It exists, and every field the file declares already matches. `apply` sends nothing for it. |

Under each `~` row, one line names each changed field with the server's value and the file's value.
Here the file raises `max_capacity` of the `orders` database in `prod` from `4` to `8`:

```
▸ Reading alethia.yaml · boutique · hetzner/nbg1
  prod   dedicated  = environment  = cluster  ~ databases/orders
    ~ databases/orders  max_capacity: 4 → 8
  dev-1  namespace  = environment  = repositories
  0 projects to create · 0 environments · 0 components · 1 component to update
```

`(unset)` means the server has no value for that field.

- **A field you leave out is never cleared.** `apply` compares only the fields the file names, and
  sends only the ones that changed. This is true for every kind: a named component such as a
  database, and a one-per-environment kind such as `cluster`. To change one field of a database,
  write that field; the other fields keep their values.
- **A `cloud_identity_id` must be one you can use.** It must name a cloud account of your
  organization, or your own personal one. Any other id is refused as `Cloud identity not found`.
- **Values compare by meaning.** `2` and `2.0` are the same number. Lists and maps compare item by
  item, and the order of a list counts.
- **A refused change does not stop the others.** If the server refuses a change, `apply` reports it
  for that component, does not deploy that environment, and continues with the other environments.
  Then it exits with an error that names each refused component.

### Setting and removing a `provider_config` key

A component's `provider_config` holds its template knobs, the same ones the console's **Advanced**
section sets. `plan` and `apply` treat it **key by key**, not as one value:

```yaml
      databases:
        - name: orders
          engine: postgres
          provider_config:
            rds_backup_retention_period: 14   # set this key
            rds_performance_insights: null    # remove this key
```

- A key you write is set to the file's value.
- A key you write as `null` is removed. `plan` shows it as a change only while the server still
  holds the key, so the removal shows once and then settles.
- A key you do not write is kept, and shows no change. A key set in the console stays set.
- `provider_config` itself must be a mapping. A whole `provider_config: null`, or an empty
  `provider_config:`, is refused before anything is sent, because the server refuses it. To remove
  every key, write each one as `null`.

`apply` sends only the keys that changed. The keys a component accepts depend on its cloud;
[Setting template knobs](/reference/cli/project#setting-template-knobs) explains how to find them.

`apply` changes the component's **settings**. It does not tell you whether the next deploy replaces
the cloud resource. To see that, read the OpenTofu plan of the deploy: `alethia project plan`.

The runner: `--runner` takes a name or an id. Omitted, the only online runner is used without a
question; with several online you are asked on a terminal, and under `--no-input` the job is left
for the server to place.

{/* fieldspec: alethia apply */}

| Field        | What it is                                                                                    | Set without the form |
| ------------ | --------------------------------------------------------------------------------------------- | -------------------- |
| Manifest     | The alethia.yaml to apply (default: ./alethia.yaml)                                           | `--file`             |
| Runner       | Runner to deploy with, by NAME or id. Omitted: the only online runner, or asked on a terminal | `--runner`           |
| Environments | Only deploy these environments (repeatable; default: every environment in the file)           | `--env`              |
| Confirm      | Apply without asking (required with --no-input)                                               | `--yes`              |
| Wait         | Queue the deploys and return instead of waiting for them                                      | `--no-wait`          |

`--output json` prints the plan and the result as typed objects instead of the lines above. In the
plan, a component with the action `update` carries a `changes` array, one entry per changed field:

```json
{
  "kind": "databases",
  "name": "orders",
  "action": "update",
  "fields": { "engine": "postgres", "max_capacity": 8 },
  "changes": [{ "field": "max_capacity", "from": 4, "to": 8 }]
}
```

`from` is `null` when the server has no value for the field. A `create` or `unchanged` component has
no `changes` key. In the result, an `errors` array lists each change the server refused, as
`{ "environment", "component", "error" }`.

## Add-ons

An environment can declare the [catalog add-ons](/reference/cli/addons) it runs. `plan` shows what
would change, and `apply` makes it so. This file declares two environments. `staging` runs
external-dns pinned to chart version `1.14.5` with two settings, and kube-prometheus-stack with a
Helm values file. `prod` runs loki at the catalog's default version:

```yaml
project: boutique
cloud:
  account: prod-account
  region: nbg1
environments:
  - name: prod
    stage: production
    placement: dedicated
    addons:
      - id: loki                         # no version: the catalog's default version
        settings:
          retentionDays: 30
  - name: staging
    stage: staging
    placement: namespace
    namespace: boutique-staging
    addons:
      - id: external-dns
        version: 1.14.5                  # pin the chart version
        settings:
          provider: cloudflare
          domainFilter: staging.boutique.example.com
      - id: kube-prometheus-stack
        settings:
          retentionDays: 7
        values_file: helm/kps-staging.yaml   # relative to alethia.yaml
```

`helm/kps-staging.yaml` is an ordinary Helm values file, next to `alethia.yaml` in the repository:

```yaml
grafana:
  replicas: 2
prometheus:
  prometheusSpec:
    resources:
      requests:
        memory: 2Gi
```

| Key | What it is |
| --- | --- |
| `id` | The add-on's catalog id. Required. An id the catalog does not have is refused, and the refusal lists the ids it does have. |
| `version` | A chart-version pin: one exact version, such as `1.14.5`. A range such as `^1.14` is refused. |
| `mode` | `managed` or `gitops`. Omitted on a new add-on, `managed`. |
| `settings` | The add-on's settings, by name: the same keys `alethia addon enable` sets. A key the add-on does not have is refused, and the refusal lists the keys it does have. |
| `values` | An Advanced Helm-values override, written inline as a mapping. |
| `values_file` | The same override, read from a file. The path is relative to `alethia.yaml` and must stay inside its directory: an absolute path, a `..` out of it, or a symlink that leads out of it is refused. Use `values` or `values_file`, not both. |

### Keep and clear

Each key means what the same flag of [`alethia addon enable`](/reference/cli/addons) means, because
`apply` sends the same request:

| You write | `apply` does |
| --- | --- |
| nothing for a key | keeps what is stored: the pin, the mode, each setting, the override |
| `version: 1.14.5` | pins the chart version |
| `version: ""` or `version: null` | removes the pin, so the catalog's default version applies |
| `settings: { key: value }` | sets that one setting and keeps the others |
| `settings: { key: null }` | resets that setting to the add-on's default |
| `values` or `values_file: path` | replaces the whole stored override |
| `values_file: ""` or `values: null` | removes the override |

### What `plan` shows

Add-ons get one line per environment, with the same marks as components. Under it, one line names
each changed field. Here staging's external-dns runs the catalog's default version and an older
domain filter, kube-prometheus-stack's values file changed, and reloader in `prod` is enabled on
the server but not in the file:

```
▸ Reading alethia.yaml · boutique · hetzner/nbg1
  prod     dedicated  = environment
    add-ons  = loki
    add-on reloader is enabled on the server and not in the file — left alone (unmanaged)
  staging  namespace  = environment
    add-ons  ~ external-dns  ~ kube-prometheus-stack
    ~ external-dns  settings.domainFilter: boutique.example.com → staging.boutique.example.com
    ~ external-dns  version: (catalog default) → 1.14.5
    ~ kube-prometheus-stack  values: sha256:4be1a07c93d2 (4 lines) → sha256:0f6e2d81c5aa (6 lines)
  0 projects to create · 0 environments · 0 components · 0 add-ons to enable · 2 to change
```

**A plan never shows what an override says.** A values file can be any file in the repository,
and a plan is printed into CI logs, so the `values` line names each side by a digest of its content
and its length. Two files that describe the same mapping have the same digest. `apply` still sends
the whole file.

`(default)` means a setting is reset to its default. `(none)` means there is no override. A setting
you reset with `null` shows as a change only while the server holds a value other than the default,
so the reset shows once and then settles.

`--output json` puts the add-ons on each environment as `addons`, each with an `id`, an `action`
and, for an `update`, the same `changes` array components carry. A change to one setting has the
setting's name in `key`. Add-ons that are on the server but not in the file are in
`unmanaged_addons`.

### What `apply` never does

- **It never disables an add-on.** An add-on that is enabled on the server and not in the file is
  listed as unmanaged and keeps running. Disable one with
  [`alethia addon disable`](/reference/cli/addons).
- **It never takes a secret from the file.** `alethia.yaml` is committed to git, so a secret setting
  in it is refused before anything is sent. The refusal names the setting. Set a secret with
  `alethia addon enable <id> --set <key>=…` or in the console. `apply` keeps a stored secret as it
  is, and `plan` never prints a secret's value.

<Callout type="info">
  **A secret for an environment that `apply` creates.** The file cannot carry a secret, and
  `alethia addon enable --env <name>` needs the environment to exist. So the first `apply` installs
  the add-on without it: external-dns on a token provider such as Cloudflare comes up and cannot
  write DNS records yet. Set the token once the environment exists, here from an environment
  variable so it stays out of your shell history, and deploy again:

  ```bash
  alethia apply --yes
  alethia addon enable external-dns --project boutique --env staging --set apiToken="$CLOUDFLARE_API_TOKEN"
  alethia apply --yes
  ```

  The second `apply` leaves the token as it is. On a workload-identity provider (`aws`, `google`,
  `azure`) there is no token: set `workloadIdentity` under `settings` in the file, because it is an
  identifier and not a secret.
</Callout>

`apply` enables add-ons after it creates components and before it deploys. If the server refuses an
add-on, `apply` reports it, does not deploy that environment, and continues with the others.

## `alethia up`

The whole first run in one command: sign in, attach nothing (see below), write the manifest, apply
it. Every step is skipped when it is already done, so it resumes wherever the last run stopped.

```bash
alethia up                                  # asks for what it needs
alethia up --project boutique --region nbg1 --cloud-account prod-account --yes --no-input
```

| Step | Skipped when |
| --- | --- |
| the control-plane URL and the login | this machine has a live credential |
| a cloud account | one is connected — **otherwise `up` stops**, see below |
| `alethia.yaml` | this directory has one |
| the apply | never; that is the point |

With the manifest already present and an account connected, `alethia up` **is** `alethia apply`.

<Callout type="info">
  `up` cannot attach a cloud account for you. Each cloud has its own keyless flow with its own
  arguments — `alethia connector aws|gcp|azure|alibaba|hetzner` — so `up` stops and names them
  rather than growing a sixth version that would drift from the five.
</Callout>

{/* fieldspec: alethia up */}

| Field         | What it is                                                                                       | Set without the form |
| ------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| Manifest      | The alethia.yaml to apply, written when it does not exist yet                                    | `--file`             |
| Project name  | Name for a project this authors (asked for on a terminal when the file is missing)               | `--project`          |
| Region        | Cloud region for a project this authors                                                          | `--region`           |
| Cloud account | Cloud account to link, by its LABEL or its id                                                    | `--cloud-account`    |
| Stage         | Stage for the environment this authors                                                           | `--stage`            |
| Machine type  | Machine type for the cluster nodes, e.g. t3.xlarge (needs a cloud account; not with --node-size) | `--instance-type`    |
| Node size     | Node size as vCPUxGiB, e.g. 4x16, mapped to the nearest machine type (not with --instance-type)  | `--node-size`        |
| Runner        | Runner to deploy with, by NAME or id. Omitted: the only online runner, or asked on a terminal    | `--runner`           |
| Confirm       | Apply without asking (required with --no-input)                                                  | `--yes`              |
| Wait          | Queue the deploys and return instead of waiting for them                                         | `--no-wait`          |

Scripted, `up` writes a single environment at `--stage`; on a terminal it asks for the whole matrix.
[`alethia project env add`](/reference/cli/project) is how a second environment arrives later.

`--instance-type` and `--node-size` choose the cluster's node shape. `up` writes it into the file
as a `cluster` component on each `dedicated` environment, so the file shows it and `apply` creates
the cluster with it. Without either flag the file has no `cluster` component, and the cluster gets
the catalog's default machine type for its cloud. The two flags are mutually exclusive.

## `alethia plan`

The same comparison, with the writes left out: what `apply` would create, what it would change
(field by field, as in [Changing a component](#changing-a-component)), what already matches, and
anything it would refuse. Nothing is written and no job is queued.

```bash
alethia plan
alethia plan --file staging.yaml --output json
```

{/* fieldspec: alethia plan */}

| Field    | What it is                                         | Set without the form |
| -------- | -------------------------------------------------- | -------------------- |
| Manifest | The alethia.yaml to plan (default: ./alethia.yaml) | `--file`             |

The per-environment OpenTofu plan runs inside every deploy. To queue one on its own — for a
pipeline that gates on it — use `alethia project plan` below.

## The `project` job commands

These `project` subcommands queue infrastructure operations that [Runners](/concepts/runner) execute. They
implement the Plan-Review-Apply workflow from the terminal, one environment at a time. The same
workflow in the console is [Plan and apply in the console](/guides/jobs/plan-and-apply).

## `alethia project plan`

Queue an [OpenTofu](/reference/glossary) plan job — the Runner runs `tofu plan`.

```bash
alethia project plan                                                        # asks which project, then which runner
alethia project plan --project boutique --env prod --runner eu-box --wait   # scripted: names all three, blocks on the job
```

| Flag | Required | Description |
|------|----------|-------------|
| `--project` | No | Project to plan, by **name** or id. Omitted on a terminal, a picker asks. |
| `--project-id` | No | Project id. Prefer `--project`, which also takes the id. Passing both is refused. |
| `--env` | No | Environment name to plan. Omitted, the project's default environment. |
| `--runner` | No | Runner to execute the job, by **name** or id. Omitted, a picker asks on a terminal; under `--no-input` the server places the job. |
| `--runner-id` | No | Runner id. Prefer `--runner`, which also takes the name. Passing both is refused. |
| `-w`, `--wait` | No | Block until the job completes |

On success, prints the job ID. Stream the plan output with
`alethia jobs logs --latest --project boutique --follow` — nothing has to be copied between the two
commands. Narrow it to the project you just planned: an unnarrowed `alethia jobs logs --latest`
takes the most recent job **the organization** has, which may be somebody else's.

## `alethia project apply`

Queue a deployment (apply) job.

```bash
alethia project apply                                                      # asks which project, then which runner
alethia project apply --project boutique --env prod --latest-plan --wait   # scripted: applies the plan just reviewed
```

| Flag | Required | Description |
|------|----------|-------------|
| `--project` | No | Project to deploy, by **name** or id. Omitted on a terminal, a picker asks. |
| `--project-id` | No | Project id. Prefer `--project`, which also takes the id. Passing both is refused. |
| `--env` | No | Environment name to deploy. Omitted, the project's default environment. |
| `--runner` | No | Runner to execute the job, by **name** or id. Omitted, a picker asks on a terminal; under `--no-input` the server places the job. |
| `--runner-id` | No | Runner id. Prefer `--runner`, which also takes the name. Passing both is refused. |
| `--latest-plan` | No | Apply the project's most recent `PLAN` job. Prefer this to `--plan-job-id`. |
| `--plan-job-id` | No | Bind the apply to the plan a prior PLAN job produced, by that job's id. |
| `-w`, `--wait` | No | Block until the job completes |

Either flag makes the apply use the exact plan you reviewed. If the project's configuration
changed since that plan was generated, the job fails with a
[config hash mismatch](/guides/jobs/plan-and-apply#config-hash-validation).

`--latest-plan` resolves that plan from the project itself, so no id moves between two commands:
plan, review, then apply. It prints the job it chose before it queues anything. It resolves `PLAN`
jobs only — the project's most recent job is as likely to be the `DEPLOY` that followed the plan —
and it needs `--project`, because without one the match is every `PLAN` job in the organization.

It takes the most recent `PLAN` **whatever its status** and refuses when that is not `SUCCESS`,
naming the job and its status. Skipping past a plan that is still running would apply an older one
you never asked for, which is the reviewed-plan guarantee inverted.

`--plan-job-id` stays for a plan you already hold the id of. Passing both is refused rather than
resolved by precedence: they name the same thing.

**Narrow any `alethia jobs get --latest` you read the plan back with.** That command resolves over
every job the organization has, not over the ones you queued, so an unnarrowed lookup can show you
another project's plan. Write it as
`alethia jobs get --latest --project boutique --type PLAN`, as
[Scripting Examples](#scripting-examples) does.

A DEPLOY job runs the fail-closed [verify gate](/guides/jobs/plan-and-apply#verify-gate) before
`tofu apply`. Follow it with `alethia jobs logs --latest --project boutique --type DEPLOY --follow`.

## `alethia project destroy`

Destroy a Project's provisioned infrastructure.

```bash
alethia project destroy                                                  # asks which project, then confirms
alethia project destroy --project boutique --env prod --wait --yes       # scripted: no confirmation prompt
alethia project destroy --project boutique --env prod --cascade --wait   # prod and every environment on its cluster
```

| Flag | Required | Description |
|------|----------|-------------|
| `--project` | No | Project to destroy, by **name** or id. Omitted on a terminal, a picker asks. |
| `--project-id` | No | Project id. Prefer `--project`, which also takes the id. Passing both is refused. |
| `--env` | No | Environment name to destroy. Omitted, the project's default environment. |
| `--runner-id` | No | Runner to execute the job, **by id only** — `destroy` has no `--runner` sibling yet. Omitted, a picker asks on a terminal; under `--no-input` the server places the job. |
| `-y`, `--yes` | No | Skip the confirmation prompt. Required with `--no-input`. |
| `--cascade` | No | Also destroy every environment placed on this environment's cluster, those environments first. Prints the full list, in order, and confirms before it queues anything. |
| `-w`, `--wait` | No | Block until the job completes. With `--cascade`, until every job completes. |

Queues a DESTROY job. The Runner runs `tofu destroy` to tear down all resources — see the console
guide's [destroy workflow](/guides/jobs/plan-and-apply#destroy-workflow) for what is kept and what is lost.

### Destroying an environment that other environments run on

A `dedicated` environment owns its cluster. `namespace` and `vcluster` environments placed on that
cluster run inside it, and their own teardown needs the cluster to still exist. So while any of them
is live, destroying the `dedicated` environment is **refused**, and the error names each one:

```text
Environment "prod" owns the cluster that 2 other environments are still placed on:
dev-1 (namespace, ACTIVE), staging (vcluster, FAILED). ...
Re-run with --cascade to see every environment it would destroy and confirm
```

An environment that was never applied (`DRAFT`) or is already `DESTROYED` does not count. Destroying
a `namespace` or `vcluster` environment is never refused for this reason.

Either destroy the listed environments first, or pass `--cascade`. It prints what it will destroy,
then asks:

```text
Will destroy, in order: dev-1 (namespace), staging (vcluster, failed), prod (dedicated, owns the cluster)
```

The order is enforced by the Console, not by timing: the DESTROY of `prod` stays `QUEUED`, and no
Runner can start it, until no live environment is left on its cluster. If the destroy of `dev-1` or
`staging` fails, `prod` keeps waiting. `--wait` stops at the failed job and names the two ways out:
destroy the failed environment again, or cancel the waiting job with
[`alethia jobs cancel`](/reference/cli/jobs).

`--project` and `--project-id` name the same field, so passing both is an error rather than a
precedence rule. The command they are being passed to is `destroy`: quietly preferring one of them
would let a wrong belief about which project is being torn down survive until it had been.

`plan` and `apply` take the runner by **name** as well, through `--runner`. `destroy` does not, for
now — it takes `--runner-id` alone, so this is the one place in the three commands where a runner
still has to be named by id. Read it out of `alethia runner list`, or leave it unset and choose from
the picker.

<Callout type="info">
To tear down a deployed **Runner** (not a Project), use [`alethia runner destroy`](/reference/cli/runners).
</Callout>

## Interactive Selection

`plan`, `apply` and `destroy` each ask for what you did not name, so none of the three needs an id
typed at it:

1. With neither `--project` nor `--project-id`, a picker lists the projects and you choose one.
2. With the runner unnamed, a second picker lists your runners, marking each one online, draining or
   offline. **Any available** is its first option, so pressing Enter leaves the job for the server
   to place.

Neither picker is shown under `--no-input` or when stdin is not a terminal. There, name the project
with `--project` and the runner with `--runner` — both take the name, so a script never has to hold
an id — or leave the runner unset for the server to place. A name no runner has is refused locally,
listing the names that do exist; a name two runners share is refused naming both ids, rather than
picking one for you.

See [TUI Components](https://github.com/alethialabs-io/alethialabs/blob/dev/docs/contributing/cli-tui.md) for details on the interactive selectors.

## Scripting Examples

```bash
# From nothing to a running project, unattended
alethia up --project boutique --region nbg1 --cloud-account prod-account --yes --no-input

# The whole project from its file, unattended
alethia apply --yes --no-input

# Plan one environment, review, apply that exact plan. No id moves between the commands.
# --latest is resolved over the whole org, so narrow the review step to this project and job type.
alethia project plan --project boutique --env prod --runner eu-box --wait
alethia jobs get --latest --project boutique --type PLAN
alethia project apply --project boutique --env prod --latest-plan --wait

# Destroy with wait
alethia project destroy --project boutique --env prod --wait
```
