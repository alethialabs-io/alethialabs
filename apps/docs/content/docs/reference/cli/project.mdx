# Project Commands

Projects are infrastructure configurations (an *app* that owns one or more environments). The CLI
can both **read** projects (`list`, `get`) and **author** them — create a project, manage its
environments, and CRUD its component resources — so the whole project lifecycle is scriptable.

All authoring commands operate on the **active organization** (set via `alethia org switch`), or on
the organization named by the global `--org <id>` for a single invocation — which is refused with
`403` if you are not a member of it. Every command accepts the global
`-o, --output <table|json|csv>` flag.

## Two rules that hold for every command on this page

**Nothing has to be copied out of another command's output.** Every reference takes the name you
already know: `--project` takes a project's name *or* its id, `--cloud-account` takes a cloud
account's label *or* its id, and `--env` takes an environment's name, stage or id. Omit one on a
terminal and you are asked, from a picker of what actually exists.

**Every question has a flag.** The interactive paths below exist so you do not have to assemble
anything by hand — they never let you say something a flag cannot. After a run that asked you
questions, the CLI prints the exact command that reproduces it, so what you answered once can be
committed to a repository:

```
Same result, without the questions:
  alethia project create boutique --region eu-west-1 --cloud-account prod-account
```

The one thing a flag cannot say is a list of environments, so a run that declared an environment
matrix through the form prints back the `alethia.yaml` its answers add up to — the file
[`alethia apply`](/reference/cli/plan-and-apply) reads. So `--no-input` always works, and so does a
pipe.

## `alethia project list`

List all projects in the active organization.

```bash
alethia project list
alethia project list --output json
```

On a terminal this is the shared navigable table (sort, filter, quit); piped or with
`--output json|csv` it is a plain projection.

| Column | Description |
|------|----------|
| Project | Project name |
| Env | The default environment's stage |
| Status | Provisioning status |
| Provider | Cloud provider |
| Region | Cloud region |
| Cost | Estimated monthly cost |
| Updated | Last change |

**Status**, **Provider**, **Region** and **Cost** are rendered for a person: the status carries a
glyph and is folded to lower case, the provider is upper-cased, an unset provider or region is `—`,
and a project the wire sent no status for reads as `draft` — an inference that tells a reader the
project has not been applied yet, rather than leaving a blank that looks like a broken table.

Under `-o csv` a script gets the values instead: each is the wire value, and each is an **empty
cell when the wire sent nothing** — including the status, because handing a script a status the
server never sent is the one thing a machine format must not do. **Cost** is a bare number and
**Updated** an RFC3339 stamp.

## `alethia project get`

Print a project's full configuration.

```bash
alethia project get boutique
alethia project get boutique --open
alethia project get                      # asks which project
```

| Argument / Flag | Required | Description |
|------|----------|-------------|
| `[project_name]` | No | Project name (positional). Omit it on a terminal to pick from a list. |
| `--open` | No | Open the project in the web console. (Long-only — `-o` is the global `--output` flag.) |

<Callout type="info">
  `get` looks a project up by **name**, so the picker returns a name and refuses one that two
  projects share — that lookup answers a duplicate with whichever project is older, and quietly
  printing another project's region, cluster endpoint and apps repo is worse than an error. Every
  other command takes `--project`, which resolves a name **or** an id.
</Callout>

Shows the full project configuration including:
- Project name, provider, region, environment
- Status and estimated monthly cost
- Component summary (network, cluster, databases, caches, etc.)
- Cloud identity reference

When run interactively without `--open`, the CLI offers to open the project in the browser after
printing it.

## `alethia project create`

Create a new project in the active organization.

```bash
alethia project create                   # asks for everything, prints the file back
```

or say it all at once:

```bash
alethia project create boutique --region eu-west-1 --cloud-account prod-account
```

or from the manifest in the current directory, which also declares the environment matrix:

```bash
alethia project create --file alethia.yaml
```

The file in the current directory is read even when `--file` is not passed, and the command prints
the line naming it. A script that must not be steered by whatever `alethia.yaml` happens to be in
the tree passes `--no-manifest`.

| Argument / Flag | Required | Description |
|------|----------|-------------|
| `[name]` | Yes* | Project name (positional). *Asked for on a terminal when omitted. |
| `--region` | Yes* | Cloud region to provision into. *Asked for on a terminal when omitted. |
| `--cloud-account` | No | Cloud account to link, by its **label** or its id. Asked for on a terminal when omitted; a project may be created with none. |
| `--stage` | No | Initial environment stage: `development` (default), `staging`, `production` |
| `--iac-version` | No | OpenTofu version to pin (defaults server-side) |
| `--placement-mode` | No | Placement of the default environment: `namespace`, `vcluster`, `dedicated` (default `dedicated`) |
| `--instance-type` | No | Machine type for the cluster nodes, for example `t3.xlarge`. Needs `--cloud-account`, because a machine type belongs to one cloud. Not with `--node-size`. |
| `--node-size` | No | Node size as vCPU and GiB, for example `4x16`. It is mapped to the nearest machine type of the project's cloud when the cluster deploys. Not with `--instance-type`. |
| `--file` | No | `alethia.yaml` to take the values and the environment matrix from. The file in the current directory is read when present, and the command says so. |
| `--no-manifest` | No | Read no manifest, not even the one in this directory. Refused together with `--file`. |

Every value resolves in one order — the flag, then `ALETHIA_REGION` and the other environment
variables, then the manifest, then the form, then the default — so a checked-in file supplies what
the command line leaves out, and a flag overrides the file for one run.

### Node shape

Without `--instance-type` or `--node-size`, the project's cluster gets the catalog's default machine
type for its cloud: `t3.large` on AWS, `e2-standard-2` on Google Cloud, `Standard_D2s_v5` on Azure,
`cpx22` on Hetzner and `ecs.g6.large` on Alibaba Cloud. Pass one of the two flags to choose the node
yourself:

```bash
alethia project create boutique --region eu-west-1 --cloud-account prod-account --instance-type t3.xlarge
alethia project create boutique --region eu-west-1 --cloud-account prod-account --node-size 4x16
```

The shape applies to every `dedicated` environment, because only a dedicated environment provisions
a cluster. A `namespace` or `vcluster` environment runs on the cluster of the environment it is
placed on. The two flags are mutually exclusive, and a create where no environment is `dedicated`
refuses them. To change the shape later, set the cluster's `instance_types` with
`alethia project component add --kind cluster`, which updates the existing cluster.

The created project prints as a card (or the typed object with `--output json`), followed —
when anything was asked for — by the `alethia project create` line that would produce the same
project without the questions. That line names every flag that shaped it, `--stage`,
`--placement-mode` and `--iac-version` included, so it can be committed as-is.

### The environment matrix

Every environment and **how each is placed onto a Fabric** is declared in `alethia.yaml`, under
`environments:`. The first entry is the default environment and owns the Fabric it provisions, so
it defaults to `dedicated`; later entries default to `namespace` and share that Fabric.

```yaml
project: shop
cloud:
  account: prod-account
  region: eu-west-1
environments:
  - name: prod
    stage: production
  - name: dev
    stage: development
    namespace: boutique-dev
  - name: staging
    stage: staging
    placement: vcluster
```

That is **one** cluster hosting three environments. With no manifest and no terminal you get the
default Production + Preview pair instead; on a terminal you are asked for each environment in
turn — name, stage, placement, namespace — and then shown the file your answers add up to, to
save as `alethia.yaml`.

A stage or a placement outside the allowed set is refused locally, naming the whole set, rather
than coming back as a `400`. The file's full reference, components included, is on
[Plan & Apply](/reference/cli/plan-and-apply#alethiayaml).

<Callout type="warn">
  Placement is the flag with a bill attached. Each `dedicated` environment is a separate cluster with
  its own OpenTofu state; `namespace` and `vcluster` share the Fabric that already exists. A four-cloud
  two-tier demo is four clusters with placement and eight without it.
</Callout>

## `alethia project plan` · `apply` · `destroy`

Queue a `PLAN`, `DEPLOY` or `DESTROY` job for one environment of a project.

```bash
alethia project plan --project boutique --env dev-1 --runner eu-box --wait
alethia project apply --project boutique --env dev-1 --latest-plan --wait
alethia project destroy --project boutique --yes
```

Omit `--project` on a terminal and you are asked which project; omit the runner and you are
asked which one (or "Any available"). `destroy` takes the runner by id only, for now.

| Flag | plan | apply | destroy | Description |
|------|------|-------|---------|-------------|
| `--project` | ✓ | ✓ | ✓ | Project by **name** or id. Asked for on a terminal when omitted. |
| `--project-id` | ✓ | ✓ | ✓ | Project id. Prefer `--project`, which also takes the name. |
| `--env` | ✓ | ✓ | ✓ | Target environment name (default: the project's default environment) |
| `--runner` | ✓ | ✓ | | Runner by **name** or id. Asked for on a terminal when omitted. |
| `--runner-id` | ✓ | ✓ | ✓ | Runner id. Prefer `--runner`, which also takes the name. |
| `--plan-job-id` | | ✓ | | Apply a specific `PLAN` job, by id |
| `--latest-plan` | | ✓ | | Apply the project's most recent `PLAN` job |
| `-w`, `--wait` | ✓ | ✓ | ✓ | Wait for job completion |
| `-y`, `--yes` | | | ✓ | Skip the confirmation prompt (required with `--no-input`) |
| `--cascade` | | | ✓ | Also destroy the environments placed on this environment's cluster, first. Prints them and confirms |

`--project` and `--project-id` name the same thing, so passing **both** is refused rather than
resolved by precedence. A project name that two projects share is also refused, naming both ids —
the command queues a `DESTROY`, and picking one of two plausible projects is not a decision the
CLI should make for you. `--runner` and `--runner-id` are the same pair, refused the same way, and
a runner name shared by two runners is refused naming both ids.

`destroy` is destructive: on a terminal it confirms, and with `--no-input` it requires `--yes`
rather than silently doing nothing.

Destroying a `dedicated` environment while `namespace` or `vcluster` environments are still placed
on its cluster is refused, naming them. Destroy them first, or pass `--cascade` — see
[`alethia project destroy`](/reference/cli/plan-and-apply#alethia-project-destroy).

### Applying the plan you just reviewed

`--latest-plan` resolves the project's own most recent `PLAN` job, so a review-then-apply pass
never moves a uuid between two commands:

```bash
alethia project plan --project boutique --env prod --wait
alethia project apply --project boutique --env prod --latest-plan --wait
```

It prints which job it chose before it queues anything. Three things it deliberately does **not**
do:

- It is **opt-in**. Without it (or `--plan-job-id`) the deploy runs its own plan, which is the
  ordinary path — a plan reference is a mode, not a hint: the Runner refuses a deploy whose plan
  did not succeed, or whose configuration moved since the plan was taken.
- It resolves `PLAN` jobs **only**. The project's most recent job is as likely to be the `DEPLOY`
  that followed the plan.
- It takes the most recent `PLAN` **whatever its status**, and refuses when that is not `SUCCESS`,
  naming the job and its status. Skipping past a plan that is still running would apply an older
  one you never asked for.

`--plan-job-id` is still there for a plan you already hold the id of.

## `alethia project design apply`

The declarative counterpart to `project component add`. The imperative commands are what you narrate
one step at a time; a design document is what a repository commits and CI replays. Both write the same
tables.

```bash
# The document, as it is now
alethia config export -p shop --out shop.json

# See what would change — writes NOTHING
alethia project design apply -p shop -e dev -f shop.json --dry-run

# Apply it
alethia project design apply -p shop -e dev -f shop.json

# Or send it to the staged-changes tray for review instead
alethia project design apply -p shop -e dev -f shop.json --stage

# From a pipe
cat shop.json | alethia project design apply -p shop -f -
```

| Flag | Required | Description |
|------|----------|-------------|
| `-f`, `--file` | Yes* | Design document path, or `-` for stdin. *Asked for on a terminal when omitted. |
| `-p`, `--project` | Yes* | Project name or id. *Asked for on a terminal when omitted. |
| `-e`, `--env` | No | Environment name, stage, or id. Omit for the project's default. |
| `--dry-run` | No | Print the changes that would be made and write nothing. |
| `--stage` | No | Stage the change for review instead of applying it. |
| `-y`, `--yes` | No | Confirm an apply whose plan **removes** a component. Required with `--no-input` only in that case. |

Both `--dry-run` and a real apply print one row per component with the action taken:

```
3 change(s) would be made in dev:
  UPDATE  databases orders
  CREATE  caches sessions
  DELETE  storage_buckets receipts
```

### The gate is on the plan, not on the command

An apply can **delete**: a kind the document omits is a kind the environment loses. So the
confirmation appears exactly where that happens, and nowhere else.

- A plan that only **adds or updates** applies unprompted, including under `--no-input`. A design
  document is what a repository commits and CI replays, and a pipeline that adds a cache does not
  need a human in it.
- A plan that **removes** a component prints what would go, then confirms. Under `--no-input` it
  requires `-y`, `--yes`.

To decide which it is, a real apply asks the server for its own `--dry-run` first, so the prompt
names the components rather than asking in the abstract:

```
This apply would DELETE 1 component(s) in dev:
  DELETE  storage_buckets receipts
```

If that check cannot be read at all, the apply is **refused** rather than run blind — `--yes`
applies without it.

<Callout type="warn">
  `--yes` on a `design apply` is not a blanket "this command is destructive" switch. It opts *that
  invocation* into removing components. Leaving it on a pipeline permanently means every later
  replay may remove components too; if a replay is suddenly asking for it, the usual cause is a
  document that stopped declaring something you meant to keep.
</Callout>

The rows are printed for a real apply as well as for `--dry-run`, so what actually went is visible
next to what was predicted.

`--dry-run` and `--stage` are mutually exclusive — one writes nothing, the other writes to the review
tray — so passing both is refused rather than silently resolved to one.

The document is validated by the **console form's own schema**, including its cross-field rules (the
node min/max/desired ordering, the VPC rule). A document the form would reject cannot be smuggled in
through the CLI, and the error names the field: `Invalid design document at cluster.node_min_size: …`.

## `alethia project env`

A project owns N independently-provisionable environments. The project is named with `--project`
(its name **or** id); omit it on a terminal and you are asked.

```bash
# List a project's environments
alethia project env list --project boutique

# Add one, answering the same four questions the --env tuple asks
alethia project env add --project boutique

# Or say it outright
alethia project env add staging --project boutique --stage staging

# As a vcluster on a named Fabric, with its own destination namespace
alethia project env add staging --project shop --stage staging \
  --placement-mode vcluster --fabric shared --namespace boutique-staging

# One that provisions its OWN cluster
alethia project env add prod --project shop --stage production --placement-mode dedicated
```

| Command | Flags | Description |
|------|----------|-------------|
| `env list` | `--project` | List the project's environments (default first) |
| `env add [name]` | `--project` `--stage` `--region` `--placement-mode` `--fabric` `--namespace` `--lifecycle` | Add an environment (name is slugified; region inherits the project's when omitted) |

| Flag | Required | Description |
|------|----------|-------------|
| `--project` | Yes* | Project name or id. *Asked for on a terminal when omitted. |
| `--stage` | No | `development` (default), `staging`, `production` |
| `--placement-mode` | No | `namespace` (default), `vcluster`, `dedicated` |
| `--namespace` | No | ArgoCD destination namespace for a shared placement (default: derived from the name) |
| `--fabric` | No | Fabric to place onto, by name (default: the one the project's default environment is on) |
| `--region` | No | Region (inherits the project's when omitted) |
| `--lifecycle` | No | `persistent` (default) or `ephemeral` |

An **added** environment defaults to `namespace` placement on the Fabric the project's default
environment already uses — the cheap rung, and the one that makes a second tier free. `--fabric`
and `--namespace` are ignored for `dedicated`, which owns a new Fabric.

The interactive form asks for the four fields the `--env` tuple can express: name, stage,
placement and namespace. `--region`, `--fabric` and `--lifecycle` stay flag-only, so the form can
never ask for something a script cannot say.

The success line names the placement you got, so a `dedicated` you did not intend is visible
immediately rather than on the next apply.

## `alethia project component`

One uniform group authors **all** of a project's component resources. The project is named with
`--project`, and the environment with `--env`.

**Which kinds exist is published by the server, and `component kinds` is how you read it.** This
page used to list them, and that list drifted: it named thirteen while the server accepted fourteen.
A kind has one of two cardinalities — **singleton** (one per project *per environment*, name-less) or
**multi** (named, many per environment) — and `kinds` prints each with its own, so the answer to
"does this one need a `--name`" comes from the same place as the list itself.

```bash
# List the supported kinds
alethia project component kinds

# List a project's components (optionally filter by --kind and/or --env)
alethia project component list --project boutique --kind databases

# Add one by answering questions — kind, name, environment, then field by field
alethia project component add --project boutique

# Or say it outright. Multi kind → --name required
alethia project component add --project boutique --kind databases --name main \
  --set engine=postgres --set port=5432 --set iam_auth=true

# Configure the cluster singleton (--name ignored; upserts)
alethia project component add --project boutique --kind cluster \
  --set 'cluster_version="1.35"' --set node_min_size=2 --set 'instance_types=["t3.medium"]'

# Remove components (destructive → confirms)
alethia project component remove --project boutique --kind databases --name main
alethia project component remove --project boutique --kind network
```

| Command | Flags | Description |
|------|----------|-------------|
| `component kinds` | — | List the component kinds the server publishes, with each one's cardinality. Needs a session — the answer is the server's, not a built-in list |
| `component list` | `--project` `--kind` `--env` | List components (all kinds, or one) |
| `component add` | `--project` `--kind` `--name` `--env` `--set` | Create a component |
| `component remove` | `--project` `--kind` `--name` `--env` `-y`, `--yes` | Delete a component (confirms) |

| Flag | Required | Description |
|------|----------|-------------|
| `--project` | Yes* | Project name or id. *Asked for on a terminal when omitted. |
| `--kind` | Yes* | Component kind. Optional on `list`, where it filters. *Asked for on a terminal for `add` and `remove`. A kind this CLI's cached list does not hold is still authorable — the picker offers it verbatim and the server decides. |
| `--name` | Yes for multi kinds | Component name. Ignored by singleton kinds, which upsert. *Asked for on a terminal by `add` and `remove`, as a picker over the components that exist. |
| `--env` | No | Environment id, name or stage. Asked for as a picker on `add`; whichever form you pass is what the picker starts on. |
| `--set` | No | `key=value` field assignment, repeatable. Asked for, one field at a time, on `add`. |
| `-y`, `--yes` | No | `remove` only: skip the confirmation prompt (required with `--no-input`) |

### Components belong to an environment

A component is scoped to one **environment**, not to the project as a whole — so two environments
can hold the same kind with different configuration. `--env` takes an environment id, name or stage.
When one value matches more than one environment, the id wins, then an exact name, then a stage. Among
stage matches, the default environment wins. So `--env staging` selects the environment named
`staging`, even when the default environment is at stage `staging`:

```bash
# dev and staging deploy DIFFERENT overlays of the same repo
alethia project component add --project shop --env dev --kind repositories \
  --set apps_destination_repo=https://github.com/acme/shop --set apps_path=overlays/dev

alethia project component add --project shop --env staging --kind repositories \
  --set apps_destination_repo=https://github.com/acme/shop --set apps_path=overlays/staging

# Inspect one tier at a time
alethia project component list --project shop --env staging
```

What `--env` defaults to differs by verb, deliberately:

- **`add` and `remove`** default to the project's **default environment**, so a single-environment
  script needs no `--env` at all.
- **`list`** defaults to **every** environment. Narrowing a read silently would hide rows you did
  not ask to hide.

<Callout type="warn">
  `remove` deletes from **one** environment — the one you named, or the default. It never touches a
  sibling environment's copy. The confirmation names both the component and the tier
  (`Deletes the databases main configuration in staging`), and so does the success line
  (`Component removed in staging`).
</Callout>

### The `--set` field setter

`--set key=value` is repeatable and generic. Each value is parsed as JSON when it can be, else taken
literally — so numbers, booleans, and arrays are typed correctly:

```bash
--set port=5432                       # number
--set iam_auth=true                   # boolean
--set instance_types='["t3.medium"]'  # array
--set 'node_size={"vcpu":4,"memory_gb":16}'  # object
--set engine=postgres                 # string
--set 'cluster_version="1.31"'        # string that would otherwise parse as a number
```

Quote a value that looks like a number but is a string field — `cluster_version=1.31` coerces to the
number `1.31`, which the server refuses.

A cluster is sized one of two ways. `node_size` is a size that works on any cloud: the deploy picks
the closest machine type in the catalog for the cluster's cloud. `instance_types` pins a machine type.
Setting one clears the other in the same write, and a single `add` that sets both fails.

`capacity_type` chooses how the nodes are bought: `on_demand` (the default) or `spot`. Spot nodes cost
less, but the cloud can take a node back at short notice. Each cloud applies `spot` to its own node
pool setting:

| Cloud | What `spot` changes |
|---|---|
| AWS | The managed node group runs on Spot. |
| GCP | The node pool runs on Spot VMs. A deploy refuses `spot` on an Autopilot cluster, which has no node pool. |
| Azure | A separate Spot worker pool is added, and it scales from zero. The system pool stays on-demand, because AKS can't run it on Spot. Only pods that tolerate the Spot taint run on the Spot pool. |
| Alibaba Cloud | The worker node pool runs on Spot at the market price. If the cluster sets `ack_spot_price_limit`, the pool uses those price limits. |
| Hetzner | Not available. Hetzner Cloud has no Spot servers, so a deploy refuses `spot`. |

```bash
alethia project component add --project boutique --kind cluster --set capacity_type=spot
```

Fields are **validated server-side** against the component's schema: an unknown or mistyped field
fails with a clear `400`, naming the offending field and the allowed set. Singleton kinds ignore
`--name` (they upsert the project's single row); multi kinds require it.

### Setting template knobs

A component's `provider_config` field sets the template's own variables: the same knobs as the
**Advanced** section of the component's card on the canvas. Examples are the GKE private endpoint,
the AKS Spot pool and the EKS volume type. Pass it as a JSON object with `--set`:

```bash
alethia project component add --project boutique --kind cluster \
  --set 'provider_config={"gke_enable_private_endpoint":true,"gke_disk_type":"pd-ssd"}'
```

In `alethia.yaml`, write it as a nested mapping under the component:

```yaml
environments:
  - name: prod
    components:
      cluster:
        node_min_size: 2
        provider_config:
          gke_enable_private_endpoint: true
          gke_disk_type: pd-ssd
      databases:
        - name: orders
          engine: postgres
          provider_config:
            cloud_sql_high_availability: true
```

**Which keys you can set depends on the project's cloud and the component.** The server checks each
key against the template for that cloud. It refuses a key it does not accept, and the error lists
every key that you can set. To find the keys, send one you know is wrong:

```
provider_config key(s) not settable for cluster on gcp: gke_private_endpoint (not a variable of this template).
Settable keys for cluster on gcp: external_dns_service_account_email, external_secrets_service_account_email,
gke_disk_type, gke_enable_private_endpoint, gke_enable_private_nodes, gke_master_authorized_cidr_blocks,
gke_secrets_encryption_enabled, gke_secrets_encryption_rotation_period, gke_volume_iops, gke_volume_throughput
```

The server refuses these keys, and says why for each one:

- a key the template does not declare;
- a key that a typed field already sets, such as `instance_types` for the node type — use that field;
- a key that Alethia always sets itself, or that the cloud can't apply;
- a key that starts with `alethia_`, which is reserved for platform context;
- a credential, such as a password or a secret's value. Store a credential as a secret, not in
  `provider_config`. The canvas does not offer these keys either, and `alethia apply` refuses them
  in a design. See [Secrets](/guides/design-project/secrets#set-a-secrets-value) and
  [Databases](/guides/design-project/databases#the-extra-database-user-aws).

Each value must have the type that the template declares. Use a JSON `true`/`false` for a `bool`
knob, a number for a `number` knob, and a list or an object where the template declares one.

**A write merges into what is stored.** A key you send replaces that key's value, and a key you do
not send keeps its value. This includes a key that someone set on the canvas. To remove a key and
go back to the template's default, set it to `null`. With `--set`, write it as JSON `null`:

```bash
alethia project component add --project boutique --kind cluster \
  --set 'provider_config={"gke_disk_type":null}'
```

In `alethia.yaml`, write `null` (or `~`) as the key's value, then run `alethia apply`:

```yaml
      cluster:
        provider_config:
          gke_disk_type: null
```

Deleting the line from `alethia.yaml` does not remove the key. A key that the file does not
declare keeps its stored value.

`alethia plan` compares `provider_config` key by key. A key the server holds and the file does
not declare, for example one set on the canvas, shows no change. A key written as `null` shows as a
change only while the server still holds it. A whole `provider_config: null` is refused: write each
key you want removed as `null`. [Plan & Apply](/reference/cli/plan-and-apply#setting-and-removing-a-provider_config-key)
has the details.

`provider_config` needs a cloud. The project, or the component, must be linked to a cloud account
first. `network` and `repositories` have no `provider_config`, and the server refuses the field on
them.
