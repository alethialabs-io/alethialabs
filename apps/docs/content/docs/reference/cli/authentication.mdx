title: Authentication
description: Device Authorization Grant flow for people, service-account tokens for pipelines, credential storage in the system keychain, and automatic refresh.
---

alethia authenticates two ways, for two different callers:

- **You, at a terminal** — the **Device Authorization Grant** (RFC 8628). You never type a password.
- **A pipeline** — a **service-account token**, supplied through `$ALETHIA_TOKEN`. No browser, no prompt.

For why the CLI authenticates this way, see [Authentication flows](/concepts/authentication); for
the protocol, its endpoints and its deviations from RFC 8628, see
[Device Authorization Grant](/reference/standards/device-code).

## Login

```bash
alethia login
```

1. The CLI prints a short `user_code` and opens your browser at the Console's `/cli/login` page.
2. Sign in there with any OAuth provider (GitHub, GitLab, Bitbucket, Google) or email OTP, if you are
   not already. The page names the account that is about to be bound, what approval hands over, who
   is asking and how long is left.
3. Check that the code on screen is the one your terminal printed, then approve. Nothing is typed
   back into the terminal.
4. The CLI, which has been waiting with a spinner, receives an access and refresh token pair and
   stores it in the system keychain. It then prints one line that says where the credential was
   stored. See [Credential storage](#credential-storage).

The URL, the code and every notice go to stderr. The result goes to stdout: one sentence, or one JSON
object with `--output json`.

```bash
alethia login --output json
```

```json
{
  "id": "alethialabs.io",
  "kind": "session",
  "action": "created",
  "job": null,
  "dry_run": false,
  "object": { "user": "you@example.com", "origin": "https://alethialabs.io", "stored_in": "keychain" }
}
```

| Flag | What it does |
| --- | --- |
| `--force`, `-f` | Sign in again even when a session is already stored |
| `--web-origin` | Sign in to this control plane and remember its URL, for a self-hosted or development control plane |
| `--no-browser` | Print the sign-in URL without opening a browser, so you can open it on another machine |
| `--insecure-storage` | Store the credential in the owner-only file instead of the system keychain |

```bash
alethia login --web-origin https://alethia.example.com   # a self-hosted control plane
alethia login --no-browser                                # open the printed URL yourself
```

`alethia login` refuses while `ALETHIA_TOKEN` or `--token` is set, and exits with status 7. Every
command would continue to use the supplied token, so the sign-in would change nothing. Remove the
variable first.

If you refuse the sign-in in the browser, the command exits with status 5. If the code expires or the
wait times out, it exits with status 4. In each case nothing is stored.

## Refusing a login you did not start

If the code on screen is not the one your terminal printed, or you did not run `alethia login` at all,
press **This isn't me**.

That records the refusal in Console rather than only in the browser. Three things follow:

- The device that is polling is told at once, with the standard `access_denied` error, instead of waiting
  out its own timeout.
- Nothing is handed over — no access token, no refresh token, and none of your linked git provider's
  OAuth token.
- The refusal is final for that link. Opening it again cannot approve it; a genuine sign-in needs a fresh
  `alethia login`.

### Force Re-authentication

```bash
alethia login --force
```

Re-authenticates even if a valid token already exists. Useful when switching accounts.

On a terminal you do not need the flag. If you are already signed in, `alethia login` names the account
and asks whether to keep that session or sign in again. **Keep this session** is the first option, so
pressing Enter changes nothing. With `--no-input`, with no terminal, or when an agent runs the command,
it asks nothing: it names the account, keeps the session, reports `"action": "unchanged"` and exits 0.
Pass `--force` to sign in again from a script.

A first sign-in asks no question. The control-plane URL is not asked for here: pass `--web-origin`, or
use `alethia init` for the guided first-run setup.

## Logout

```bash
alethia logout
```

Removes the stored credential for the current control plane from both places it can be: the system
keychain and the credentials file. It also deletes the kubeconfig credential cache, for every
organization. After that, an exec kubeconfig from `alethia cluster kubeconfig` fails until you run
`alethia login` again. See [Revoke access](/guides/get-a-kubeconfig#revoke-access).

`alethia logout` tries every removal before it reports a failure. If it cannot delete the keychain
entry, the file or the cache, it prints the reason on stderr and exits with a non-zero status. If you
are not signed in, it changes nothing and exits 0.

`alethia logout` does not unset `ALETHIA_TOKEN`. A token from the environment is never stored, so
there is nothing to remove. The command warns you that the variable is still set.

```bash
alethia logout --output json
```

```json
{
  "id": "alethialabs.io",
  "kind": "session",
  "action": "deleted",
  "job": null,
  "dry_run": false,
  "object": { "origin": "https://alethialabs.io", "keychain": true, "file": false, "kubeconfig_cache": true }
}
```

## Check the credential in use

```bash
alethia auth status
```

Shows the credential that the next command would send: the account, the control plane, where the
credential is stored and when the access token expires. The credential itself is never printed.

`alethia auth status` reads the stored credential and sends no request. Use `alethia whoami` when
you want the control plane to confirm the identity. `alethia whoami` shows the same storage and
expiry lines.

```bash
alethia auth status --output json
```

```json
{
  "user": "you@example.com",
  "origin": "https://alethialabs.io",
  "source": "keychain",
  "stored_in": "the system keychain",
  "expires_at": "2027-01-31T10:15:00Z",
  "renews_automatically": true
}
```

`source` is one of four values:

| `source` | Where the credential comes from |
| --- | --- |
| `flag` | The `--token` flag. Not stored. |
| `env` | The `ALETHIA_TOKEN` environment variable. Not stored. |
| `keychain` | The system keychain |
| `file` | The owner-only credentials file. `path` gives its location. |

For `flag` and `env`, `user` is absent, because a supplied token does not name an account that the
CLI can read. `expires_at` is `null` when the token does not state its own expiry, as a
service-account token does not. With no credential, the command exits with status 4.

## Token Lifecycle

| Token | TTL | Purpose |
|-------|-----|---------|
| Access token | 1 hour | `Authorization: Bearer` header on API calls |
| Refresh token | 90 days | Obtain new access tokens transparently |

Before each API call, alethia checks the access token's expiry and refreshes it automatically when it
is within a minute of expiring — see [Refresh](/reference/standards/device-code#refresh). You never
notice it.

If the control plane refuses a stored access token during a command, the CLI renews the credential
once and sends the request again. A token from `ALETHIA_TOKEN` or `--token` is never renewed.

## Identity & Active Org

After logging in, confirm who you are signed in as and which organization the CLI is scoped to:

```bash
alethia whoami   # user, active org, role, plan, default runner
alethia config   # control-plane URL, active org, on-disk file paths
```

The active organization is sent as the `X-Alethia-Org` header on every request. Set or change it
with `alethia org switch`. See [Identity & Global Options](/reference/cli/identity) and
[Organizations, Members & Teams](/reference/cli/organizations).

## Running in CI

The device flow needs a browser and a person, so a pipeline cannot use it. Mint a **service-account
token** instead:

```bash
alethia token create --name "github-actions"
```

The token is printed **once**, on stdout, with everything else on stderr — so you can pipe it
straight into a secret store without selecting it by eye:

```bash
alethia token create --name "github-actions" | gh secret set ALETHIA_TOKEN
```

Then set `ALETHIA_TOKEN` in your job and use the CLI normally. Nothing is written to disk, and no
`alethia login` is needed:

```yaml
- name: Deploy staging
  env:
    ALETHIA_TOKEN: ${{ secrets.ALETHIA_TOKEN }}
  run: |
    alethia project apply --env staging --wait --no-input
```

Pair it with `--no-input`, which makes the CLI fail rather than prompt — together they mean a job
never hangs waiting for an answer nobody is there to give.

### What a service token can do

A token **acts as the person who created it**, inside the **one organization** it was minted for.
That org is fixed when the token is created: an `X-Alethia-Org` header that disagrees with it is
refused, not ignored, so a token issued for one organization can never act on another.

It also stops working the moment its creator leaves that organization — membership is re-checked on
every request, not trusted from when the token was minted.

A service token cannot run [break-glass](/reference/cli/ops). The `alethia ops` verbs need an
interactive session from `alethia login`, and the server refuses a service token there with a
`403` — even when the person who created it is a break-glass operator. A token pinned to one
organization must not carry an identity that acts across every tenant. The server refuses the
service token itself, not a delivery path: an operator's session token is still accepted from
`ALETHIA_TOKEN` or `--token`, so never place one in CI.

### Minting a token

Run `alethia token create` on a terminal with no flags and it asks for the two things it needs:

{/* fieldspec: alethia token create */}

| Field | What it is | Set without the form |
| --- | --- | --- |
| Name | What this token is for, so a list of tokens is a list of purposes | `--name` |
| Expires | A token that never expires is a credential nobody remembers to rotate | `--expires-in-days` |

The flags are the complete contract: anything the form can ask, a flag can set, so
`--no-input` never needs a prompt.

```bash
alethia token create                              # asks for the name and the lifetime
alethia token create --name ci --expires-in-days 90   # the same, unattended
```

`--expires-in-days 0` — the default — never expires. That is a deliberate choice rather than an
oversight, and it is why the form asks: a credential with no end date is one nobody remembers to
rotate.

### Managing tokens

```bash
alethia token list     # id, name, prefix, created, expires, last used, status
alethia token revoke   # pick from the live tokens, or pass an id
```

`alethia token list` shows `last used: never` for a token nothing has ever presented. That is usually
the most interesting row on the list — a credential that was minted, put somewhere, and forgotten.

`alethia token revoke` with no argument shows the tokens that are still live and revokes the one you
pick, so you never have to copy an opaque id out of `token list` by eye. Already-revoked tokens are
left out of the picker; revoking one again does nothing.

{/* fieldspec: alethia token revoke */}

| Field | What it is | Set without the form |
| --- | --- | --- |
| Token | The token to revoke; it stops working on its very next request | `[id]` |

```bash
alethia token revoke                                           # pick from a list
alethia token revoke 3f2b9c14-7a1e-4d68-9c05-2b8e6a1d40f7    # revoke a known id, no prompt
```

<Callout type="info">
Revoke carries **no `--yes`**, unlike every other destructive command. Its asymmetry runs the other
way: revoking a token you did not mean to costs one `alethia token create`, while failing to revoke a
leaked one costs the organization. A confirmation here would fail an incident-response pipeline and
leave the credential live.
</Callout>

<Callout type="warn">
The token value is shown **once** and is never stored — the server keeps only a hash of it. If you
lose it, revoke it and mint another. There is no way to read it back, by design.
</Callout>

Minting, listing and revoking tokens requires the `org:manage_tokens` permission, which **owners and
admins** hold. Operators deliberately do not: issuing a credential that carries someone's access into
an unattended pipeline is a higher bar than deploying infrastructure by hand.

## Environment Variables

| Variable | Default | Purpose |
|----------|---------|---------|
| `ALETHIA_WEB_ORIGIN` | Production URL (baked at build) | Override the Alethia API URL |
| `ALETHIA_TOKEN` | unset | A service-account token for non-interactive use. When set, the CLI uses it before any stored credential, and never writes it to the system keychain or to a file. |

```bash
export ALETHIA_WEB_ORIGIN=http://localhost:3000
alethia login  # authenticates against local dev server
```

The `--token` flag does the same thing as `$ALETHIA_TOKEN` and takes precedence over it. Prefer the
environment variable in CI: a flag value lands in the process table and in shell history, where an
environment variable does not.

## Credential storage

`alethia login` stores the credential in the credential store of the operating system:

| System | Store |
| --- | --- |
| macOS | Keychain |
| Linux | The Secret Service, for example GNOME Keyring or KWallet |
| Windows | Credential Manager |

The entry is filed under the service `alethia`, with the host of the control plane as the account.

Some hosts have no credential store: a container, a CI runner, or a Linux host with no desktop
session. On those hosts the CLI stores the credential in a file that only your user can read:

```
~/.config/alethia/credentials.json
```

The CLI also uses the file when the credential store does not answer within 3 seconds, and when you
pass `--insecure-storage`. In each case `alethia login` prints one line on stderr that says which of
the two it used. The file has mode `0600` and its directory has mode `0700`.

```json
{
  "access_token": "eyJ...",
  "refresh_token": "eyJ...",
  "user_email": "you@example.com",
  "origin": "https://alethialabs.io"
}
```

The access-token expiry is read from the JWT itself (the `exp` claim), so no separate timestamp is
stored. The active-org context is kept separately in `~/.config/alethia/config.json` (see
[Configuration](/reference/cli/configuration)).

<Callout type="warn">
The credentials file is not encrypted. Filesystem permissions are its only protection. Prefer the
system keychain where one is available.
</Callout>

### The order the CLI looks for a credential

1. The `--token` flag
2. The `ALETHIA_TOKEN` environment variable
3. The system keychain
4. The credentials file

The first one found is used. A supplied token always wins over a stored sign-in.

### One credential for each control plane

A stored credential records the control plane that issued it, and the CLI uses it for that control
plane only. If you change `web-origin`, the CLI does not send the old credential to the new URL. It
reports that you are not signed in, and you run `alethia login` again. The system keychain holds one
entry for each control plane. The credentials file holds one credential.

### Moving from the file to the keychain

An earlier version of the CLI stored every credential in the file. This version reads that file
without changing it. The next time you sign in, or the next time the CLI renews the access token, it
writes the credential to the system keychain, reads the entry back, and compares it with what it
wrote. Only then does it remove the file, and it prints one line that says the credential moved. If
the keychain entry does not read back, the file stays.

A credential stored with `--insecure-storage` stays in the file.
