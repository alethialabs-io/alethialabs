# Cluster Commands

A cluster is what a project environment runs on. You do not create one here: provisioning an
environment creates it, and this group reads it back. The command is `alethia cluster` (singular)
with a `clusters` alias, so both forms work interchangeably.

<Callout type="info">
The CLI is a client of the same Console API. These commands call `/cli/clusters` with your
[CLI token](/reference/cli/authentication) and operate on the **active organization**, which you change with
`alethia org switch`. For one invocation, `alethia cluster list --org <id>` scopes the call to a
different organization instead — `--org` is a global flag, accepted on every command, and refused
with `403` if you are not a member of the organization you name.
</Callout>

## `alethia cluster list`

List every cluster across your projects — one row per project environment.

```bash
alethia cluster list
alethia clusters list
alethia cluster list -o json
```

The command takes no input of its own; only the [global flags](/reference/cli) apply.

| Column | Meaning |
|--------|---------|
| Project | The project and its environment — the same label `cluster get` titles its card with. |
| Cluster | The cloud's name for the cluster, or `—` before it is provisioned. |
| Version | The Kubernetes version. |
| Status | A glyph and the status, with the status message appended when a cluster is degraded or failed. |
| ArgoCD | `exposed` when a managed-ingress URL exists, `port-fwd` when access is by port-forward, `—` when the cluster is not provisioned yet. |
| Nodes | Min / desired / max node count. |
| Region | The cloud region. |
| Cost | The estimated monthly cost, rendered exactly as the console's billing pages render it. |

```
Project                   Cluster                 Version  Status    ArgoCD    Nodes  Region     Cost
api-backend (production)  api-backend-production  1.30     ● active  exposed   1/3/5  eu-west-1  $210.00/mo
data-pipeline (staging)   data-pipeline-staging   1.29     ● active  port-fwd  1/2/3  us-east4   $95.00/mo
```

At a terminal this is a navigable table; in a pipe, with `--no-input`, or with `-o json` / `-o csv`
it prints statically. Backing call: `GET /cli/clusters`.

## `alethia cluster get`

Show one cluster in full, including the command that gets you a kubeconfig and how to reach its ArgoCD.

```bash
alethia cluster get
alethia cluster get api-backend
alethia cluster get api-backend-production -o json
```

| Input | Required | Description |
|-------|----------|-------------|
| `[selector]` | No — at a terminal | Matches a project name, a cluster name, or a cluster id, case-insensitively. Falls back to a project-name substring. |

**Run it with no selector and the CLI asks which cluster**, listing every one you have with its
status. That is the whole reason the selector is optional: you never have to run `cluster list`
first and copy a name out of it.

The selector is required when a prompt could not work: with `--no-input`, with a piped stdin that
could never answer one, and with a redirected stdout that has no screen to draw one on. In each
case the command exits non-zero explaining what to pass. The last is the easy one to hit —
`alethia cluster get -o json > clusters.json` refuses rather than writing a form into your file.
A selector that matches **nothing** is an error too, not an empty screen —
`alethia cluster get typo || echo missing` prints `missing`.

A selector that matches **more than one** cluster — the usual case is one project with a production
and a staging environment — asks which you meant rather than picking for you. With `--no-input` it
refuses and names the candidates, so you can re-run with the cluster name or id, both of which are
unique.

```
╭─────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╮
│  A P I - B A C K E N D   ( P R O D U C T I O N )                                                                                                        │
│                                                                                                                                                         │
│  Status        ● active                                                                                                                                 │
│  Cluster       api-backend-production                                                                                                                   │
│  Version       K8s 1.30                                                                                                                                 │
│  Region        eu-west-1                                                                                                                                │
│  Nodes         1 / 3 / 5  (min/desired/max)                                                                                                             │
│  Est. cost     $210.00/mo                                                                                                                               │
│  Kubeconfig    aws eks update-kubeconfig --name api-backend-production --region eu-west-1                                                               │
│  ArgoCD        https://argocd.api-backend.example.com                                                                                                   │
│  ArgoCD admin  after the kubeconfig command above: kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d  │
│  GitOps        6/6 synced · 5/6 healthy · rev 9c1f0a3                                                                                                   │
│  Apps repo     github.com/acme/api-backend-apps                                                                                                         │
╰─────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╯
```

Only the fields a cluster actually has are shown: a cluster that is still provisioning has no name,
no version, no kubeconfig row and no ArgoCD block.

Backing calls: `GET /cli/clusters`, then `GET /cli/clusters/{id}` for the kubeconfig command and the
GitOps posture. The second one is best-effort — if it fails you still get the cluster, without the
Kubeconfig and GitOps lines.

### ArgoCD access

ArgoCD is installed on every provisioned cluster. The **ArgoCD** row is its URL where a managed
ingress exists, and a note to port-forward where the cloud does not have one yet.

The admin password is **never stored by Alethia** — it would be plaintext in the control-plane
database — so the card prints the command that reads it from the cluster's own initial-admin
secret. It is a `kubectl` command, so get a kubeconfig first (the **Kubeconfig** row, above it),
then run:

```bash
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d
```

Where there is no managed ingress, reach the UI through a port-forward first:

```bash
kubectl -n argocd port-forward svc/argocd-server 8080:443
```

### GitOps posture

The **GitOps** row summarises the cluster's ArgoCD applications: how many are synced, how many are
healthy, and the short revision they are deployed at. It reads `failed at <step>` when the last
deploy failed, and `unknown (no snapshot yet)` when there is no trustworthy reading — which is a
different statement from "nothing is deployed", and deliberately not rendered as one.

## `alethia cluster kubeconfig`

Get a short-lived kubeconfig for a cluster without a cloud login of your own. A runner in the
cluster's network mints the credential and seals it to a one-time key that this command makes.
Only this machine can open the result. For the task, with the tiers, lifetimes and revocation, see
[Get a kubeconfig for your cluster](/guides/get-a-kubeconfig).

```bash
alethia cluster kubeconfig
alethia cluster kubeconfig api-backend
alethia cluster kubeconfig api-backend --admin --ttl 4h
alethia cluster kubeconfig api-backend --output api-backend.kubeconfig
alethia cluster kubeconfig api-backend --static --output -
alethia cluster kubeconfig api-backend-production --no-input
```

| Input | Required | Default | Description |
|-------|----------|---------|-------------|
| `[selector]` | No — at a terminal | The picker | The same selector as `cluster get`: a project name, a cluster name or a cluster id. Omit it at a terminal and the CLI asks which cluster. |
| `--admin` | No | Off (read-only) | Get the admin tier. Needs the `cluster:access_admin` permission, which owners and admins hold. Without it, the tier is read-only, which needs `cluster:access_readonly` (owners, admins and operators). |
| `--ttl` | No | `1h` | The credential's lifetime, from `15m` to `8h`, in whole seconds (`90m` and `2h30m` work). An admin credential's real lifetime is set by the cloud. See [the lifetime table](/guides/get-a-kubeconfig#choose-how-long-the-credential-lasts). |
| `--static` | No | Off (exec) | Write a kubeconfig that holds the credential itself and stops working when it expires. Hetzner and Alibaba Cloud always get this shape. |
| `--merge` | No | On | Merge into the first file in `$KUBECONFIG`, or into `~/.kube/config`, and make the context current. |
| `--output` | No | None | Write a standalone kubeconfig to this file instead of merging. `-` writes it to stdout. |

The selector is required where a prompt cannot work: with `--no-input`, with a piped stdin, and
with a redirected stdout. Every flag has a default, so a selector with `--no-input` is a complete
call.

### Where the kubeconfig goes

| Flags | Result |
|-------|--------|
| None, or `--merge` | The CLI merges the context `alethia-<project>-<env>` into the first file in `$KUBECONFIG`, or into `~/.kube/config`, and makes it the current context. It replaces the cluster, user and context entries with that name, and keeps every other entry, unknown key and comment. It takes kubectl's `<file>.lock` lock while it writes, and follows a symlinked kubeconfig. |
| `--output FILE` | The CLI writes a standalone kubeconfig to that file. |
| `--output -` | The CLI writes the kubeconfig to stdout. This is the only way the credential goes to stdout. |

Every file the command writes gets mode `0600`, and the write is atomic. All other messages go to
stderr, so stdout is empty unless you pass `--output -`.

**The `--output` rules.** In this command `--output` takes a file path, not the global
`table`/`json`/`csv` format, and it has no `-o` short form. `--output table`, `--output json` and
`--output csv` are refused, so a habit cannot write a credential to a file called `json`. To write a
file with one of those names, pass `./json`. `--output` replaces the merge, so do not pass
`--merge` with it, not even as `--merge=false`: the two flags together are an error. Turning off
`--merge` without an `--output` is refused too, because the kubeconfig would go nowhere.

### Exec and static

| Shape | Clouds | What the kubeconfig holds |
|-------|--------|---------------------------|
| Exec (the default) | AWS, GCP, Azure | No credential. It runs `alethia cluster token` with the cluster id, so `kubectl` gets a new token whenever one expires. The command also caches the token it just minted, so the first `kubectl` call does not wait for a runner. |
| Static (`--static`) | All five, and always on Hetzner and Alibaba Cloud | The credential itself: a bearer token, or a client certificate and key. It stops working at its expiry. |

The cluster list does not tell the CLI which cloud a cluster is on. So without `--static`, the CLI
asks for exec. If the cloud refuses (`422`), it asks again for static. A second `422` means the cloud
cannot mint either shape.

The exec kubeconfig pins the cluster's API server and certificate authority, and it never turns off
TLS verification. It needs the `alethia` command on the `PATH` of every machine that runs `kubectl`
with it.

### What the command prints

On stderr, after the kubeconfig is written:

- the context name and the file it went to;
- the tier, and for an exec kubeconfig the TTL of each token, or for a static one its real expiry;
- a `kubectl --context` command to try;
- if the cluster's API endpoint is private, a note that `kubectl` needs network access to it, for
  example through a VPN or a bastion host.

A spinner shows while the runner works, but only at a terminal with prompts turned on. With
`--no-input`, nothing is drawn.

### Exit codes and refusals

The command exits `0` when it wrote the kubeconfig, and `1` for every error. It prints the error on
stderr after `Error:`. These are the refusals from the control plane, and what the CLI prints:

| Status | Cause | The CLI prints |
|--------|-------|----------------|
| `401` | The session is not valid. | Run `alethia login`. |
| `402` | A usage limit of the organization's plan. The mint runs on a runner and uses runner minutes. | The server's reason, and a pointer to `alethia usage`. |
| `403` | Your role does not hold the tier's permission. | Which roles can mint that tier. For `--admin`, a hint to drop it. |
| `404` | No such cluster in the active organization. | A pointer to `alethia org switch` and `--org`. |
| `409` | The environment is a draft, is being destroyed, or has no successful deploy. | The server's reason, and a pointer to `alethia project apply`. |
| `422` | The cluster's cloud cannot mint a kubeconfig (it is not AWS, GCP, Azure, Alibaba Cloud or Hetzner, or it has no cloud identity). | The server's reason. |
| `429` | More than 20 requests in 10 minutes, per person, per organization. | How long to wait, from the `Retry-After` header. |

After the request is accepted, the CLI polls until the mint is ready, failed or expired. It waits
up to 10 minutes, the server's window, and gives up a minute after that on its own clock. A failed
mint prints the runner's reason, which is always one of a fixed set of sentences. For each message
and what to do, see [Troubleshoot](/guides/get-a-kubeconfig#troubleshoot).

The command refuses a credential that is not the tier and shape it asked for, one sealed for
another request or cluster, and one that has already expired.

Backing calls: `POST /cli/clusters/{id}/kubeconfig`, then `GET /cli/clusters/{id}/kubeconfig/{mint}`
until the credential is ready. A ready credential is served once.

## `alethia cluster token`

Print a credential for `kubectl`. This is the exec plugin that the kubeconfig from
`alethia cluster kubeconfig` runs. You do not usually run it yourself.

```bash
alethia cluster token
```

| Input | Required | Default | Description |
|-------|----------|---------|-------------|
| `[cluster-id]` | No — at a terminal | The picker | The cluster id, a lowercase UUID as `cluster get` shows it. `kubectl` always passes it. Omit it at a terminal and the CLI asks which cluster, which is a way to check that your session can still mint. Without a terminal, it is required. |

The command takes no flags of its own. The global `--org` and `--token` flags apply.

**Stdout** carries one `client.authentication.k8s.io/v1` `ExecCredential` document and nothing
else: the token and its expiry. **Stderr** carries every error, after `alethia cluster token:`,
and `kubectl` shows that line. The command exits `0` when it printed a credential and `1`
otherwise. It never prompts: if your session expired, it fails and tells you to run
`alethia login`. It never prints the update notice.

### The cache

The command keeps each credential in a cache until 60 seconds before the credential expires. So
only the first `kubectl` call in each credential's lifetime waits for a new mint.

| Property | Value |
|----------|-------|
| Directory | `alethia/kubecache` in the user configuration directory: `~/.config` on Linux (or `$XDG_CONFIG_HOME`), `~/Library/Application Support` on macOS, `%AppData%` on Windows |
| Modes | Directory `0700`, files `0600`. A directory that others can read is tightened. A cache file that is a symlink, is owned by another user, or that others can read is refused, not replaced. On Windows the user profile's access control applies instead. |
| Files per cluster | The token and its expiry for each tier, the re-mint profile, and a lock file |
| Locking | One lock per cluster. If several `kubectl` calls start on an empty cache, the first one mints and the others wait for it, so there is one mint. |

### Re-minting

When the cache has no fresh credential, the command mints a new one, in the exec shape, with the
profile that `alethia cluster kubeconfig` recorded: the tier, the TTL and the organization. It
uses that organization even if your active organization changed since, unless you pass `--org`.
A cluster with no profile, for example a kubeconfig copied from another machine, gets the
read-only tier with a 1-hour TTL in the active organization, never the admin tier.

Each mint checks your permission again. So a person whose role changes, or who leaves the
organization, stops getting tokens when the current one expires.

## Accessing a cluster with kubectl

The **Kubeconfig** row is the command that writes a kubeconfig with **your own cloud CLI**, under
your own cloud login. Alethia does not issue a credential through this row: whether the command
works is your cloud account's decision. To get a kubeconfig through Alethia instead, use
[`alethia cluster kubeconfig`](#alethia-cluster-kubeconfig). In `-o json` output the same answer is the
`kubeconfig` object, with `command` and `note` fields.

Alethia builds the command from values the cluster's last successful deploy recorded, so it is
the same command the console's cluster card shows. Run it, then use `kubectl`:

<Tabs items={["AWS", "GCP", "Azure", "Alibaba Cloud", "Hetzner"]}>
  <Tab value="AWS">
    ```bash
    aws eks update-kubeconfig --name api-backend-production --region eu-west-1
    kubectl get nodes
    ```
  </Tab>
  <Tab value="GCP">
    ```bash
    gcloud container clusters get-credentials data-pipeline-staging --region us-east4 --project acme-data-prod
    kubectl get nodes
    ```

    For a zonal cluster, one deployed to a zone such as `us-east4-a`, the command names the zone
    instead of the region.
  </Tab>
  <Tab value="Azure">
    ```bash
    az aks get-credentials --resource-group rg-api-backend-production --name api-backend-production
    kubectl get nodes
    ```
  </Tab>
  <Tab value="Alibaba Cloud">
    Alethia does not record the ACK cluster ID yet, and ACK's kubeconfig API needs it. The
    **Kubeconfig** row names the cluster and its region instead. Find the cluster's ID in the ACK
    console, then call `DescribeClusterUserKubeconfig` with the `aliyun` CLI. Its `config` field
    is the kubeconfig. Or use [`alethia cluster kubeconfig`](#alethia-cluster-kubeconfig), which
    needs no ACK cluster ID.
  </Tab>
  <Tab value="Hetzner">
    Hetzner has no cloud CLI command for a kubeconfig, so the **Kubeconfig** row has none. The
    cluster's Talos admin configuration stays encrypted on the platform. Use
    [`alethia cluster kubeconfig`](#alethia-cluster-kubeconfig) instead: your runner mints a
    short-lived certificate for you.
  </Tab>
</Tabs>

When a value the command needs was not recorded, the row names the missing value instead of
printing a command with a guess in it. Redeploying the environment records it.
