# Cluster Commands

A cluster is what a project environment runs on. You do not create one here: provisioning an
environment creates it, and this group reads it back. The command is `alethia cluster` (singular)
with a `clusters` alias, so both forms work interchangeably.

<Callout type="info">
The CLI is a client of the same Console API. These commands call `/cli/clusters` with your
[CLI token](/reference/cli/authentication) and operate on the **active organization**, which you change with
`alethia org switch`. For one invocation, `alethia cluster list --org <id>` scopes the call to a
different organization instead — `--org` is a global flag, accepted on every command, and refused
with `403` if you are not a member of the organization you name.
</Callout>

## `alethia cluster list`

List every cluster across your projects — one row per project environment.

```bash
alethia cluster list
alethia clusters list
alethia cluster list -o json
```

The command takes no input of its own; only the [global flags](/reference/cli) apply.

| Column | Meaning |
|--------|---------|
| Project | The project and its environment — the same label `cluster get` titles its card with. |
| Cluster | The cloud's name for the cluster, or `—` before it is provisioned. |
| Version | The Kubernetes version. |
| Status | A glyph and the status, with the status message appended when a cluster is degraded or failed. |
| ArgoCD | `exposed` when a managed-ingress URL exists, `port-fwd` when access is by port-forward, `—` when the cluster is not provisioned yet. |
| Nodes | Min / desired / max node count. |
| Region | The cloud region. |
| Cost | The estimated monthly cost, rendered exactly as the console's billing pages render it. |

```
Project                   Cluster                 Version  Status    ArgoCD    Nodes  Region     Cost
api-backend (production)  api-backend-production  1.30     ● active  exposed   1/3/5  eu-west-1  $210.00/mo
data-pipeline (staging)   data-pipeline-staging   1.29     ● active  port-fwd  1/2/3  us-east4   $95.00/mo
```

At a terminal this is a navigable table; in a pipe, with `--no-input`, or with `-o json` / `-o csv`
it prints statically. Backing call: `GET /cli/clusters`.

## `alethia cluster get`

Show one cluster in full, including the command that gets you a kubeconfig and how to reach its ArgoCD.

```bash
alethia cluster get
alethia cluster get api-backend
alethia cluster get api-backend-production -o json
```

| Input | Required | Description |
|-------|----------|-------------|
| `[selector]` | No — at a terminal | Matches a project name, a cluster name, or a cluster id, case-insensitively. Falls back to a project-name substring. |

**Run it with no selector and the CLI asks which cluster**, listing every one you have with its
status. That is the whole reason the selector is optional: you never have to run `cluster list`
first and copy a name out of it.

The selector is required when a prompt could not work: with `--no-input`, with a piped stdin that
could never answer one, and with a redirected stdout that has no screen to draw one on. In each
case the command exits non-zero explaining what to pass. The last is the easy one to hit —
`alethia cluster get -o json > clusters.json` refuses rather than writing a form into your file.
A selector that matches **nothing** is an error too, not an empty screen —
`alethia cluster get typo || echo missing` prints `missing`.

A selector that matches **more than one** cluster — the usual case is one project with a production
and a staging environment — asks which you meant rather than picking for you. With `--no-input` it
refuses and names the candidates, so you can re-run with the cluster name or id, both of which are
unique.

```
╭─────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╮
│  A P I - B A C K E N D   ( P R O D U C T I O N )                                                                                                        │
│                                                                                                                                                         │
│  Status        ● active                                                                                                                                 │
│  Cluster       api-backend-production                                                                                                                   │
│  Version       K8s 1.30                                                                                                                                 │
│  Region        eu-west-1                                                                                                                                │
│  Nodes         1 / 3 / 5  (min/desired/max)                                                                                                             │
│  Est. cost     $210.00/mo                                                                                                                               │
│  Kubeconfig    aws eks update-kubeconfig --name api-backend-production --region eu-west-1                                                               │
│  ArgoCD        https://argocd.api-backend.example.com                                                                                                   │
│  ArgoCD admin  after the kubeconfig command above: kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d  │
│  GitOps        6/6 synced · 5/6 healthy · rev 9c1f0a3                                                                                                   │
│  Apps repo     github.com/acme/api-backend-apps                                                                                                         │
╰─────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╯
```

Only the fields a cluster actually has are shown: a cluster that is still provisioning has no name,
no version, no kubeconfig row and no ArgoCD block.

Backing calls: `GET /cli/clusters`, then `GET /cli/clusters/{id}` for the kubeconfig command and the
GitOps posture. The second one is best-effort — if it fails you still get the cluster, without the
Kubeconfig and GitOps lines.

### ArgoCD access

ArgoCD is installed on every provisioned cluster. The **ArgoCD** row is its URL where a managed
ingress exists, and a note to port-forward where the cloud does not have one yet.

The admin password is **never stored by Alethia** — it would be plaintext in the control-plane
database — so the card prints the command that reads it from the cluster's own initial-admin
secret. It is a `kubectl` command, so get a kubeconfig first (the **Kubeconfig** row, above it),
then run:

```bash
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d
```

Where there is no managed ingress, reach the UI through a port-forward first:

```bash
kubectl -n argocd port-forward svc/argocd-server 8080:443
```

### GitOps posture

The **GitOps** row summarises the cluster's ArgoCD applications: how many are synced, how many are
healthy, and the short revision they are deployed at. It reads `failed at <step>` when the last
deploy failed, and `unknown (no snapshot yet)` when there is no trustworthy reading — which is a
different statement from "nothing is deployed", and deliberately not rendered as one.

## `alethia cluster kubeconfig`

Get a short-lived kubeconfig for a cluster without a cloud login of your own. A runner in the
cluster's network mints the credential and seals it to a one-time key that this command makes.
Only this machine can open the result.

```bash
alethia cluster kubeconfig
alethia cluster kubeconfig api-backend
alethia cluster kubeconfig api-backend --admin --ttl 4h
alethia cluster kubeconfig api-backend --output api-backend.kubeconfig
alethia cluster kubeconfig api-backend --static --output -
```

| Input | Required | Description |
|-------|----------|-------------|
| `[selector]` | No — at a terminal | The same selector as `cluster get`. Omit it and the CLI asks which cluster. |
| `--admin` | No | Get the admin tier. Owners and admins only. The default is read-only. |
| `--ttl` | No | How long the credential lasts, from `15m` to `8h`. The default is `1h`. |
| `--static` | No | Write a file that holds the credential and stops working at its TTL. |
| `--merge` | No | Merge into `$KUBECONFIG` or `~/.kube/config`. This is the default. |
| `--output` | No | Write a separate file instead of merging. `-` prints the kubeconfig. |

By default the command merges the context `alethia-<project>-<env>` into your kubeconfig and makes
it the current context. It replaces an older entry with the same name and leaves all other entries
as they are. The file gets mode `0600`. In this command, `--output` takes a file path, not the
`table`/`json`/`csv` format, and `--output -` is the only way the credential goes to stdout. All
other messages go to stderr.

On AWS, GCP and Azure the kubeconfig runs `alethia cluster token` to get each token, so `kubectl`
keeps working after a token expires. Hetzner and Alibaba Cloud issue certificates, so their
kubeconfig is always static and stops working at its TTL. If the cluster's API endpoint is private,
the command tells you that `kubectl` needs network access to it, for example through a VPN or a
bastion host.

The mint runs as a job on your organization's runner, so a runner must be online. Backing calls:
`POST /cli/clusters/{id}/kubeconfig`, then `GET /cli/clusters/{id}/kubeconfig/{mint}` until the
credential is ready.

## `alethia cluster token`

Print a credential for `kubectl`. This is the command that the kubeconfig from
`alethia cluster kubeconfig` runs. You do not usually run it yourself.

```bash
alethia cluster token
```

| Input | Required | Description |
|-------|----------|-------------|
| `[cluster-id]` | No — at a terminal | The cluster id. `kubectl` always passes it. Omit it at a terminal and the CLI asks which cluster. |

The command prints one `ExecCredential` document on stdout. It keeps the credential in a cache
under the CLI's configuration directory (directory mode `0700`, file mode `0600`) until 60 seconds
before the credential expires. Thus only the first `kubectl` call in each credential's lifetime
waits for a new mint. If several `kubectl` calls start at the same time, they share one mint. The
command refuses a cache file that other users can read. It never prompts: if your session expired,
it fails and tells you to run `alethia login`.

## Accessing a cluster with kubectl

The **Kubeconfig** row is the command that writes a kubeconfig with **your own cloud CLI**, under
your own cloud login. Alethia does not issue a kubeconfig or any credential here: whether the
command works is your cloud account's decision. In `-o json` output the same answer is the
`kubeconfig` object, with `command` and `note` fields.

Alethia builds the command from values the cluster's last successful deploy recorded, so it is
the same command the console's cluster card shows. Run it, then use `kubectl`:

<Tabs items={["AWS", "GCP", "Azure", "Alibaba Cloud", "Hetzner"]}>
  <Tab value="AWS">
    ```bash
    aws eks update-kubeconfig --name api-backend-production --region eu-west-1
    kubectl get nodes
    ```
  </Tab>
  <Tab value="GCP">
    ```bash
    gcloud container clusters get-credentials data-pipeline-staging --region us-east4 --project acme-data-prod
    kubectl get nodes
    ```

    For a zonal cluster, one deployed to a zone such as `us-east4-a`, the command names the zone
    instead of the region.
  </Tab>
  <Tab value="Azure">
    ```bash
    az aks get-credentials --resource-group rg-api-backend-production --name api-backend-production
    kubectl get nodes
    ```
  </Tab>
  <Tab value="Alibaba Cloud">
    Alethia does not record the ACK cluster ID yet, and ACK's kubeconfig API needs it. The
    **Kubeconfig** row names the cluster and its region instead. Find the cluster's ID in the ACK
    console, then call `DescribeClusterUserKubeconfig` with the `aliyun` CLI. Its `config` field
    is the kubeconfig. Or use [`alethia cluster kubeconfig`](#alethia-cluster-kubeconfig), which
    needs no ACK cluster ID.
  </Tab>
  <Tab value="Hetzner">
    Hetzner has no cloud CLI command for a kubeconfig, so the **Kubeconfig** row has none. The
    cluster's Talos admin configuration stays encrypted on the platform. Use
    [`alethia cluster kubeconfig`](#alethia-cluster-kubeconfig) instead: your runner mints a
    short-lived certificate for you.
  </Tab>
</Tabs>

When a value the command needs was not recorded, the row names the missing value instead of
printing a command with a guess in it. Redeploying the environment records it.
