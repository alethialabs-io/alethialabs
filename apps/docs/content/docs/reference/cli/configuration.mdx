alethia stores configuration and credentials under the OS user-config directory (`~/.config/alethia`
on Linux, `~/Library/Application Support/alethia` on macOS — the location follows Go's
`os.UserConfigDir`). Inspect the resolved values and on-disk paths at any time with
[`alethia config`](#alethia-config).

## File Locations

| File | Purpose |
|------|---------|
| `~/.config/alethia/credentials.json` | CLI authentication tokens (access + refresh JWT) |
| `~/.config/alethia/config.json` | Active organization context (id, name, slug) |

## credentials.json

Created by `alethia login`. Contains JWT tokens for API authentication:

```json
{
  "access_token": "eyJ...",
  "refresh_token": "eyJ...",
  "user_email": "you@example.com"
}
```

The access token is refreshed automatically before each API call if expired. See [Authentication](/reference/cli/authentication).

## config.json

Created/updated by `alethia org switch`. Records the active organization, which is sent as the
`X-Alethia-Org` header on every request:

```json
{
  "active_org_id": "org_123",
  "active_org_name": "Acme",
  "active_org_slug": "acme"
}
```

Clear it with `alethia config clear-context`.

## `alethia config`

Show the resolved CLI configuration: the control-plane URL (`ALETHIA_WEB_ORIGIN`), the active
organization context, and the on-disk paths of the credentials and config files.

```bash
alethia config
```

```
Field          Value
web origin     https://app.alethialabs.io (config)
active org     Acme
active org id  org_123
credentials    /Users/you/Library/Application Support/alethia/credentials.json
config         /Users/you/Library/Application Support/alethia/config.json
```

`alethia config -o json` emits the same values as a JSON object. The command reads local files
only: it sends nothing.

## `alethia config clear-context`

Remove the active organization from the config file. After it, commands act in your personal
scope until you choose an organization again with `alethia org switch`.

```bash
alethia config clear-context
```

It changes only the local config file. No organization and no membership is touched. When no
organization was active, it changes nothing and says so. With `-o json` it prints the result
object every command that changes something prints: `action` is `updated` or `unchanged`, and
`object` names the organization that was active.

## Config keys

These are the keys `alethia config get` reads. `alethia config set` writes the ones marked
`config set`; a key set anywhere else says which command owns it, because a value you can read and
cannot write needs to tell you what does write it.

{/* configkeys */}

| Key | What it is | How to set it |
| --- | --- | --- |
| `web-origin` | The control-plane URL the CLI talks to (hosted, self-hosted or dev). | `config set` |
| `active-org` | The organization every request is scoped to, sent as X-Alethia-Org. | `alethia org switch` |

`active-org` is deliberately read-only. Setting it by name would have to resolve that name to an id
and a slug — which is a server round-trip, and that round-trip is `alethia org switch`. A
`config set active-org` that wrote only the name would leave the id stale and scope every subsequent
request to the *previous* organization.

The underscore spellings (`web_origin`, `active_org`) are accepted too, because that is how the keys
appear in `config.json` and people type what they have read.

## `alethia config set`

```bash
alethia config set                                       # pick the key, edit the current value
alethia config set web-origin https://alethia.internal.example.com   # the same, unattended
```

Run with no arguments on a terminal, `config set` asks for both:

{/* fieldspec: alethia config set */}

| Field | What it is | Set without the form |
| --- | --- | --- |
| Config key | Which value to change | `[key]` |
| Value | The new value; the form describes it with the chosen key's own summary | `[value]` |

The value field is pre-filled with the **stored** value, so the form is an edit rather than a
re-type, and it is validated by the same rule `config set` applies — a value the form accepts is
never refused a moment later. It shows what is stored rather than what is in effect, because that
is what the write replaces: if `ALETHIA_WEB_ORIGIN` is set, the form says so and still seeds the
file's value, so pressing Enter cannot overwrite it with the environment's.

With `--no-input` both arguments are required. Without them the command exits `9` and names the
form that works; it does not guess. A key the CLI does not have, a key another command owns and a
value that is not a URL each exit `8`, before anything is written.

Setting a key to the value it already has changes nothing and says so. With `-o json`,
`config set` prints the result object every command that changes something prints:

```json
{
  "id": "web-origin",
  "kind": "config",
  "action": "updated",
  "job": null,
  "dry_run": false,
  "object": {
    "key": "web-origin",
    "value": "https://alethia.internal.example.com",
    "previous": "https://alethialabs.io"
  }
}
```

`action` is `unchanged` when the stored value was already this one.

<Callout type="info">
`ALETHIA_WEB_ORIGIN` **outranks** the config file. If it is set to a different URL,
`alethia config set web-origin` says so after saving, because otherwise the write appears to succeed
and every subsequent command keeps talking to the environment's origin. The warning is on stderr,
and in the `-o json` result it is the `shadowed` field.
</Callout>

## `alethia config get`

```bash
alethia config get web-origin     # one value
alethia config get                # every key
alethia config get -o json
```

`alethia config get` prints the bare value in the default table format — so
`$(alethia config get web-origin)` works — and key/value pairs under `-o json` or `-o csv`.

An unset key, such as `active-org` before you have picked an organization, prints as `—` in the
table and as an empty string under `-o json` and `-o csv`. The dash is for a person reading a
column; a script tests the machine formats for emptiness.

## `alethia export`

Write a project as an [`alethia.yaml`](/reference/cli/plan-and-apply#alethiayaml): the file
`alethia plan` and `alethia apply` read. Use it when you built the project in the console and now
want it in git, or want to copy one environment into another project.

```bash
alethia export shop --env prod > alethia.yaml   # one environment, to stdout
alethia export shop --all --out alethia.yaml    # every environment, to a file
alethia plan                                    # nothing to change
```

| Flag | Default | Description |
|------|---------|-------------|
| `--env` | _(asked, or the only one)_ | The environment to export, by name or id. |
| `--all` | off | Export every environment. The default environment is written first. |
| `--out` | _(stdout)_ | Write the file here instead of stdout. |
| `--force` | off | Replace `--out` if the file already exists. Without it, an existing file is refused. |
| `--format` | `yaml` | The document to write. `yaml` is `alethia.yaml`. `console-json` is the console's design document; see [The console's design document](#the-consoles-design-document). |

A project with more than one environment needs `--env` or `--all`. On a terminal, `export` asks
which one. With `--no-input`, it exits `9` and names both flags and every environment. The project
name is optional on a terminal, where you pick it from a list; with `--no-input` it is required.

The file is the command's output, on stdout or in the file `--out` names. Everything else is on
stderr: the line that says which file was written, and the list of what was left out. `export`
writes a document, so `-o json` does not change it.

| Exit code | Meaning |
| --- | --- |
| `0` | The file was written. |
| `6` | The project, or the environment `--env` names, does not exist. The error lists the ones that do. |
| `7` | `--out` names a file that exists and `--force` was not passed, or it names a symbolic link. |
| `8` | The flags cannot be combined, or `--format` is not a format. |
| `9` | A value is missing and nothing can ask for it. |

### The schema line

The first line of the file is a comment that names the file's JSON Schema:

```yaml
# yaml-language-server: $schema=https://alethialabs.io/docs/schemas/alethia-yaml/v1.json
```

An editor with a YAML language server reads it and then checks and completes the file as you type:
the keys, the stages and the placements. `alethia init` and `alethia up` write the same line into
the file they author. Add it to a file you wrote by hand. The schema
describes the keys of the file. It leaves the fields of a component open, because they differ by
kind and by cloud; `alethia plan` checks those against the control plane.

The file holds the project's cloud account (by its label), the region, the OpenTofu version, and
for each environment its stage, placement, namespace, components and add-ons. Each component
carries the settable fields described below. Each add-on carries its version pin, its delivery mode
and its non-secret settings. The output is the same on
every run: environments, components and add-ons are in a fixed order, so a re-export shows only
what changed.

### The console's design document

`--format console-json` writes a different document: the design document of **one** environment, as
JSON. It is the nested shape the console's design form holds, and the one
[`alethia project design apply`](/reference/cli/project) accepts.

```bash
# Print the default environment's design document
alethia export my-project --format console-json

# Round-trip it: export, edit, apply
alethia export my-project --env staging --format console-json --out staging.json
alethia project design apply -p my-project -e staging -f staging.json --dry-run
alethia project design apply -p my-project -e staging -f staging.json
```

It takes `--env` (by name, stage or id) and not `--all`. Without `--env` the server exports the
project's default environment. With `-o json` the document is wrapped in an object that also
carries its file name and its format.

<Callout type="info">
  `alethia config export` is the old name of this command. It still runs, prints one line on stderr
  that names the new command, and will be removed in a later release. One difference remains: the
  old name replaces an existing `--out` file without being asked, as it always did, and
  `alethia export` needs `--force`.
</Callout>

### What is written, and what is left out

`export` never writes a value that Alethia stores as a secret, a credential setting, or an add-on's
Advanced values override. It works from an allow-list: it writes a stored value only when Alethia
publishes that value as a plain, non-secret setting.

<Callout type="warn">
A credential that someone typed into an ordinary setting, such as a database user name or a
parameter list, is written as typed. Review the file before you commit it.
</Callout>

| Part of the file | Written only when |
|------------------|-------------------|
| A component field | The [published component schema](/reference/cli/project) declares the field, does not mark it `writeOnly` or `format: password`, and its name is not a credential name. The value must be a string, number or boolean, or a list or map of them. |
| A `provider_config` key | The key is a [settable template knob](/reference/cli/project#setting-template-knobs) of that component kind on the component's cloud. Credential knobs, such as a secret's `value` or `rds_extra_credentials`, are never settable, so they are never written. |
| An add-on setting | The add-on catalog declares the setting, does not name it a secret, and the value is a single string, number or boolean. The catalog's secret names and the add-on's own secret names are both checked, in any letter case, so `APITOKEN` counts as the secret `apiToken`. A list or map value is left out. |

Some values are always left out:

- an add-on's **Advanced values override**, because it is free-form Helm values and can hold a
  password. To manage the override from git, put it in a file next to `alethia.yaml` and name it with
  [`values_file:`](/reference/cli/plan-and-apply#where-a-values-file-can-come-from);
- a component's own `cloud_identity_id`, which is a reference to a credential;
- a server field such as an endpoint or a status, which the schema does not declare.

`export` then checks each value that passed the allow-list for the shape of a credential and
leaves out any value that matches:

- a URL with a user name or password, such as `https://x-access-token:…@github.com/acme/apps`;
  each URL in a list separated by commas, semicolons or spaces is checked;
- a URL with a credential in its query string, such as `?token=…`, `?access_token=…` or a signature;
- a `Bearer …` or `Basic …` value, or a connection string with a password, such as
  `user:pw@tcp(db)/app`;
- a map that has, at any depth, a key whose name contains `secret`, `pass`, `pwd`, `auth`,
  `apikey`, `token`, `credential`, `privatekey` or `accesskey`. Separators are ignored, so `db_pass`,
  `api_key` and `private-key` match. A name/value pair such as `{name: master_password, value: …}`
  counts too. Names are compared after Unicode NFKC normalization, with Cyrillic and Greek
  look-alikes read as Latin letters.

`--out` writes a new file, and fails if a file already exists at that path. `--force` replaces the
file and keeps its permissions. `export` never writes through a symbolic link, with or without
`--force`, and a write that fails leaves no partial file.

The file pins `iac.version` to the OpenTofu version that the project uses now. A comment at the top
of the file says so. Delete the line to use the server's default version.

A field that the file leaves out keeps its stored value: `apply` never clears it. A comment at the
top of the file lists each thing that is not in it, and `export` prints the same list on stderr.
The list also names the environments you did not export, the add-ons that are disabled, the
components that are destroyed, and attached BYO charts and BYO IaC, which `alethia.yaml` cannot
describe yet.

An ephemeral environment is exported with `lifecycle: ephemeral`. A persistent environment has no
`lifecycle` line, because `persistent` is the default.

## Runner Credentials

The `alethia` CLI does not store Runner credentials. A self-operated Runner is a
separate binary configured entirely through environment variables — register the
Runner in the console (or via the API) to obtain a `runner_id` / `runner_token`,
then set `ALETHIA_RUNNER_ID` and `ALETHIA_RUNNER_TOKEN` on the host. See
[Self-Operated Runners](/guides/runners/self-operated) for the full env contract.

## Environment Variables

| Variable | Default | Purpose |
|----------|---------|---------|
| `ALETHIA_WEB_ORIGIN` | `https://alethialabs.io` (compiled-in default) | Override the Alethia API base URL |
| `ALETHIA_NO_UPDATE_CHECK` | unset | Disable the daily interactive new-release notice |

These are the CLI configuration environment variables. Runner processes use a separate runtime
environment documented with the runner deployment method.

## Global Flags

Four persistent flags are available on every command:

| Flag | Default | Description |
|------|---------|-------------|
| `-o, --output <table\|json\|csv>` | `table` | Output format. `json`/`csv` print static, machine-readable output, and never open an interactive table. |
| `--no-input` | off | Disable interactive prompts; fail instead of prompting. Auto-enabled when stdin is not a terminal. A form is refused separately when the stream it would draw on is redirected, so `alethia … 2> log` still renders the rich table. |
| `--token <token>` | unset | Service-account token for non-interactive use. Prefer the `ALETHIA_TOKEN` environment variable in CI: a flag value lands in the process table and in shell history. |
| `--org <id>` | the active org | Organization to act in for this invocation, instead of the active one. Sent as the `X-Alethia-Org` header on every request, and used as the org in the request path of `members` and `teams`. It selects a scope rather than granting one: the control plane refuses it with `403` when you are not a member of that organization. Under a service token it must name the token's OWN organization — a different one is refused with `403`, never quietly ignored, so a pipeline cannot believe it is acting on one org while every write lands in another. |

See [Identity & Global Options](/reference/cli/identity) for output-format examples and scripting tips.

## Control-Plane URL Resolution

The control-plane URL resolves in precedence order: the `ALETHIA_WEB_ORIGIN` environment
variable, then the persisted config (`alethia config set web-origin <url>`), then a compiled-in
default (`https://alethialabs.io`). The hosted default is a constant baked into the binary, so the
production build needs no configuration (GoReleaser's `ldflags` inject only the CLI version, not the
URL). For development or a self-hosted control plane, override it with the environment variable:

```bash
export ALETHIA_WEB_ORIGIN=http://localhost:3000
alethia login  # authenticates against local server
```
