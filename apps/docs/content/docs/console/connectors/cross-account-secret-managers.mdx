# Cross-Account Secret Managers

A Project's workloads sometimes need secrets that live in a **different** cloud account than the cluster — a central AWS Secrets Manager account, a shared GCP Secret Manager project, an Azure Key Vault in another subscription, or an Alibaba KMS Secrets Manager in another RAM account. The **cross-account secret manager** connectors let the cluster read those secrets **keylessly**: no access key is created, and Alethia never holds admin in the account that owns the secrets.

| Connector | Reads from | Auth method |
|-----------|-----------|-------------|
| **AWS Secrets Manager (cross-account)** | Secrets Manager in another AWS account | `iam_role` |
| **GCP Secret Manager (cross-project)** | Secret Manager in another GCP project | `service_account` |
| **Azure Key Vault (cross-subscription)** | Key Vault in another Azure subscription (same tenant) | `service_principal` |
| **Alibaba KMS Secrets Manager (cross-account)** | KMS Secrets Manager in another RAM account | `ram_role` |

## How it works

Each cluster runs the [External Secrets Operator](/console/design-project/secrets). It already authenticates to the cluster's own cloud with the cluster's workload identity (IRSA on AWS, Workload Identity on GCP, workload identity on Azure, RRSA on Alibaba). A cross-account connector points that same identity at a secret manager in another account through a **trust grant the secret owner creates**:

1. **You bootstrap a least-privilege read grant** in the account that owns the secrets, using a small OpenTofu module Alethia ships. The grant trusts your cluster's identity and allows **read only**.
2. **You paste the grant's references** (a role ARN, a project id, a vault URL) into the connector. No key is stored — only references.
3. **The operator reads across the boundary.** Alethia renders an additional `ClusterSecretStore` that resolves secrets from the other account, alongside the cluster's native store.

This is the same [zero-credential model](/concepts/security) the rest of Alethia uses: the secret owner grants the least privilege, and the control plane only references it.

## Set up a cross-account connector

Each connector needs a one-time bootstrap in the account that **owns the secrets**. The OpenTofu modules live in the Alethia repository under `infra/connector/<cloud>/secrets-xacct/`, each with a README.

### AWS Secrets Manager

Run `infra/connector/aws/secrets-xacct` in the secrets account. It creates a read-only role that trusts your cluster's external-secrets identity and grants `secretsmanager:GetSecretValue` on the secrets you name. Enter the printed **Target Role ARN**, the **target account id**, and the **region** in the connector.

Name the secret ARNs you intend to share. The module has no wildcard fallback, so it refuses to apply rather than granting read on every secret in the account.

You can also set an `external_id` on the module to require an `sts:ExternalId` on the assume. If you do, enter the same value in the connector's **External ID** field: the operator sends it with the assume, and AWS rejects the read when the two disagree. This control is AWS-only — the other three clouds bind the grant to a specific principal instead, so there is nothing equivalent to set.

### GCP Secret Manager

Run `infra/connector/gcp/secrets-xacct` in the secrets project. It grants your cluster's external-secrets service account `roles/secretmanager.secretAccessor` on each secret you name. Enter the **target project id** in the connector.

### Azure Key Vault

Run `infra/connector/azure/secrets-xacct` in the subscription that owns the vault. It assigns your cluster's workload identity the **Key Vault Secrets User** role on the target vault. Enter the **target subscription id** and the **vault URL** in the connector.

### Alibaba KMS Secrets Manager

Run `infra/connector/alibaba/secrets-xacct` in the secrets account. It registers your cluster's OIDC issuer as a RAM OIDC provider and creates a read-only KMS role that trusts your cluster's external-secrets service account. Enter the printed **Target Role ARN** and **Target OIDC Provider ARN** in the connector.

## What is not supported

<Callout type="warn">
Two combinations are out of scope, by cloud-platform limits rather than choice:

- **Hetzner** has no cloud secret manager. Use the [HashiCorp Vault connector](/console/connectors/pluggable) for secrets on Hetzner.
- **Azure cross-tenant** is not available keyless. An Azure managed or workload identity cannot be used across tenants. The Azure connector reads across **subscriptions within one tenant**; a vault in a different tenant needs an app registration and federated credential in that tenant, which is outside this connector.
</Callout>
