title: Set up alerts
description: Send platform events to Slack, Microsoft Teams, Discord, Google Chat, Mattermost, Rocket.Chat, PagerDuty, a webhook or email, with policies that choose what fires.
---

Get notified when a deploy fails, a runner goes offline, or someone changes a role. A **channel** is
where a notification goes. A **policy** chooses which events go to which channels. Every
notification is logged as a **delivery** under **Activity**.

## Before you begin

- Your organization is on the Pro or Enterprise plan. On other plans, the Alerts card on the overview
  says that alerting needs Pro. Security and access events (see [Events](#events)) need Enterprise.
- Your role can manage alerts.
- On a self-hosted console, `ALETHIA_CRED_ENCRYPTION_KEY` is set (a stable 32-byte base64 value,
  for example from `openssl rand -base64 32`). Every channel except email stores a secret, and
  without the key those channels are disabled. A console with pluggable connectors already has it.

## Channels

Add the channels first, so that a policy has somewhere to send.

1. Open **Alerts → Channels** and select **Add channel**.
2. Pick the transport and give the channel a name.
3. Paste the destination from the table. The sheet's **Where to find this** says where the
   service shows it.
4. Select **Add channel**. Alethia sends a sample event to check the destination, and adds the channel
   only when it arrives.

| Transport | You paste | Where it comes from |
| --- | --- | --- |
| Slack | Payload URL | Slack: Apps → Incoming Webhooks → Add to a channel |
| Microsoft Teams | Payload URL | The channel's Workflows or Incoming Webhook connector |
| Discord | Payload URL | Channel → Edit → Integrations → Webhooks → New Webhook |
| Google Chat | Payload URL | The space's Apps & integrations → Webhooks |
| Mattermost | Payload URL | Integrations → Incoming Webhooks → Add |
| Rocket.Chat | Payload URL | Admin → Integrations → New → Incoming Webhook |
| Webhook | Payload URL, and an optional signing secret | Any HTTPS endpoint you run |
| PagerDuty | Routing key | The Integration Key of an Events API v2 integration |
| Email | Recipients, separated by commas | — |

There is no Alethia app to install in Slack or Teams, and no OAuth. A payload URL or routing key
is a secret: anyone who has it can post to your channel. Alethia encrypts it. If one leaks, replace
it in the service.

**Webhook.** Alethia POSTs JSON `{ channel, event, sent_at }`. With a signing secret, each request
carries `X-Alethia-Signature: sha256=<HMAC-SHA256 of the body>`. Compute the HMAC over the raw body
and compare. A webhook needs no third-party account, so it is the quickest way to test alerting.

**Email** needs no secret and no encryption key. It is sent through Amazon SES (see
[Email](/self-host/email)). Without SES, the email is written to the server log instead.

To check a channel later, select **Verify** (or **Re-verify**) on it. A check writes no delivery to
**Activity**. Deleting a channel keeps its delivery history.

## Policies

1. Open **Alerts → Policies** and select **New policy**.
2. Give it a **Name**, such as `Production deploy failures`, and an optional description.
3. Under **Events**, pick one or more events.
4. Set the conditions, all optional:
   - **Minimum severity**: drop events below `info`, `warning` or `critical`.
   - **Scope filters**: limit to some **Projects**, **Job types**, **Resource types** or **Actions**.
   - **Throttle & grouping**: **Notify at most once per** a time window, so repeats of the same
     event become one notification.
5. Under **Routing**, turn on the channels to notify. A policy can notify several channels, and a
   channel can serve several policies.
6. Select **Create policy**.

A disabled policy keeps its settings and sends nothing.

### Events

Events come from the platform as things happen. You do not wire them up. Every event has a severity,
which the message shows, for example as a Slack emoji, or as a field that a webhook can route on.

| Category | Events that fire today | Listed as soon |
| --- | --- | --- |
| Deploy & drift | Deploy started, succeeded or failed; job cancelled; destroy requested or completed; possible orphaned resources; auto-teardown gave up; cluster missing; environment status conflict | Drift detected |
| Policy (PDP) | Action denied, sensitive action allowed, role permissions changed | Policy overridden |
| Access & roles (RBAC) | Grant added or revoked; role created, changed or deleted; SSO provider updated or removed | — |
| Members | Member invited, joined or removed | Member suspended |
| Cloud identities | Identity connected or revoked; credential expiring or failed | Credentials rotated |
| Cost | Budget threshold crossed | Spend spike, overage started |
| Workers & runners | Worker unhealthy (a runner went offline) | Worker stalled, runner minutes exhausted |
| Authentication | — | SSO sign-in failed, new-device sign-in, sign-in blocked |
| Platform health | Background loop degraded or recovered, and other platform warnings | — |
| Support | Case opened, replied, resolved, reopened or closed | Case assigned |

Events marked soon can be chosen now, and start to fire when they ship. The **Policy (PDP)** and
**Access & roles** events need the Enterprise plan: on Pro you can pick them, but nothing is sent.

## Activity

**Alerts → Activity** lists every notification: the event, the channel, the status, the attempts and
any error. A delivery goes from `pending` to `sent`. One that fails is `failed`, and Alethia retries
it with backoff. After the last retry it is `dead`. You do not need to schedule the retries.

## Check that it worked

Trigger an event that a policy watches, such as a plan that you cancel. A `sent` row appears under
**Activity**, and the message arrives in the channel.
