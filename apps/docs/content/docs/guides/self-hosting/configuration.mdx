# Configuration

All configuration is environment variables in `.env`. The installer creates `.env`
from `.env.example` and generates every instance secret; the rest you set. Internal
service URLs (Postgres, SeaweedFS) are wired by compose — you don't set those.

## Ingress

| Key | Notes |
|---|---|
| `ALETHIA_DOMAIN` | Your domain; Caddy gets TLS for it. Empty → plain HTTP on `:80`. |
| `ALETHIA_ACME_EMAIL` | Let's Encrypt contact email. |
| `NEXT_PUBLIC_APP_URL` | Public origin, e.g. `https://alethia.example.com`. |
| `ALETHIA_TRUSTED_IP_HEADER` | Single-value client-IP header that your ingress overwrites. Defaults to `cf-connecting-ip`. |

The bundled Caddy configuration overwrites `cf-connecting-ip` before it forwards a request.
If you use another ingress, set `ALETHIA_TRUSTED_IP_HEADER` to a header that ingress controls.
Strip any value supplied by the client, set the real client address, and keep the app container
unreachable from the public network. Production authentication returns `503` when the header is
missing or is not one valid IPv4 or IPv6 address. This refusal prevents all users from sharing one
rate-limit bucket.

## Instance secrets (generated by the installer)

Every instance secret is required and generated per install. The list, with the
command that makes each value, is `deploy/selfhost/secrets.manifest`. You do not
type these values:

- The installer generates each one on a first install. When you run it again to
  upgrade, it adds any secret your `.env` does not have yet. It never changes a
  value that is set.
- `.env.example` leaves each one empty. `docker compose` stops before any
  container starts when one is empty, and names the variable.
- In production, the console refuses to start when one of them holds a template
  placeholder. The error names the variable and the command that generates a value.

| Key | What it protects |
|---|---|
| `BETTER_AUTH_SECRET` | Signs sessions and cookies. |
| `CLI_JWT_SECRET` | Signs CLI and runner tokens. The runner reads it too. |
| `ALETHIA_DB_PASSWORD` / `ALETHIA_APP_DB_PASSWORD` | The two bundled Postgres roles. |
| `ALETHIA_CRED_ENCRYPTION_KEY` | AES-256-GCM key that encrypts api-key [connector](/guides/connectors/pluggable) secrets and alert-channel webhooks at rest. |
| `OPENFGA_DB_PASSWORD` | The OpenFGA Postgres (the `enterprise` compose profile). |
| `ALETHIA_STORAGE_ACCESS_KEY_ID` / `ALETHIA_STORAGE_SECRET_ACCESS_KEY` | The bundled object store. Compose builds the SeaweedFS identity from these two values. |
| `ALETHIA_SNAPSHOT_HMAC_KEY` | Signs a job's configuration snapshot when the job is queued. The console checks it when a runner claims the job. |
| `ALETHIA_CRON_SECRET` | Bearer token for the maintenance endpoints and the detailed `/api/health` view. |
| `ALETHIA_RUNNER_BOOTSTRAP_TOKEN` | Shared token the bundled runner presents to register itself. |
| `ALETHIA_OIDC_SIGNING_KEY` | Signs the workload-identity tokens that keyless AWS, GCP, Azure and Alibaba connectors use. |
| `ALETHIA_RECEIPT_SIGNING_KEY` | Signs evidence receipts. |

### Rotate a secret

Run the rotation script on the install box. It needs only a shell, `openssl` and
`docker compose`. It does not need Node.js.

```sh
sh /opt/alethia/deploy/selfhost/rotate-secret.sh ALETHIA_CRON_SECRET
```

The script generates a new value, writes it to `.env` and restarts the services
that read it. Some secrets need extra steps, and the script does those too:

- `ALETHIA_CRED_ENCRYPTION_KEY`: the current key stays in the keyring as
  `ALETHIA_CRED_ENCRYPTION_KEY_<id>`. The new key gets the next key ID. Then the
  script encrypts every stored secret again with the new key, inside the
  `migrate` image. The console keeps working during the rotation. Remove the old
  key from `.env` after you have checked your connectors and alert channels.
- `ALETHIA_OIDC_SIGNING_KEY`: the current key is kept as
  `ALETHIA_OIDC_SIGNING_KEY_PREVIOUS`. The issuer keeps publishing it until the
  tokens it signed expire.
- The database passwords: the script changes the role's password in Postgres
  first, then writes `.env`.
- The storage keys: the script recreates the object store with the new identity.

Run `sh /opt/alethia/deploy/selfhost/rotate-secret.sh --list` to see every name.

## Database & storage

Defaults target the bundled `postgres` + `seaweedfs`. To use a managed Postgres or
S3/R2 instead, point `ALETHIA_DATABASE_URL` / `ALETHIA_STORAGE_*` at them and set
`ALETHIA_STORAGE_AUTO_CREATE_BUCKETS=false`.

| Key | Notes |
|---|---|
| `ALETHIA_DB_USER` / `ALETHIA_DB_NAME` | bundled Postgres user/db |
| `ALETHIA_STORAGE_ENDPOINT` | S3 endpoint (bundled SeaweedFS by default) |
| `ALETHIA_STORAGE_ACCESS_KEY_ID` / `_SECRET_ACCESS_KEY` | Instance secrets (see above). The bundled SeaweedFS reads its identity from them. For managed S3/R2, set them to that service's credentials. |

## Email (SMTP / SES)

Transactional email is pluggable. The transport is chosen by `EMAIL_PROVIDER` when
set (`smtp` | `ses`), else auto-detected from whichever provider's
credentials are present, in precedence order **SMTP → SES**. With none
configured, sign-in/account emails are logged to the console instead of sent (a
fresh install works with zero email setup). From-addresses must be verified sending
identities/domains for the chosen provider.

**Generic SMTP** — bring any provider (Postmark, Mailgun, SES-SMTP, a local Mailpit):

| Key | Notes |
|---|---|
| `SMTP_HOST` | SMTP server host. Selects SMTP. |
| `SMTP_PORT` | Default `587`. |
| `SMTP_USER` / `SMTP_PASS` | Optional auth credentials. |
| `SMTP_SECURE` | Implicit TLS on connect. Defaults to `true` on port 465, else `false`. |

**AWS SES** — set `ALETHIA_SES_REGION` to select it (requires SES production access
to mail arbitrary recipients):

| Key | Notes |
|---|---|
| `ALETHIA_SES_REGION` | SES region, e.g. `eu-central-1`. Selects SES. |
| `ALETHIA_SES_ACCESS_KEY_ID` / `_SECRET_ACCESS_KEY` | Optional; omit to use the AWS default credential chain (IAM role / `AWS_*`). |
| `ALETHIA_SES_AUTH_CONFIG_SET` / `_GENERAL_CONFIG_SET` | Optional. The configuration set each stream sends through, so its bounce and complaint events reach SNS. |
| `ALETHIA_SES_EVENTS_TOPIC_ARNS` | The exact SNS topic ARNs, comma-separated, that `/api/webhooks/ses` accepts. Unset: the webhook refuses every message. |

**All providers:**

| Key | Notes |
|---|---|
| `EMAIL_PROVIDER` | Optional. Pins the transport (`smtp` \| `ses`); omit to auto-detect. Any other value, including the removed `resend`, is refused. |
| `AUTH_EMAIL_FROM` | Auth/security from address, e.g. `Alethia <no-reply@auth.yourdomain>` (quote it). |
| `EMAIL_FROM` | Product/general from address; falls back to `AUTH_EMAIL_FROM`. |

## OAuth providers (optional)

Only the providers you configure appear on the sign-in screen.

| Key |
|---|
| `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` |
| `GITLAB_APPLICATION_ID` / `GITLAB_SECRET` |
| `BITBUCKET_KEY` / `BITBUCKET_SECRET` |

Set each provider's callback URL. GitHub and Google are native social providers and use
`https://<your-domain>/api/auth/callback/<provider>`. GitLab and Bitbucket are registered
through the generic OAuth plugin and use `https://<your-domain>/api/auth/oauth2/callback/<provider>`.

## Cloud connectors (optional)

| Key | Default | Notes |
|---|---|---|
| `NEXT_PUBLIC_CONNECTOR_ASSETS_ORIGIN` | your `NEXT_PUBLIC_APP_URL` | Origin that serves the connector setup files the AWS, GCP, Azure and Alibaba connect flows hand out (`alethia-{aws,gcp,azure,alibaba}-setup.sh`, `alethia-bootstrap.yaml`). A self-managed instance serves them itself: the files ship in `apps/console/public/`, so the default is your own console origin and no hosted service is involved. Set this only to serve the files from somewhere else, such as a bucket or a CDN. The origin must be publicly reachable, because the commands download the files with `curl`. |

## Managed runner fleet (optional)

By default, runners are static — you register them yourself (see [Runners](/guides/runners)).
Set `FLEET_PROVIDER=hcloud` to let the in-app scaler provision warm runner VMs on Hetzner Cloud and
scale them by queue depth. Unset / `manual` → no managed fleet (the scaler is a no-op).

| Key | Default | Notes |
|---|---|---|
| `FLEET_PROVIDER` | `manual` | `hcloud` provisions real Hetzner VMs; `manual` = no-op. |
| `HCLOUD_TOKEN` | — | Hetzner Cloud API token. Required when `FLEET_PROVIDER=hcloud`. |
| `ALETHIA_RUNNER_BOOTSTRAP_TOKEN` | generated | Low-privilege shared token fleet VMs present to self-register. An instance secret: the installer generates it. |
| `ALETHIA_WEB_ORIGIN` | — | Console URL the VMs call back to (must be reachable from them). |
| `HCLOUD_SERVER_TYPE` | `cax21` | Hetzner server type (ARM CAX recommended for runner workloads). |
| `HCLOUD_IMAGE` | `ubuntu-24.04` | Base OS image for fleet VMs. |
| `HCLOUD_SSH_KEYS` | — | Comma-separated Hetzner SSH key IDs. |
| `FLEET_RUNNER_IMAGE_TAG` | `latest` | Runner image tag pulled from GHCR. |
| `FLEET_RUNNER_SLOTS` | `1` | Concurrent job slots per fleet runner. |
| `FLEET_BOOT_GRACE_SECONDS` | `180` | Seconds a freshly-booted VM is exempt from scale-down (cloud-init grace). |

Warm pools are managed in the console **Fleet** page (DB-backed). `FLEET_POOLS` is **deprecated** —
imported once into an empty pools table on first boot, then ignored.

> A complete production template lives at `deploy/prod/.env.production.example`.
