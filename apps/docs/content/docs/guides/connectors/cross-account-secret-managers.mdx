title: Read secrets from another cloud account
description: Let a cluster read secrets from a cloud secret manager in another AWS account, GCP project or Azure subscription, through a read-only grant and no stored key.
---

Let a cluster read secrets from a secret manager in another account, project or subscription. The
owner of the secrets creates a read-only grant for the cluster's identity. Alethia stores only
references to that grant, never a key.

<Callout type="warn">
These three connectors are listed as **Coming soon** in the connector catalog, so you cannot connect
them yet. This page describes how they work.
</Callout>

| Connector | Reads from | What you enter |
| --- | --- | --- |
| AWS Secrets Manager (cross-account) | Secrets Manager in another AWS account | Target Role ARN, target account ID, region, and optionally External ID |
| GCP Secret Manager (cross-project) | Secret Manager in another GCP project | Target project ID |
| Azure Key Vault (cross-subscription) | Key Vault in another subscription of the same tenant | Target subscription ID, vault URL |

## Before you begin

- The cluster runs the [External Secrets Operator](/guides/design-project/secrets), which signs in
  with the cluster's workload identity: IRSA on AWS, Workload Identity on GCP and Azure.
- You can create IAM grants in the account that owns the secrets.
- You have the Alethia repository. The grant modules are in `infra/connector/<cloud>/secrets-xacct/`,
  each with a README.

## Steps

<Steps>

### Create the grant in the secrets account
Apply the module for your cloud in the account that owns the secrets:

| Cloud | Module | It grants |
| --- | --- | --- |
| AWS | `infra/connector/aws/secrets-xacct` | A read-only role that trusts the cluster's external-secrets identity, with `secretsmanager:GetSecretValue` on the secret ARNs you name. There is no wildcard: the module refuses to apply without a list. |
| GCP | `infra/connector/gcp/secrets-xacct` | `roles/secretmanager.secretAccessor` on each secret you name, for the cluster's external-secrets service account. |
| Azure | `infra/connector/azure/secrets-xacct` | The **Key Vault Secrets User** role on the vault, for the cluster's workload identity. |

On AWS, you can also set `external_id` on the module. Then enter the same value in the connector's
**External ID** field. AWS refuses the read when the two differ. GCP and Azure bind the grant to one
identity instead, so they have no such field.

### Enter the references in the connector
Open **Connectors**, select the connector under **Secrets**, and enter the values from the first
table.

### Deploy
Alethia adds a second `ClusterSecretStore` that reads from the other account, next to the cluster's
own store.

</Steps>

## Keep the grant working when you rebuild a cluster

Each grant names the cluster's external-secrets identity. On AWS that identity has a stable name, so
a rebuild keeps working. On GCP, a re-created service account is a new identity, even with the same
name. On Azure, a re-created managed identity gets a new object ID. So on those two clouds, a
rebuilt cluster cannot read until you apply the grant again.

To avoid this, create the identity yourself once, grant it access, and set these template variables:

| Cloud | Variables |
| --- | --- |
| GCP | `external_secrets_service_account_email` |
| Azure | `external_secrets_identity_name`, `external_secrets_identity_resource_group` |

The template then uses your identity and never creates, changes or deletes it. Leave them unset to
let the template own the identity.

## What is not supported

- **Hetzner** has no cloud secret manager. Use the
  [HashiCorp Vault connector](/guides/connectors/pluggable) instead.
- **Azure across tenants.** A managed identity cannot be used in another tenant. A vault in another
  tenant needs an app registration and a federated credential there, which this connector does not
  make.

## Check that it worked

An `ExternalSecret` that names a secret in the other account syncs, and its Kubernetes Secret has
the value.
