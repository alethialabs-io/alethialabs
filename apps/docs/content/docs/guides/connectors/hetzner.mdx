Connect a Hetzner Cloud project so that Alethia can provision into it. Hetzner Cloud has no OIDC
provider and no role-assumption API, so Hetzner is the one supported cloud that is not keyless: it
connects with an API token that is scoped to one project, encrypted at rest, and revocable at any
time.

## Before you begin

- You have a Hetzner Cloud project for Alethia. A token reaches everything in its project, so use a
  project that does not already hold infrastructure you value.
- Your Alethia role can manage connections (`manage_identities`).

## What Alethia provisions on Hetzner

Hetzner Cloud has no managed Kubernetes and no managed data services. Alethia provisions a
self-managed [Talos Linux](https://www.talos.dev/) Kubernetes cluster on Hetzner servers (ARM `CAX`,
or x86 `CX`, `CPX` and `CCX`), with Cilium networking and the Hetzner CSI driver for volumes.
Databases, caches and queues run in the cluster through ArgoCD: CloudNativePG for PostgreSQL, Valkey
for caches, and RabbitMQ for queues.

## Steps

<Steps>

### Create a project-scoped API token
In the [Hetzner Cloud Console](https://console.hetzner.cloud/), open the project, then
**Security → API Tokens → Generate API token**. Give it **Read & Write** permission, because
provisioning creates servers, networks and volumes.

### Paste the token
In Alethia, open **Connectors**, select **Hetzner Cloud**, then select **Connect**. Paste the token
into **API Token**.

### Add Object Storage keys (optional)
To provision storage buckets, open **Object Storage keys (optional)** and paste an S3 access key
and secret key. Hetzner has no API that makes these keys: generate them in the Hetzner Console
under S3 credentials. Give both keys or neither.

### Connect
Select **Connect**.

</Steps>

To connect from a terminal, run `alethia connector hetzner --token-stdin` and pipe the token in. A
`--token` flag also works, but it lands in your shell history. Add `--s3-access-key` and
`--s3-secret-key` for buckets. See [Connector commands](/reference/cli/connector).

### With a self-operated runner

A runner you operate can read the token from `HCLOUD_TOKEN` in its own environment, so that
Alethia does not store a token. See [Self-operated runners](/guides/runners/self-operated).

## How the token is kept

The console encrypts the token with AES-256-GCM before it stores it, and never returns it. The
console decrypts it to check the connection, and when a runner claims a job, to hand it to that
runner. It is never written into a project's configuration snapshot.

## Check that it worked

### Verification

When you select **Connect**, the console calls the Hetzner Cloud API
(`GET /v1/locations`) with the token. No runner is involved.

| Result | State |
| --- | --- |
| `200` | **Connected**. Alethia also syncs the project's locations, which placement uses. |
| `401` or `403` | **Verification failed**: the token is wrong or was revoked. |

To fix a failed check, see [Troubleshoot: connect a cloud](/troubleshooting/connect#hetzner).

## Stop Alethia's access

Delete the token in the Hetzner Cloud Console. Alethia's access ends at once.
