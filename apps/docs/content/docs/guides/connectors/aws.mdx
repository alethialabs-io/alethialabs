title: Connect an AWS account
description: Connect an AWS account with a keyless IAM role that trusts the Alethia OIDC issuer, from AWS CloudShell, a Terraform module, or the CLI.
---

Connect an AWS account so that Alethia can provision into it. Alethia stores only a role ARN. It
signs in with a short-lived token, never with an access key.

## Before you begin

- You can create IAM roles, policies and identity providers in the AWS account.
- Your Alethia role can manage connections (`manage_identities`).
- An AWS account can have one IAM OIDC provider for each issuer URL. If you connected this account
  before, the setup reuses the existing provider.

## Steps

The **AWS CLI / CloudShell** and **Terraform / IaC** tabs create the same resources.

<Tabs items={["AWS CLI / CloudShell", "Terraform / IaC"]}>
  <Tab value="AWS CLI / CloudShell">
    <Steps>

    ### Open the connect sheet
    In the console, open **Connectors**, select **Amazon Web Services**, then select **Connect**.

    ### Run the setup in AWS CloudShell
    Select **Open CloudShell** and paste the command from the sheet. The `aws` CLI in CloudShell is
    already signed in. To run it on your own machine, select **Download script**. A self-hosted
    console passes its own issuer URL as the script's first argument.

    ### Paste the role ARN it prints
    Paste the ARN that the script prints into **IAM Role ARN**, then select **Connect**. You can
    paste the whole output: the field keeps only the ARN.

    </Steps>
  </Tab>
  <Tab value="Terraform / IaC">
    <Steps>

    ### Open the connect sheet
    In the console, open **Connectors**, select **Amazon Web Services**, select **Connect**, then
    choose **Terraform / IaC**.

    ### Apply the module
    Select **Download module** and apply it with `tofu apply` or `terraform apply`. It needs no
    variables. A self-hosted console sets `issuer_url` to its own issuer.

    ### Paste the role_arn output
    Paste the `role_arn` output into **IAM Role ARN**, then select **Connect**.

    </Steps>
  </Tab>
</Tabs>

To connect from a terminal, run `alethia connector aws`. By default it deploys the `AlethiaConnect`
CloudFormation stack with your local `aws` CLI. `--script` runs the setup script instead, and
`--role-arn <arn>` submits a role you already made. See
[`alethia connector aws`](/reference/cli/connector#alethia-connector-aws).

## What the setup creates

| Resource | Purpose |
| --- | --- |
| An IAM OIDC provider for the Alethia issuer | The trust root for Alethia in your account. |
| `AlethiaProvisionerRole` | Trusts only `sts:AssumeRoleWithWebIdentity` from that provider, for audience `sts.amazonaws.com` and subject `alethia-connector`. No external ID. |
| Five policies: `AlethiaProvisionerRole-ComputeNet`, `-ComputeScale`, `-Data`, `-Edge` and `-IAM` | Name the exact actions the templates use, instead of `AdministratorAccess`. |

### IAM role permissions

The role can manage EC2 and VPC networking, EKS, RDS (Aurora), ElastiCache, Route 53, ACM,
Secrets Manager, DynamoDB, SQS, SNS, ECR, S3, KMS, CloudWatch Logs, Kinesis Firehose, EventBridge,
Application Auto Scaling, and the IAM roles of the in-cluster controllers. A project uses only the
services it needs.

The `-IAM` policy denies attaching `AdministratorAccess`, `PowerUserAccess` or `IAMFullAccess` to
anything. It limits `iam:PassRole` to the provisioned services, and denies `organizations:*`,
`account:*` and billing actions. So the role cannot give itself admin rights. The full scope is in
[Security](/concepts/security#aws-keyless-issuer-direct-iam-role).

## Check that it worked

### Verification

When you select **Connect**, the console checks the connection at once. No runner is involved. It
assumes the role, calls `sts:GetCallerIdentity`, and runs a few read calls. The account then shows
one of these states:

| State | Meaning |
| --- | --- |
| **Connected** | Alethia can assume the role and has the permissions it checks for. |
| **Limited permissions** | Alethia can assume the role, but some permissions are missing. They are listed. |
| **Verification failed** | AWS refused the assume. The reason is shown. |

To fix a failed check, see [Troubleshoot: connect a cloud](/troubleshooting/connect#aws).

## Stop Alethia's access

Delete `AlethiaProvisionerRole`, and its OIDC provider if nothing else uses it. To also remove the
account from Alethia, see
[Disconnect an account](/guides/connectors/managing-connections#disconnect-an-account).
