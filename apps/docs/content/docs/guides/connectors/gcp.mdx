title: Connect a GCP project
description: Connect a Google Cloud project with Workload Identity Federation, from Cloud Shell, a Terraform module, or the CLI. No service account key is made.
---

Connect a Google Cloud project so that Alethia can provision into it. Your project's Workload
Identity Pool trusts the Alethia OIDC issuer, so no service account key is ever made.

## Before you begin

- You can enable APIs, create service accounts and Workload Identity Pools, and grant IAM roles in
  the project.
- Your Alethia role can manage connections (`manage_identities`).
- You know the project ID.

## Steps

The **gcloud CLI** and **Terraform** tabs create the same resources.

<Tabs items={["gcloud CLI (Cloud Shell)", "Terraform"]}>
  <Tab value="gcloud CLI (Cloud Shell)">
    <Steps>

    ### Open the connect sheet
    In the console, open **Connectors**, select **Google Cloud**, then select **Connect**. Enter the
    **Project ID** and choose **gcloud CLI**.

    ### Run the setup in Cloud Shell
    Select **Open Cloud Shell** and paste the command from the sheet. It already names your project.
    To run it with a local `gcloud`, select **Download script**.

    ### Enter the project number it prints
    Enter the number in **Project number**, then select **Connect**.

    </Steps>
  </Tab>
  <Tab value="Terraform">
    <Steps>

    ### Open the connect sheet
    In the console, open **Connectors**, select **Google Cloud**, then select **Connect**. Enter the
    **Project ID** and choose **Terraform**.

    ### Apply the module
    Select **Download module** and apply it with your `gcloud` login. Set `project_id`. The other
    variables have defaults.

    ### Enter the project_number output
    Enter it in **Project number**, then select **Connect**.

    </Steps>
  </Tab>
</Tabs>

Alethia builds the credential configuration from the project ID and number. For a custom setup,
select **Paste a credential config instead** and paste a full `external_account` configuration, for
example the module's `credential_config` output.

To connect from a terminal, run `alethia connector gcp --project <id>`. It needs a local,
authenticated `gcloud`. `--manual` runs the setup in the browser Cloud Shell, and `--wif-config`
submits a configuration you already have. See
[`alethia connector gcp`](/reference/cli/connector#alethia-connector-gcp).

## What the setup creates

| Resource | Value |
| --- | --- |
| Workload Identity Pool and OIDC provider | `alethia-pool`, `alethia-oidc-provider`. Issuer `https://alethialabs.io/api/oidc`, audience `alethia-gcp-wif`, subject `alethia-connector`. |
| Provisioner service account | `alethia-provisioner`, which the pool may impersonate. |
| Application database account | `alethia-appdb`, for [password-free Cloud SQL](#password-free-cloud-sql). |
| external-dns account | `alethia-external-dns`. It can list zone names only; record writes are granted per zone at deploy time. |

The project number is needed because the token exchange names the pool by number, and a number
cannot be looked up before Alethia is signed in.

### Service account permissions

The provisioner gets predefined admin roles for GKE, Compute networking and security, Service
Networking, Cloud SQL, Memorystore, Cloud DNS, Artifact Registry, Secret Manager and Cloud KMS, plus
`iam.serviceAccountUser`. It never gets `roles/editor`.

Six custom roles replace the predefined roles that also read data. They manage Cloud Storage
buckets without object access, Firestore databases without entity access, Pub/Sub topics without
publish or consume, add-on service accounts, project metadata, and DNS-zone IAM.

`cloudkms.admin` lets the provisioner create the key that encrypts Kubernetes Secrets. It cannot
use the key, so it cannot read a Secret. IAM grants are scoped to one zone, one secret, or one
service account, so the provisioner does not need project `setIamPolicy`. Details are in
[Security](/concepts/security#gcp-workload-identity-federation).

## Optional APIs you enable yourself

Alethia does not hold `serviceusage.services.enable`, because it would let the provisioner turn on
any API, including billable ones. It can only check whether an API is on.

| Feature | API | Enable with |
| --- | --- | --- |
| Container registry → **Vulnerability scanning** | `containerscanning.googleapis.com` | `gcloud services enable containerscanning.googleapis.com --project <PROJECT_ID>` |

If you turn on scanning without the API, the deploy stops before it changes anything and names the
API. Enable it and deploy again. With scanning off, repositories are created with scanning
disabled and need nothing.

## Password-free Cloud SQL

To let your apps reach Cloud SQL with an IAM token instead of a password, set this value on the
project in Alethia:

```text
cloud_sql_app_service_account_email = alethia-appdb@<PROJECT_ID>.iam.gserviceaccount.com
```

The script prints it at the end, and the module outputs it as `cloud_sql_app_service_account_email`.
If you leave it unset, apps use password authentication, and turning on IAM auth shows a warning.

`alethia-appdb` has `roles/cloudsql.client` and `roles/cloudsql.instanceUser`. Google grants these
only on the whole project, and that needs `setIamPolicy`, which the provisioner does not hold. So
you make this grant once, at setup.

<Callout type="warn">
Every environment in the project shares `alethia-appdb`. An app in one environment can log in to
another environment's Cloud SQL instance; its SQL grants still limit what it can do. To isolate
environments by identity, use separate Google Cloud projects. On AWS and Azure, Alethia creates
one database identity per environment instead.
</Callout>

## Check that it worked

### Verification

When you select **Connect**, the console exchanges a token through your pool and runs a Compute
read call. No runner is involved. The account then shows **Connected**, **Limited permissions**
(missing permissions are listed), or **Verification failed**. To fix a failed check, see
[Troubleshoot: connect a cloud](/troubleshooting/connect#gcp).

## Stop Alethia's access

Delete the Workload Identity Pool, or remove the service account binding. Alethia stores only the
project ID, the project number and the configuration built from them.
