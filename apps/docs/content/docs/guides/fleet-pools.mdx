---
title: Run a warm pool of runners
description: On a self-hosted console, configure a warm pool of managed runners for a cloud, so the fleet controller keeps capacity sized to demand.
---

Keep ready runners waiting for jobs, within a spend ceiling, on one version. A **warm pool** states
the target for one cloud's managed runners. The **fleet controller** reads every pool every 60
seconds and provisions, drains or replaces runners to match. A change to a pool takes effect on the
next tick, with no redeploy.

Pools are for managed runners, which the controller creates and removes for you. To add a runner you
operate yourself, use **Add Runner** on the [Runners](/guides/runners) page.

## Before you begin

- You run your own console. The **Pools** panel is not shown on the hosted service.
- You are an owner or admin. Others see the panel read-only, and **Add pool** is disabled with the
  reason.
- `FLEET_PROVIDER=hcloud` is set, so that runners are real Hetzner servers. Without it, a pool is
  advisory: the controller logs what it would do and creates nothing, and the panel says so.

## Add a pool

There is one pool per cloud. A cloud that has a pool is disabled in the picker, and a pool's cloud
cannot change later.

<Steps>

### Open the wizard
On the **Runners** page, find **Pools** in the left column and select **Add pool**. The wizard has
five steps: **Cloud**, **Placement**, **Capacity**, **Version** and **Review**.

### Choose the cloud
Pick the **Cloud provider**. A **Display name (optional)** names the pool card. It defaults to the
cloud's name.

### Set placement
Enter **Locations** as region codes separated by commas, such as `fsn1,nbg1` on Hetzner. The
controller spreads runners across them, so one bad region does not take the pool down. Set a
**Minimum per location** to keep that many runners in each, or `0` for none.

### Set capacity

| Field | Meaning |
| --- | --- |
| **Warm minimum** | Runners kept ready at all times, even with no jobs queued. |
| **Maximum** | The most runners the pool ever runs, however long the queue. |
| **Idle buffer** | Spare runners kept above demand, so a new job rarely waits for a boot. `0` matches demand exactly. |
| **Slots / runner** | Jobs one runner runs at once. More slots share one server's CPU and memory. |

The maximum must be at least the warm minimum, and the idle buffer cannot exceed the maximum. If
the minimum per location times the number of locations exceeds the maximum, the wizard warns you.
A preview says what the numbers mean, including the most jobs at once (maximum × slots).

Under **Advanced scaling**:

| Field | Meaning |
| --- | --- |
| **Rollout surge** | Extra runners allowed above the maximum during a version change, so capacity does not drop. |
| **Scale-down grace** | Idle 60-second ticks before a runner is removed. More ticks stop the pool from shrinking and growing on spiky demand. |

### Choose the version source
- **Channel** follows a release stream, usually `stable`. Each tick, the controller picks the newest
  release on it.
- **Pinned** holds one version until you change it.

### Create the pool
Check the summary and select **Create pool**. The controller starts at once.

</Steps>

New runners always start at the target version. When the version changes, the controller replaces
runners one step per tick. It drains an old runner only when it can start a new one first, so online
capacity never drops below the warm minimum.

## Edit, pause or delete a pool

Open **Pool actions** (**⋮**) on the pool card:

| Action | What happens |
| --- | --- |
| **Edit** | Opens the wizard on the pool. Everything but the cloud can change. |
| **Pause** | Drains every runner to zero and closes each runner's usage session, so nothing keeps billing. **Resume** rebuilds the warm minimum over the next few ticks. |
| **Delete** | Drains and removes the pool's runners on the next tick, then the pool. It cannot be undone. |

Pause and delete drain a busy runner first: it stops taking new jobs and finishes the one it runs.
No running job is dropped.

## Check that it worked

The pool card shows:

- **Warm capacity**: online runners against the target, as a meter of online, busy and missing
  runners, with how many are below the floor, busy or draining.
- **Rollout**: the share of runners on the target version, with progress during a change.
- **Versions** and **Locations**: where the runners are, flagged when one is on another version or a
  location has an offline runner.
- **Healthy**, or **Degraded** when the pool is below its warm minimum or a runner is offline. A
  paused pool is dimmed and marked **Paused**.
- For managers, this month's provisioned hours, estimated cost and use.
