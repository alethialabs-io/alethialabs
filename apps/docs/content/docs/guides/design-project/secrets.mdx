# Secrets

The secrets section creates entries in your cloud provider's secret management service. Secrets can be auto-generated with configurable parameters or set to custom values after provisioning.

## Fields Per Secret

| Field | Type | Description |
|-------|------|-------------|
| **Name** | Text input | Secret name (alphanumeric + hyphens only) |
| **Provider** | Select | Cloud-native store or a [pluggable connector](/guides/connectors/pluggable) |
| **Generate** | Toggle | Auto-generate a random value |
| **Length** | Number | 8–128 characters |
| **Special Characters** | Toggle | Include `!@#$%^&*()` in generated value |

## Set a secret's value

Alethia never stores a secret's value in the project. You supply it in the secret store instead:

1. To let Alethia make the value, leave **Auto-generate value** on and set **Length** and
   **Special Characters**. Alethia generates the value when it creates the secret.
2. To use your own value, turn **Auto-generate value** off. On AWS, Alethia creates the secret in
   AWS Secrets Manager with the placeholder value `editme`.
3. After the deploy, write the real value into the secret, for example:

   ```bash
   aws secretsmanager put-secret-value \
     --secret-id <secret-name> \
     --secret-string '<value>'
   ```

   Replace `<secret-name>` with the secret's name in AWS Secrets Manager.

To keep values outside the cloud, make a secrets connector, such as HashiCorp Vault, the
environment's secret store. Then write the value in that store. See
[Pluggable connectors](/guides/connectors/pluggable).

<Callout type="warn">
The AWS template has a `value` variable for a secret. The **Advanced** section does not offer it,
and Alethia refuses it in `provider_config`. A value there would be stored in plaintext in the
project. A project saved before this change can still hold one: Alethia keeps it and still applies
it, and it never shows the value. To remove it, choose **Remove the stored value** in the secret's
**Advanced** section.
</Callout>

## Secrets Provider

By default secrets are created in the cluster cloud's native secret store. Select **HashiCorp Vault** to manage them in a Vault instance instead:

- Requires a connected [Vault connector](/guides/connectors/pluggable) (Vault address + token).
- Per-Project knobs: the KV **mount path** and **KV version** (1 or 2).
- The cloud-native secret resources are skipped at provision time; Vault entries are managed by the composed module.

## Presets

Quick-add buttons create secrets with recommended settings:

| Preset | Length | Special Chars | Use Case |
|--------|--------|--------------|----------|
| PostgreSQL Password | 32 | Yes | Database master password |
| API Token | 48 | No | Application API key |
| JWT Secret | 64 | No | Token signing key |
| Redis Password | 32 | No | Cache authentication |
| Custom Secret | 32 | No | User-defined |

## Integration with Kubernetes

After provisioning, secrets are synced to Kubernetes via the **External Secrets Operator** (installed by ArgoCD — see [GitOps & ArgoCD](/concepts/gitops-argocd)). This creates Kubernetes `Secret` resources from cloud secret store entries, keeping them in sync automatically.
