---
title: Migrate from ingress-nginx
description: Move an environment from the deprecated Ingress NGINX add-on to the Traefik add-on, and from Ingress objects to Gateway API routes.
---

Replace the deprecated **Ingress NGINX** add-on with **Traefik**, then, when you are ready, move
from Ingress objects to Gateway API routes. The Kubernetes project retired ingress-nginx: its last
release is 4.15.1, and it gets no more security fixes.

From 2027-02-09, Ingress NGINX accepts no new installs from the console or the CLI. An environment
that already has it keeps it: it still deploys, you can still change its settings, and Alethia never
removes it for you.

The migration has two stages:

1. **Swap the controller.** Traefik serves your existing Ingress objects unchanged.
2. **Move to Gateway API.** Rewrite each Ingress as an `HTTPRoute`. This stage is optional.

## Before you begin

- You can run `kubectl` against the cluster. See [Get a kubeconfig](/guides/get-a-kubeconfig).
- `jq` is installed, for the annotation review.
- For Stage 2, [ingress2gateway](https://github.com/kubernetes-sigs/ingress2gateway) is installed.

## Stage 1: swap the controller

Traefik's NGINX provider reads Ingress objects with `ingressClassName: nginx` and their
`nginx.ingress.kubernetes.io/*` annotations. The add-on setting **Serve NGINX-class Ingresses**
turns it on; it is off by default. Both controllers can run at once, each behind its own load
balancer, and you move traffic by moving DNS.

<Steps>
<Step>

### Review your annotations

List the annotations your Ingress objects use:

```bash
kubectl get ingress --all-namespaces -o json \
  | jq -r '.items[].metadata.annotations // {} | keys[]' \
  | grep '^nginx.ingress.kubernetes.io/' | sort | uniq -c
```

Compare the list with the [annotation reference](/reference/ingress-nginx-annotations). Traefik
ignores an annotation it does not support and still serves the route. Three are access controls:
`denylist-source-range`, the ModSecurity and OWASP rule annotations, and `auth-tls-match-cn`. For
each, add a Traefik middleware first, or keep that Ingress on Ingress NGINX by leaving the setting
off: it applies to every NGINX-class Ingress at once.

</Step>
<Step>

### Enable Traefik

1. On the canvas, select **Add** and choose **Traefik**.
2. Turn on **Serve NGINX-class Ingresses** once the review is done. From then on, every NGINX-class
   Ingress answers on Traefik's load balancer, even before you move DNS.
3. Select **Enable add-on**, then deploy.

From the CLI:

```bash
alethia addon enable traefik --project my-project --set ingressNginx=true
```

The setting needs an IngressClass named `nginx` with `spec.controller: k8s.io/ingress-nginx`, which
the Ingress NGINX add-on creates. On an environment that never ran it, create the class yourself, or
leave the setting off and use `ingressClassName: traefik`.

</Step>
<Step>

### Check that Traefik serves your routes

Get Traefik's address, then send a request for one of your hosts to it without changing DNS:

```bash
kubectl -n traefik get service -l app.kubernetes.io/name=traefik
curl --resolve app.example.com:443:<traefik-address> https://app.example.com/
```

Repeat for each host. Check each behaviour an annotation controls: redirects, rewrites,
authentication and allowlists.

</Step>
<Step>

### Move DNS

Point each host at Traefik's address. If external-dns manages your records, both controllers write
their address to the Ingress status and compete for the record until you remove Ingress NGINX, so
do the next steps in a quiet period.

</Step>
<Step>

### Keep the nginx IngressClass

Removing the Ingress NGINX add-on deletes the `nginx` IngressClass, and Traefik then stops serving
your Ingresses. Tell ArgoCD to keep it:

```bash
kubectl annotate ingressclass nginx argocd.argoproj.io/sync-options=Delete=false --overwrite
```

</Step>
<Step>

### Remove Ingress NGINX

Open **Ingress NGINX** on the canvas, select **Remove**, then deploy. The controller and its load
balancer go. Your Ingress objects and the `nginx` IngressClass stay.

</Step>
</Steps>

## Stage 2: move to Gateway API

<Steps>
<Step>

### Install the Gateway API CRDs

Neither the Traefik chart nor an Alethia cluster includes them. Install the standard channel before
the next step, or the add-on cannot sync:

```bash
kubectl apply --server-side \
  -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.6.3/standard-install.yaml
```

</Step>
<Step>

### Turn on Gateway API in Traefik

Open **Traefik** on the canvas, turn on **Gateway API**, save, and deploy. Traefik creates a
`traefik` GatewayClass and a `traefik-gateway` Gateway in the `traefik` namespace, with one HTTP
listener on port 8000. For HTTPS, add a listener with `certificateRefs` under `gateway.listeners` in
the add-on's raw Helm values.

</Step>
<Step>

### Convert each Ingress

Write a first draft of the routes:

```bash
ingress2gateway print --providers ingress-nginx --all-namespaces > routes.yaml
```

Review it before you apply it: the tool does not convert authentication, cookie affinity, rate
limits or snippets. Point each route's `parentRefs` at `traefik-gateway` in the `traefik` namespace.

</Step>
<Step>

### Remove the Ingress

When the route serves the host, delete the Ingress. When no NGINX-class Ingress is left, turn off
**Serve NGINX-class Ingresses**.

</Step>
</Steps>

## Check that it worked

```bash
kubectl get ingressclass nginx
kubectl get httproute --all-namespaces
```

After Stage 1, the `nginx` class still exists and every host answers through Traefik. After
Stage 2, each host has an `HTTPRoute` and no NGINX-class Ingress is left.
