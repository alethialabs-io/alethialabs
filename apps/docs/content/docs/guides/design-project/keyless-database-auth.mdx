---
title: Use keyless database auth
description: Connect a service to a PostgreSQL or MySQL database with short-lived cloud IAM tokens instead of a password.
---

Connect a service to its database with its own cloud identity and a short-lived token, so no
database password sits in the cluster. How it works on each cloud is in
[Keyless database auth](/concepts/keyless-database-auth).

## Before you begin

- The project runs on AWS, GCP or Azure. Hetzner runs PostgreSQL in your cluster, with no cloud
  identity to mint tokens, so there the database keeps a generated password.
- The database engine is PostgreSQL or MySQL.
- Your runner has `ALETHIA_KEYLESS_DB_AUTH_ENABLED=true`. Without it, the binding uses the password
  path.
- Your runner runs a published image. It schedules its own image as a sidecar and as a setup Job.
  Set `ALETHIA_RUNNER_IMAGE` only to use a private mirror. A runner built from source has no
  published image, so keyless deploys fail there.

## Steps

1. Select the database card. Under **Security**, turn on **IAM authentication**.
2. Connect the service to the database: drag from the service's handle to the database card.
3. In the service's **Connections** tab, map these values to environment variables. Do not map
   `password`: there is none.

   | Value | Resolves to |
   | --- | --- |
   | `endpoint` | `127.0.0.1`: a proxy in the service's pod |
   | `port` | 5432 for PostgreSQL, 3306 for MySQL |
   | `username` | The service's cloud login, filled in from the deploy |

4. Configure your application to connect to that host, port and user with no password. You do not
   change any other code.
5. Review the plan and deploy.

You do not mark the binding as keyless. It follows the database: with **IAM authentication** on,
the binding is keyless; with it off, the binding uses a generated password. To switch, change the
setting on the database and deploy again.

## Check that it worked

- The deployment's **Deploy** tab lists no omitted binding. If Alethia cannot wire a keyless
  binding, for example because an identity is missing, it leaves the binding out and names the
  reason there.
- Your service's pod has a second container: the Cloud SQL Auth Proxy on GCP, or
  `alethia db-authproxy` on AWS and Azure.
- No Kubernetes Secret holds a password for this database.
- The application connects. A failed login means the database user and the cloud identity do not
  match: see [Troubleshoot design and GitOps](/troubleshooting/design-project#a-keyless-binding-is-omitted-at-deploy).
