---
title: Add a database
description: Add a managed PostgreSQL or MySQL database to an environment, set its capacity, backups and version, and read its credentials.
---

Add a relational database to the environment. You can add as many as you need.

## Before you begin

- You have a project open on the [canvas](/guides/design-project/the-canvas).

## Steps

1. Select **Add**, then **Database** in the **Data** group.
2. Choose **PostgreSQL** or **MySQL**. On Hetzner, only PostgreSQL is offered. The first database
   is named `primary`.
3. Under **General**, check the **Port**. The default is 5432.
4. Under **Capacity**, set **Min capacity** and **Max capacity**. The database scales between them:

   | Cloud | Service | Unit | Range | Default |
   | --- | --- | --- | --- | --- |
   | AWS | Aurora Serverless v2 | ACU (about 2 GiB of memory each) | 0.5–128 | 0.5–4 |
   | GCP | Cloud SQL | vCPU | 1–96 | 1–4 |
   | Azure | Azure Database Flexible Server | vCores | 1–64 | 2–4 |

   On Hetzner the database runs in your cluster on CloudNativePG. Set **Storage**, the volume per
   PostgreSQL instance in GiB, and **Instances**, one primary plus replicas (1–5), under
   **In-cluster sizing** instead.
5. Under **Security**:
   - Turn on **IAM authentication** so that services connect with short-lived cloud tokens instead
     of a password. See [Use keyless database auth](/guides/design-project/keyless-database-auth).
     It is unavailable on Hetzner, and the switch says why.
   - Set **Backup retention** in days (0–35). `0` turns automated backups off. Point-in-time restore
     covers this window.
6. Optional: under **Advanced**, pin an **Engine version**, or choose an **Instance class**. Empty
   values use the template's defaults.

### Engine versions

The lists come from your cloud account when Alethia can read them. When it cannot:

| Cloud | PostgreSQL | MySQL |
| --- | --- | --- |
| AWS | 14–18, default 16 | 8.0 and 8.4, default 8.0 |
| GCP | 14–18, default 15 | 5.7, 8.0 and 8.4, default 8.0 |
| Azure | 14–18, default 16 | 5.7, 8.0.21 and 8.4, default 8.0.21 |
| Hetzner | 16 | Not offered |

## Read the credentials

Alethia generates the database's password at deploy. A service gets it through a
[binding](/guides/design-project/services), as a Kubernetes Secret that the External Secrets
Operator keeps in sync, so you never copy it.

## Read the extra database user on AWS

On AWS, Alethia also creates a second database user, `demouser`, on the database `demodb`. It
generates the password and stores the user name, password and database name in AWS Secrets
Manager. After the deploy, the database records that secret's ARN as `extra_secret_ref`. Read the
credentials from the secret.

You cannot change this user on the canvas or in `provider_config`, because the template variable
`rds_extra_credentials` holds the password too, and Alethia does not store a credential in a
component's configuration.

A project saved earlier can still hold an `rds_extra_credentials` value. Alethia keeps applying it
and never shows it. To remove it:

1. Open the database's **Advanced** group.
2. Choose **Remove the stored value**.
3. Deploy. The secret is rewritten with the default user, database and a new password.
4. Update the services that read the old credentials.

## Check that it worked

After the deploy, open the database's **Status** tab. **Endpoints** shows the hostname, with a copy
button.
