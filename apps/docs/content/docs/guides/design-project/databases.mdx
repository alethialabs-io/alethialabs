# Databases

The databases section configures managed relational database instances. Multiple databases can be added per project, each with its own engine, version, and capacity settings.

## Fields Per Database

| Field | Type | Description |
|-------|------|-------------|
| **Name** | Text input | Unique per project, lowercase, used in resource naming |
| **Engine** | Select | Provider-specific engine (see below) |
| **Engine Version** | Auto-set | Determined by engine selection |
| **Min Capacity** | Number | Minimum capacity (ACUs for Aurora, vCPUs for Cloud SQL) |
| **Max Capacity** | Number | Maximum capacity for auto-scaling |
| **Port** | Number | Database port (default: 5432 for PostgreSQL, 3306 for MySQL) |
| **IAM Auth** | Toggle | Authenticate with short-lived cloud IAM tokens instead of a password. PostgreSQL and MySQL, on AWS, GCP and Azure. See [Keyless database auth](/guides/design-project/keyless-database-auth) |

## Adding Multiple Databases

Click **"Add Database"** to add another instance. Each database gets its own card in the form. The first database defaults to:
- Name: `primary`
- Engine: Aurora PostgreSQL (or equivalent)
- Capacity: 0.5–4 ACUs

Common patterns:
- **Primary + Read Replica**: One write database + one read-optimized database
- **Multi-service**: Separate databases per microservice (e.g., `users-db`, `orders-db`)

## After Provisioning

Once deployed, the database card in the [project detail](/guides/dashboard/project-detail) Services tab shows:
- **Writer endpoint** — primary connection string
- **Reader endpoint** — read replica connection (Aurora only)
- **Master credentials** — stored in Secrets Manager (ARN shown, copy button)
- **Status** — ACTIVE, CREATING, or FAILED

<Callout type="info">
**IAM authentication** lets a workload connect using its own cloud identity and a short-lived token
instead of a stored password — nothing to rotate, no secret in the cluster. A service bound to an
IAM-auth database picks this up automatically.

It covers **PostgreSQL and MySQL on AWS, GCP and Azure**. Alibaba Cloud and Hetzner have no
token-based database login, so a database on either stays on the password path even with the toggle
on. See [Keyless database auth](/guides/design-project/keyless-database-auth) for how it works per
cloud and its current rollout status.
</Callout>

## The extra database user (AWS)

On AWS, Alethia creates a second database user beside the master user. Alethia generates its
password and stores the user name, password and database name in AWS Secrets Manager. After the
deploy, the database records the secret's ARN as `extra_secret_ref`. Read the credentials from that
secret.

You cannot set this user on the canvas or with `provider_config`. The template variable
`rds_extra_credentials` holds the user name, the database name and the password in one value, and
Alethia does not store a credential in a component's configuration. The **Advanced** section shows a
note in its place. Because the three fields are one variable, the user name and database name are
not settable either: every new database gets the template defaults, user `demouser` on database
`demodb`. Read them from the same Secrets Manager secret as the password.

<Callout type="warn">
A project saved before this change can still hold an `rds_extra_credentials` value. Alethia keeps it
and still applies it, and it never shows the value. To stop storing it, open the database's
**Advanced** section and choose **Remove the stored value**. The next deploy then rewrites the
secret with the template's default user name and database and a generated password. Update the
services that read the old credentials.
</Callout>
