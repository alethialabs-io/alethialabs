Find a cluster that Alethia deployed, check its health, and get what you need to reach it.

## Before you begin

- At least one environment has deployed. A cluster appears when an environment's first deploy
  succeeds, and stays until the environment is destroyed.
- Your role can view clusters.

## Steps

<Steps>

### Open Clusters
Select **Clusters** in the sidebar for every cluster in the organization, or **Clusters** inside a
project for that project's clusters. Each row is one environment's cluster.

### Narrow the list
Use the filter bar: **Search** (environment, project or cluster name), **Cloud**, **Region**, and
the status chips **Needs attention**, **In progress**, **Healthy** and **Unverified**. **Reset**
clears them. The filters and page number are in the page URL, so you can share the view. The list
updates by itself when a cluster changes.

### Open the record
Select a row. The cluster's record opens in a side panel, and its URL opens the same record.

</Steps>

## Read the table

| Column | What it shows |
| --- | --- |
| **Environment** | The environment, with the cluster's name in the cloud under it |
| **Project** | The project. Hidden on a project's own page. |
| **Status** | See [Statuses](#statuses). A second line says what failed, such as **Last run failed** or **Deleted outside Alethia**, and links to the newest run. |
| **Cloud** | Cloud, region and Kubernetes version |
| **Components** | Healthy components out of all, such as `3 / 4 healthy`: the control plane, databases and caches |
| **Last observed** | When Alethia last saw the control plane, or **Never** |

### Statuses

The status comes from the control plane, the databases and caches, and the environment's current run.

| Status | Meaning | Filter |
| --- | --- | --- |
| **Active** | Every component is healthy. | Healthy |
| **Queued**, **Deploying**, **Destroying** | A run is in progress. | In progress |
| **Reconciling** | A component is changing. A changing control plane shows its own state, such as **Updating**. | In progress |
| **Degraded** | A database or cache failed. | Needs attention |
| **Unreachable** | A probe could not reach the control plane. | Needs attention |
| **Missing** | A drift scan or probe found the cluster deleted outside Alethia. | Needs attention |
| **Unverified** | Nothing confirmed the control plane recently. | Unverified |

A cluster whose last run failed is under **Needs attention**, even when it is **Active**.

## Use the record

- **Status**: the result, the healthy components, when and how the control plane was last seen (a
  probe or the last deploy), and how long a current run has taken. **Details** shows what the cloud
  answered to a failed probe.
- **Components**: the control plane (EKS, GKE, AKS, or `k8s` on Hetzner), each database and cache,
  and the DNS domain, each with its status and an endpoint to copy.
- **Cluster access**: the API endpoint, the kubeconfig commands and the download. Shown only when
  the cluster has an API endpoint.
- **ArgoCD**: the ArgoCD address, a button that opens it, and the command that reads the admin
  password.

At the bottom, **Open project**, **Open Architecture** and **View last run** take you to the project,
the environment on the canvas, and the newest run.

### Resolve a missing cluster

For a **Missing** cluster with no run in progress, the record offers three choices. Nothing changes
until you pick one.

- **Redeploy** or **Tear down** opens the environment on the canvas, where you deploy or destroy it.
- **Mark as destroyed** records the environment and cluster as destroyed. It calls no cloud and starts
  no job, so remove leftover resources in the cloud account yourself. The history stays, and you can
  deploy again later.

## Get a kubeconfig

**Cluster access** lists each way the cluster supports:

- `alethia cluster kubeconfig <cluster-name>`: a runner mints a short-lived kubeconfig, so you need
  no cloud login. Works on AWS, GCP, Azure and Hetzner. See [Get a kubeconfig](/guides/get-a-kubeconfig).
- The cloud's own command, under **Or, with access to the cloud account**: runs under your own cloud
  login. AWS, GCP and Azure only.
- **Download kubeconfig (1h, read-only)**: a static, read-only file that expires after an hour. Only
  people with `cluster:access_readonly` see it.

The cloud commands, filled in from the cluster's last successful deploy:

<Tabs items={["AWS", "GCP", "Azure"]}>
  <Tab value="AWS">
    ```bash
    aws eks update-kubeconfig --name {cluster-name} --region {region}
    ```
  </Tab>
  <Tab value="GCP">
    ```bash
    gcloud container clusters get-credentials {cluster-name} --region {region} --project {gcp-project-id}
    ```

    A zonal cluster uses `--zone {zone}` instead of `--region {region}`.
  </Tab>
  <Tab value="Azure">
    ```bash
    az aks get-credentials --resource-group {resource-group} --name {cluster-name}
    ```
  </Tab>
</Tabs>

When a value the cloud command needs was not recorded, only the `alethia` command is shown. When
there is no command at all, a note says why. `alethia cluster get` prints the same commands. See
[Accessing a cluster with kubectl](/reference/cli/clusters#accessing-a-cluster-with-kubectl).

The ArgoCD password command reads a Secret, so a read-only kubeconfig cannot run it. Use
`alethia cluster kubeconfig --admin` or the cloud's own command.

### Download a kubeconfig

Select **Download kubeconfig (1h, read-only)**. The record shows **A runner is minting it.**, and
after 20 seconds **Still waiting for a runner to mint it.** with a link to the runners; with no runner
online, it cannot finish. The browser then saves the file. **Cancel**, or closing the record, stops the wait, and a kubeconfig finished
after that expires unread. Details, including private endpoints, are in
[Get a kubeconfig](/guides/get-a-kubeconfig#get-a-kubeconfig-from-the-console).

## What every cluster has

ArgoCD installs ArgoCD itself, External DNS, the External Secrets Operator, Metrics Server and a
storage class (GP3 EBS, Persistent Disk or Managed Disk). On AWS it also installs the AWS Load
Balancer Controller and Karpenter. See [GitOps with ArgoCD](/concepts/gitops-argocd).

The names, endpoints and ArgoCD address come from the OpenTofu outputs of the last successful deploy.

## Check that it worked

The record shows the cluster's status and components, and `kubectl` with the kubeconfig lists the
cluster's nodes.
