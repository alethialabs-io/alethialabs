# Get a kubeconfig for your cluster

`alethia cluster kubeconfig` gets you a short-lived kubeconfig for a cluster that Alethia
provisioned. You do not need a login to the cloud account. A runner in your organization mints the
credential inside the cluster's network and seals it to a one-time key that the CLI makes. Only
the machine that ran the command can open the result.

This page shows you how to get the kubeconfig and how to choose its tier, lifetime and shape. It
also tells you how to reach a private endpoint, how to revoke access, and how to fix each refusal.
For every flag and default, see the
[`alethia cluster kubeconfig` reference](/reference/cli/clusters#alethia-cluster-kubeconfig).

<Callout type="info">
  If you already have a login to the cloud account, you can also use your own cloud CLI. The
  **Kubeconfig** row of `alethia cluster get` and the cluster card show that command. See
  [kubeconfig commands](/guides/clusters#kubeconfig-commands).
</Callout>

## Before you begin

Make sure that:

- The `alethia` CLI is installed and you are signed in. See [Install the CLI](/get-started/install-the-cli).
- The cluster runs on AWS, GCP, Azure, Alibaba Cloud or Hetzner. Other clouds cannot mint a
  kubeconfig through Alethia.
- The environment has at least one successful deploy, and it is not being destroyed.
- The environment has a `dedicated` placement. An environment placed on a shared cluster as a
  `namespace` or `vcluster` cannot get a kubeconfig, because the credential would give access to
  the whole shared cluster. See [Fabrics & Placement](/concepts/fabrics-and-placement).
- A runner is online for your organization. The mint runs as a job on it. See [Runners](/guides/runners).
- Your role allows the tier you want. See [Choose the access tier](#choose-the-access-tier).

## Get a read-only kubeconfig

<Steps>
<Step>

### Run the command

```bash
alethia cluster kubeconfig
```

The CLI lists your clusters and asks which one you want. To skip the question, name the cluster.
The selector matches a project name, a cluster name or a cluster ID:

```bash
alethia cluster kubeconfig api-backend
```

</Step>
<Step>

### Wait for the runner

The CLI sends the request, and then waits while a runner mints the credential. On an idle runner
this takes a few seconds. A runner that is busy with a deploy can take longer. The CLI waits for up
to 10 minutes.

</Step>
<Step>

### Use the context

The CLI adds the context `alethia-<project>-<env>` to your kubeconfig and makes it the current
context. It prints the context name and a command to try:

```bash
kubectl --context alethia-api-backend-production get namespaces
```

</Step>
</Steps>

By default the CLI merges the context into the first file in `$KUBECONFIG`, or into
`~/.kube/config`. It replaces an older context with the same name, and it does not change your
other contexts. To write a separate file instead, use `--output`:

```bash
alethia cluster kubeconfig api-backend --output api-backend.kubeconfig
```

## Choose the access tier

There are two tiers. Read-only is the default. Each tier is a separate permission, and a request
gets exactly the tier it asks for. No cloud changes a read-only request into an admin one.

| Tier | Flag | Who can get it | In-cluster identity |
|---|---|---|---|
| Read-only | none (the default) | Owners, admins and operators: the `cluster:access_readonly` permission | The `alethia-view` ServiceAccount in the `alethia-system` namespace, bound to the `alethia:view` ClusterRole |
| Admin | `--admin` | Owners and admins only: the `cluster:access_admin` permission | The cloud's own admin credential for the cluster |

A viewer can get neither tier. A custom role can hold either permission. See
[Roles & permissions](/concepts/access-control/roles-and-permissions).

### What read-only allows

The `alethia:view` ClusterRole grants only the `get`, `list` and `watch` verbs. It is the built-in
Kubernetes `view` role, written out rule by rule, plus nodes, namespaces and events. It does not
aggregate from `view`, so a custom role that a cluster operator aggregates into `view` cannot widen
it.

| API group | Resources |
|---|---|
| core | `pods`, `pods/log`, `pods/status`, `services`, `services/status`, `endpoints`, `configmaps`, `persistentvolumeclaims`, `persistentvolumeclaims/status`, `replicationcontrollers`, `replicationcontrollers/scale`, `replicationcontrollers/status`, `serviceaccounts`, `bindings`, `events`, `limitranges`, `resourcequotas`, `resourcequotas/status`, `namespaces`, `namespaces/status`, `nodes` |
| `apps` | `deployments`, `replicasets`, `statefulsets`, `daemonsets`, with their `scale` and `status` subresources, and `controllerrevisions` |
| `batch` | `jobs`, `cronjobs`, with their `status` subresources |
| `autoscaling` | `horizontalpodautoscalers`, `horizontalpodautoscalers/status` |
| `policy` | `poddisruptionbudgets`, `poddisruptionbudgets/status` |
| `networking.k8s.io` | `ingresses`, `ingresses/status`, `networkpolicies` |
| `discovery.k8s.io` | `endpointslices` |
| `events.k8s.io` | `events` |
| `extensions` | The legacy `deployments`, `replicasets`, `daemonsets`, `ingresses` and `networkpolicies` |

So with read-only access you can run `kubectl get`, `kubectl describe`, `kubectl logs` and
`kubectl events`. You cannot:

- read Secrets, so you cannot read the ArgoCD admin password;
- run `kubectl exec`, `kubectl attach`, `kubectl port-forward` or `kubectl proxy`;
- read custom resources, such as ArgoCD `Application` objects, or RBAC objects;
- change anything.

For any of these, use the admin tier.

### Get an admin kubeconfig

```bash
alethia cluster kubeconfig api-backend --admin
```

On AWS, GCP and Azure, the admin credential is your organization's cloud identity for the cluster.
On Alibaba Cloud it is a certificate that ACK issues to that identity. On Hetzner it is an admin
certificate from the cluster's Talos API. In each case every user maps to the same identity in
the cluster. The read-only tier also uses one shared ServiceAccount for every user. So the
cluster's own audit log cannot tell your users apart. Alethia's record of each request does. See
[What Alethia records](#what-alethia-records).

## Choose how long the credential lasts

`--ttl` sets the credential's lifetime. The default is `1h`. The shortest is `15m` and the
longest is `8h`. The value must be a whole number of seconds, such as `90m` or `2h30m`.

```bash
alethia cluster kubeconfig api-backend --admin --ttl 4h
```

A read-only credential lasts the TTL on every cloud. The cluster's API server sets the final
expiry, and a cluster that limits token lifetimes can make it shorter.

**For an admin credential, the TTL is a ceiling, not a guarantee.** The admin credential is the
cloud's own, and the cloud sets its lifetime. On AWS, GCP, Azure and Hetzner it lasts at most
about an hour, whatever the TTL. The runner reports the credential's real expiry, never a shorter
one. For a static kubeconfig, the CLI prints that expiry when it writes the file.

| Cloud | Read-only | Admin |
|---|---|---|
| AWS | The TTL | 14 minutes, whatever the TTL. The exec plugin gets a new token when it expires. |
| GCP | The TTL | The access token's own lifetime, about 1 hour, whatever the TTL |
| Azure | The TTL | The access token's own lifetime, about 60 to 90 minutes, whatever the TTL |
| Alibaba Cloud | The TTL | The TTL, rounded up to a whole minute |
| Hetzner | The TTL | The cluster's admin certificate lifetime: about 1 hour on the managed template, whatever the TTL. The Talos API cannot shorten it. |

Alethia refuses an admin kubeconfig whose real lifetime is longer than 8 hours. A Hetzner cluster
deployed before the 1-hour lifetime keeps a 24-hour admin certificate, so its admin requests are
refused until its next deploy applies the change. That deploy does not restart any node. Read-only
requests work on that cluster.

## Choose exec or static

A kubeconfig gets its credential in one of two shapes.

| | Exec (the default on AWS, GCP and Azure) | Static (`--static`, and always on Hetzner and Alibaba Cloud) |
|---|---|---|
| What the file holds | No credential. It runs `alethia cluster token` to get one. | The credential itself: a bearer token or a client certificate |
| When the credential expires | `alethia cluster token` mints a new one, so `kubectl` keeps working | The file stops working. Run the command again for a new one. |
| What the machine needs | The `alethia` CLI on the `PATH` wherever `kubectl` runs, with a valid session | Only `kubectl` |
| If someone copies the file | It is useless without a signed-in `alethia` CLI | It works for anyone until it expires |

Hetzner and Alibaba Cloud issue certificates, so their kubeconfig is always static. You do not need
to pass `--static` for them: the CLI asks for exec, and if the cloud refuses, it asks again for
static.

### How the exec shape caches the credential

`alethia cluster token` keeps each credential in a cache until 60 seconds before it expires. So
only the first `kubectl` call in each credential's lifetime waits for a runner. If several `kubectl`
calls start at the same time, they share one mint. The cache is in the CLI's configuration
directory:

| OS | Cache directory |
|---|---|
| Linux | `~/.config/alethia/kubecache` (or `$XDG_CONFIG_HOME/alethia/kubecache`) |
| macOS | `~/Library/Application Support/alethia/kubecache` |
| Windows | `%AppData%\alethia\kubecache` |

The directory has mode `0700` and each file has mode `0600`. The CLI refuses a cache file that
other users can read.

Each new token comes from a new mint, with the tier, TTL and organization that you chose when you
ran `alethia cluster kubeconfig`. Each mint checks your permission again. So if someone removes you
from the organization or changes your role, `kubectl` stops working when the current token expires.

### Use a kubeconfig on another machine or in CI

To print the kubeconfig instead of writing it to a file, use `--output -`. This is the only way
the CLI writes a credential to stdout:

```bash
alethia cluster kubeconfig api-backend --static --output - > api-backend.kubeconfig
```

A static file works on any machine with `kubectl` until it expires. Treat it as a password.

An exec kubeconfig works on another machine only if that machine has the `alethia` CLI and a
session. In CI, use a service token: set `ALETHIA_TOKEN`, or pass `--token`. See
[Running in CI](/reference/cli/authentication#running-in-ci). A machine that did not run
`alethia cluster kubeconfig` has no record of your choices, so it always mints read-only credentials
with a 1-hour TTL, in its active organization.

## Reach a cluster with a private endpoint

The runner checks whether the cluster's API endpoint is reachable from the internet. If it is
private, the CLI still writes the kubeconfig and prints this note:

```
Note: this cluster's API endpoint is private. kubectl needs network access to it from this machine (a VPN or a bastion); the credential alone is not enough.
```

The credential is valid, but `kubectl` must reach the endpoint. Connect to the cluster's network
first, for example through a VPN or a bastion host. Alethia does not proxy traffic to the cluster.

## Revoke access

A short lifetime is the main control. These are the other controls, and their limits:

- **Remove the person's access.** Remove them from the organization, or change their role so that
  it does not hold the `cluster:access_*` permissions. They cannot get a new credential after that.
  An exec kubeconfig stops working when its current token expires. A static file, or a token
  already in the cache, works until it expires.
- **Revoke every read-only credential for a cluster.** Delete the ServiceAccount. Every token it
  issued stops working at once, for every user. You need admin access to do this:

  ```bash
  kubectl -n alethia-system delete serviceaccount alethia-view
  ```

  The next read-only request creates the ServiceAccount again. To find every object that the
  read-only tier created, use the label `app.kubernetes.io/managed-by=alethia`.
- **Admin credentials cannot be revoked through Alethia.** They end at their real expiry, as shown
  in [the lifetime table](#choose-how-long-the-credential-lasts). On Hetzner the admin
  certificate lasts about an hour, and only a rotation of the cluster's certificate authority ends
  it earlier.
- **Clear the cache on a machine.** `alethia logout` does not delete the credential cache yet. To
  end access from a machine at once, delete the cache directory from
  [the table above](#how-the-exec-shape-caches-the-credential).

## What Alethia records

Alethia writes an audit record **before** it returns a credential. It writes one record when you
request a kubeconfig, and one when the CLI collects it. Each record holds:

- who asked, and from which IP address;
- the cluster, the tier, the shape and the requested TTL;
- the client (the CLI) and whether the call used a session or a service token.

The record never holds the credential. Alethia does not store the credential either: the console
holds only the sealed copy, and it deletes that copy when the CLI collects it, or 10 minutes after
the request.

A refused request appears in [Activity](/guides/access/activity-log) as a denied attempt, like
every other refused action.

## Troubleshoot

`alethia cluster kubeconfig` prints each error after `Error:`. `alethia cluster token` prints
each error after `alethia cluster token:`, and `kubectl` shows that line.

### Refusals from the control plane

| Status | Message | What to do |
|---|---|---|
| 401 | your session is not valid — run `alethia login`, then try again | Run `alethia login`. |
| 402 | your organization's plan does not allow another kubeconfig right now: … (see `alethia usage`) | The mint runs on a runner, so it uses runner minutes. Run `alethia usage` to see the limit you reached. |
| 403 | your role cannot mint a kubeconfig for this cluster (owners, admins and operators can) | Ask an owner or admin for a role that holds `cluster:access_readonly`. |
| 403 | your role cannot mint an admin kubeconfig for this cluster (owners and admins can); drop --admin for read-only access | Run the command again without `--admin`, or ask for a role that holds `cluster:access_admin`. |
| 404 | the cluster was not found in the active organization (`alethia org switch`, or pass --org) | Switch to the cluster's organization with `alethia org switch`, or pass `--org`. |
| 409 | The cluster has not been provisioned, so there is nothing to mint a kubeconfig for — deploy the environment first (`alethia project apply`) | Deploy the environment. A draft environment, one being destroyed, and one with no successful deploy cannot get a kubeconfig. |
| 422 | This cluster's cloud cannot mint a kubeconfig through Alethia | The cluster is not on AWS, GCP, Azure, Alibaba Cloud or Hetzner, or it has no cloud identity. Use the cloud's own CLI. |
| 429 | too many kubeconfig requests — try again in … | You made more than 20 requests in 10 minutes in this organization. Each new exec token counts as a request. Wait for the time shown. |

### Messages while the CLI waits

| Message | What to do |
|---|---|
| the kubeconfig request expired before a runner completed it — check that a runner is online for this organization (`alethia runner list`), then try again | No runner collected the job within 10 minutes. Check that a runner is online with `alethia runner list`. |
| timed out waiting for a runner to mint the kubeconfig — check that a runner is online … | The same as above, measured on your machine's clock. |
| the kubeconfig request is gone (already collected, or expired and swept) — run the command again | Run the command again. A credential can be collected only once. |
| your role no longer allows collecting this kubeconfig (it changed after the request) | Your role changed while the mint ran. Ask for the permission again. |
| the minted credential had already expired when it arrived; check this machine's clock, then try again | Set your machine's clock correctly. |

### Reasons a runner gives

When a mint fails, the CLI prints `the runner could not mint the kubeconfig:` and one of these
reasons. The runner sends only these fixed sentences, never the cloud's own error text.

| Reason | What to do |
|---|---|
| The runner could not mint the credential. | A cause with no specific sentence. Read the mint job's log with `alethia jobs logs --latest --type MINT_KUBECONFIG`. |
| The cluster was not found in the cloud account. | The cluster no longer exists, or it was renamed outside Alethia. Check it in the cloud console. |
| The runner could not reach the cluster's API endpoint. | Check that the runner's network can reach the cluster's API endpoint. |
| The runner could not assume the cluster's cloud identity. | Check the cloud identity in [Connectors](/guides/connectors). |
| The cloud refused to issue a credential for this cluster. | The cloud identity cannot get cluster credentials. Check its permissions in the cloud. |
| The read-only identity could not be prepared in the cluster. | The runner could not create or check the `alethia-view` ServiceAccount or the `alethia:view` ClusterRole. Check whether someone changed them. |
| This cloud cannot issue the requested kubeconfig shape. | Run the command again without `--static`, or with it. |
| The runner could not seal the credential to the client key. | Run the command again. |
| Kubeconfig mints are not available for an environment placed on a shared cluster. | The environment has a `namespace` or `vcluster` placement. See [Before you begin](#before-you-begin). |

### Other errors

| Message | What to do |
|---|---|
| --ttl must be whole seconds from 15m to 8h | Pass a TTL from `15m` to `8h`. |
| --output takes a file path here (or - for stdout), not a format | In this command `--output` takes a file name. To write a file called `json`, pass `./json`. |
| if any flags in the group [merge output] are set none of the others can be | Pass `--merge` or `--output`, not both. |
| … is locked by another writer (kubectl?) | Another program is writing your kubeconfig. If nothing is running, delete the `.lock` file that the message names. |
| kubecache: insecure cache file | A cache file can be read by other users. Delete the file that the message names, then run the command again. |
| a cluster id is required | `alethia cluster token` needs a cluster ID when it does not run at a terminal. Get a new kubeconfig with `alethia cluster kubeconfig`. |

### kubectl says "You must be logged in to the server (Unauthorized)"

The credential expired, or someone revoked it. With a static kubeconfig, run
`alethia cluster kubeconfig` again.

With an exec kubeconfig, the cache can still hold a token that was revoked, for example after
someone deleted the read-only ServiceAccount. The cache serves that token until 60 seconds before
it expires. Delete the cache directory from
[the table above](#how-the-exec-shape-caches-the-credential), then run `kubectl` again. The next
mint creates the ServiceAccount again.
