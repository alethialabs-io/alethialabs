---
title: Get a kubeconfig for your cluster
description: Get a short-lived kubeconfig for a cluster that Alethia deployed, from the CLI or the console, without a login to the cloud account.
---

Get a kubeconfig that lets `kubectl` reach your cluster for a limited time. You do not need a login
to the cloud account. How this works, and how to revoke it, is in
[Cluster access](/concepts/cluster-access).

## Before you begin

- The `alethia` CLI is installed and you are signed in. See [Install the CLI](/get-started/install-the-cli).
- The cluster runs on AWS, GCP, Azure or Hetzner, and its environment has had at least one
  successful deploy.
- The environment has a `dedicated` placement. An environment on a shared cluster (`namespace` or
  `vcluster`) cannot get a kubeconfig. See [Fabrics & Placement](/concepts/fabrics-and-placement).
- A runner is online for your organization. See [Runners](/guides/runners).
- Your role is owner, admin or operator. Only owners and admins can get admin access.

## Get a kubeconfig from the CLI

<Steps>
<Step>

### Run the command

```bash
alethia cluster kubeconfig
```

The CLI lists your clusters and asks which one you want. To skip the question, name the project,
the cluster, or the cluster ID:

```bash
alethia cluster kubeconfig api-backend
```

</Step>
<Step>

### Wait for the runner

A runner in your organization makes the credential. On an idle runner this takes a few seconds. The
CLI waits up to 10 minutes.

</Step>
<Step>

### Use the context

The CLI adds the context `alethia-<project>-<env>` to your kubeconfig, makes it the current
context, and prints a command to try:

```bash
kubectl --context alethia-api-backend-production get namespaces
```

</Step>
</Steps>

The CLI writes to the first file in `$KUBECONFIG`, or to `~/.kube/config`. It replaces an older
context with the same name and leaves your other contexts alone. To write a separate file, add
`--output api-backend.kubeconfig`.

## Get a kubeconfig from the console

1. Open **Clusters** and select the cluster's row.
2. Under **Cluster access**, select **Download kubeconfig (1h, read-only)**.
3. Wait while the record shows **A runner is minting it.** Your browser then saves
   `alethia-<project>-<env>.kubeconfig`.

The console file is always read-only, lasts 1 hour, and holds the credential itself. Anyone who has
the file can use it until it expires, so treat it as a password. For anything else, use the CLI.
The download needs Chrome 133, Firefox 130 or Safari 17 or later, over HTTPS.

## Choose the options

| You want | Add | What changes |
| --- | --- | --- |
| Full control of the cluster | `--admin` | The cloud's own admin credential instead of read-only. Owners and admins only, and never a service token. |
| A longer or shorter lifetime | `--ttl 4h` | From `15m` to `8h`; the default is `1h`. An admin credential lasts at most what the cloud allows, about an hour. |
| A file that needs only `kubectl` | `--static` | The file holds the credential. Without it, the file calls `alethia cluster token` each time it needs a new one. Hetzner is always static. |
| A separate file | `--output <file>` | Writes that file instead of merging into your kubeconfig. `--output -` prints to stdout. |

Read-only access lets you run `kubectl get`, `describe`, `logs` and `events`. It cannot read
Secrets or custom resources, run `exec` or `port-forward`, or change anything. The full list of
resources is in [Cluster access](/concepts/cluster-access#what-read-only-allows).

## Use it in CI or on another machine

A static file works on any machine with `kubectl` until it expires:

```bash
alethia cluster kubeconfig api-backend --static --output - > api-backend.kubeconfig
```

An exec kubeconfig needs the `alethia` CLI and a session on the machine that runs `kubectl`. In
CI, set `ALETHIA_TOKEN` to a service token. See
[Running in CI](/reference/cli/authentication#running-in-ci). A service token gets read-only access
only.

## If the cluster's endpoint is private

The CLI and the console say so when they hand you the kubeconfig. The credential is valid, but
`kubectl` must reach the endpoint: connect through a VPN or a bastion host first. Alethia does not
proxy traffic to the cluster.

## Check that it worked

```bash
kubectl --context alethia-api-backend-production get nodes
```

You see the cluster's nodes. If you see `Unauthorized`, a refusal, or the CLI times out, see
[Troubleshoot cluster access](/troubleshooting/cluster-access).
