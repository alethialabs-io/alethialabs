# HashiCorp Vault

One file, `default.yaml`, because nothing here depends on the cloud.

## What "install Vault" used to give you

A sealed one. `vault operator init` had never been run, so the server answered nothing, its readiness
probe never passed, and the Application sat Progressing at any budget — on every cloud, with no knob
in the product that could change it. The chart has no init hook: HashiCorp's position is that
initialising is an operator act, and `server.postStart` is left empty for you to fill.

`initialize` (on by default) fills it. Alethia applies a one-shot Job **inside the cluster** — Vault
answers only on the cluster network, so nothing outside it can do this — which initialises, unseals,
mounts KV v2 at `secret/`, and revokes the root token.

## Where the key goes

The seal is **Shamir**, and the unseal key is written to the `alethia-vault-addon-state` Secret in
the add-on's own namespace. Nowhere else: not to Alethia, not to the job log, not into the deploy's
config snapshot. It is generated by Vault inside the cluster and stored by a pod in that cluster.

Say the limit of that plainly, because a claim nobody can reconcile with the design is worse than no
claim: against a cluster-admin, an etcd backup, or a volume snapshot, an unseal key sitting in the
same etcd as the ciphertext buys **nothing** over a plain Secret. What it buys is real and different
— an audit log of every read, leases, revocation and rotation — and it is on a cluster you already
control.

**No standing root token exists.** The Job revokes the one `vault operator init` returns before it
exits. Mint an operator credential when you need one, with the unseal key:

```sh
vault operator generate-root -init            # prints a nonce and an OTP
vault operator generate-root -nonce=<nonce>   # paste the unseal key
vault operator generate-root -decode=<encoded token> -otp=<otp>
```

## Auto-unseal with a cloud KMS

Vault's `awskms` / `gcpckms` / `azurekeyvault` seals remove the need to hold an unseal key across
restarts — and they do **not** remove the need for this Job. `vault operator init` is still required
exactly once and still has to be run by somebody; auto-unseal is an alternative to *storing a key*,
not to *initialising*.

If you own a KMS key and an identity the pod can assume, reach that seal through the add-on's
Advanced values YAML, which deep-merges over `server.standalone.config`. Alethia does not provision
the key or the identity binding: a marketplace add-on is a chart plus your configuration, and it can
see neither the project's cloud nor its infrastructure outputs.

## What is deliberately not here

Nothing in this directory is a secret, so there is no incomplete file to warn about — Vault mints its
own credentials once it is open.
